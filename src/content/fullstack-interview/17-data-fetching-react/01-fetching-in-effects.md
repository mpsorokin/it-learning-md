# Fetching in Effects

## Interview questions

### Когда fetch через useEffect приемлем?
<!-- question-id: 17-data-fetching-react-q01 -->
#### Ответ

Предположение для примеров: React 19.2.8; версия библиотеки запросов не задана, поэтому для TanStack Query ниже подразумевается v5. Ручной fetch в Effect приемлем для небольшой client-only части, когда запрос действительно является синхронизацией с внешней системой, результат принадлежит одному экрану и не нужны предварительная загрузка, общий cache, дедупликация или сложная политика повторов. Effect запускается после client commit, зависит от полного набора реактивных параметров и должен очищать предыдущую работу при смене параметров и unmount. Для fetch обычно используют AbortController плюс защиту от устаревшего результата; проверяют response.ok, сетевые ошибки и форму JSON до помещения данных в state. Effect не запускается при server rendering, поэтому для маршрута, где важен заполненный HTML до hydration, предпочтительнее data loader фреймворка или server rendering. В большой части экранов проще передать владение запросом framework data API или cache-библиотеке: ручной Effect быстро превращается в самодельную систему cache, retries, race handling и loading states. Strict Mode в development намеренно делает setup → cleanup → setup, так что корректность не должна зависеть от однократного mount. См. [React: useEffect](https://react.dev/reference/react/useEffect).

### Какие проблемы у ручного fetch в Effect?
<!-- question-id: 17-data-fetching-react-q02 -->
#### Ответ

Effect выполняется только на клиенте: первоначальный server-rendered ответ содержит loading UI, а браузер должен загрузить JavaScript и выполнить hydration, прежде чем начать запрос. Если дочерние компоненты ждут данные родителя для собственных запросов, получается waterfall; требования данных лучше поднять к маршруту и параллелить. Компоненты, которые размонтировались и смонтировались снова, без общего cache повторяют запрос; несколько потребителей не дедуплицируют его автоматически. Каждый экран вручную реализует pending/error/empty/refetch states, retry, backoff, отмену и race protection, а также правила stale data и повторной синхронизации при фокусе или reconnect. Пропущенная dependency либо показывает данные для старого ID, либо новая нестабильная функция запускает лишний цикл. Abort отменяет клиентское ожидание, но не гарантирует откат уже выполненной серверной операции. Поэтому Effect годится для локального простого запроса, а общие ресурсы лучше описывать declarative query по ключу или использовать встроенный data fetching фреймворка. Ручное решение оправдано, если оно проще и имеет явные тесты на смену параметров, unmount, ошибку и ответы в обратном порядке. [React описывает эти ограничения и альтернативы](https://react.dev/reference/react/useEffect#what-are-good-alternatives-to-data-fetching-in-effects).

### Cache.
<!-- question-id: 17-data-fetching-react-q03 -->
#### Ответ

Cache — локальная реплика данных с известным ключом и политикой актуальности, а не новый источник истины. Она экономит повторные сетевые round trips, сохраняет уже полученные данные между mount-ами, позволяет нескольким observer-ам читать один resource и поддерживает background refresh. Ключ должен однозначно описывать ресурс и все влияющие на результат параметры: tenant/user scope, фильтры, сортировку, страницу, locale или версию API; секреты вроде access token обычно в ключ не помещают. Cache требует правил stale/fresh, invalidation после записи, удаления старых записей, ошибок и границы доступа. Его scope важен: browser QueryClient обычно живёт на уровне приложения, тогда как SSR требует нового клиента на запрос/пользователя, иначе данные одного запроса могут попасть другому. Persistent cache отдельно увеличивает срок хранения и должен учитывать logout, смену пользователя, размер и чувствительные данные. Нельзя считать, что cache гарантирует актуальность: сервер остаётся authoritative, а клиентская копия обновляется по выбранному протоколу.

### Deduplication.
<!-- question-id: 17-data-fetching-react-q04 -->
#### Ответ

Дедупликация объединяет конкурентные запросы за одним и тем же ресурсом: наблюдатели одного QueryClient с одним ключом могут разделить выполняющийся Promise и его результат. Это не синоним cache и не дедупликация всех URL: одинаковый endpoint с разными фильтрами, tenant или ключом — разные данные; разные QueryClient также имеют разный scope. Правильный query key является частью корректности: слишком общий ключ смешивает данные, слишком уникальный теряет совместное использование. Повторные запросы после завершения регулируются свежестью, invalidation и refetch policy, а не только in-flight dedupe. Мутации обычно не объединяются автоматически, потому что две записи могут иметь разные side effects и порядок; для повторяемых команд нужен idempotency key или серверное правило. При SSR безопасная дедупликация действует в пределах одного request-scoped клиента, а глобальный singleton клиента на сервере создаёт риск утечки данных между пользователями.

### Race conditions.
<!-- question-id: 17-data-fetching-react-q05 -->
#### Ответ

Race возникает, когда для A начат запрос A, затем параметр меняется на B, запрос B завершается быстрее, и более поздний ответ A перезаписывает состояние экрана. В ручном Effect для каждого запуска создают свой AbortController и флаг active/request generation; cleanup отменяет fetch и запрещает старому запуску менять state. Abort экономит сеть/парсинг там, где API поддерживает signal, а проверка актуальности нужна даже при abort: ответ мог уже завершиться, сторонний клиент может игнорировать signal, а серверная работа не отменяется. Данные желательно привязывать к ключу параметров, чтобы временно не показать результат прошлого пользователя под новым заголовком; если сохраняем их как placeholder, UI должен явно показывать переход. Query library разделяет cache entries ключами и управляет отменой, но ключи всё равно должны быть полными. Для записи race решается иначе: нужны серверные версии/ETag, idempotency и конфликтная политика, а не только клиентский AbortController. [React рекомендует abort или игнорирование результата в cleanup](https://react.dev/learn/synchronizing-with-effects#fetching-data).
