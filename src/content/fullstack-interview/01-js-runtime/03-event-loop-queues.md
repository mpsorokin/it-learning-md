# Event Loop и очереди

## Interview questions

### Что такое Event Loop?
<!-- question-id: fullstack-interview-01-js-runtime-010 -->

#### Ответ

Event Loop — механизм host-среды, который координирует выполнение JavaScript и готовые асинхронные callbacks. ECMAScript определяет Promise jobs и выполнение языка, а браузерный task loop, rendering opportunities, timers и I/O определяются HTML/host API; Node.js имеет собственную event-loop архитектуру. Поэтому популярная схема «одна общая очередь макрозадач и одна очередь микрозадач» полезна для базовых примеров, но не полностью описывает все среды.

В браузере агент выполняет текущий task до завершения, затем обрабатывает microtask queue до опустошения (включая новые microtasks), после чего браузер может обновить rendering и выбрать следующий task. Реальная последовательность зависит от готовности задач и rendering opportunities. Event loop не делает синхронный JavaScript параллельным: пока выполняется длинный callback, тот же агент не обслуживает ввод и не рисует кадр.

В Node.js есть дополнительные фазы и API, включая timers, poll, check и `process.nextTick`; относительный порядок не следует механически переносить из браузера. Для корректности нужно указывать host и проверять контракт нужного API.

### Зачем Event Loop нужен JavaScript?
<!-- question-id: fullstack-interview-01-js-runtime-011 -->

#### Ответ

JavaScript в обычном браузерном main thread выполняет синхронный код последовательно. Host-среда может завершать I/O, таймеры и другие операции вне этого стека, а Event Loop передаёт callback в JS, когда host считает его готовым к запуску. Это даёт отзывчивую координацию событий без необходимости приостанавливать текущую инструкцию посреди выполнения.

Модель устраняет блокировки ожиданием I/O: пока запрос сети ожидает, поток может обрабатывать другие события. Однако она не гарантирует, что тяжёлое вычисление будет вынесено в отдельный поток. Длинная синхронная задача или бесконечная цепочка microtasks блокируют обработку других задач и rendering на том же event loop.

Для CPU-bound работы используют Web Workers или worker threads, передавая им данные и принимая результат сообщением; shared memory требует явной синхронизации. Даже при worker-ах у каждого JS agent свой цикл выполнения, а DOM обычно доступен только main thread.

### Что такое task/macrotask?
<!-- question-id: fullstack-interview-01-js-runtime-012 -->

#### Ответ

Task (часто неформально «macrotask») — единица работы host event loop: например, выполнение script, callback таймера, обработчик пользовательского события или некоторые сообщения/I/O callbacks. Термин «macrotask» широко используется в обучающих материалах, но браузерная спецификация HTML чаще говорит «task» и описывает очереди задач по task source, а не одну универсальную FIFO очередь.

Event Loop запускает одну готовую task; её синхронный код выполняется до конца. В браузере затем наступает microtask checkpoint, после которого host может перейти к rendering и следующей задаче. Приоритет и порядок между разными task sources не всегда задаются простым глобальным FIFO.

Практический пример — `setTimeout(fn, 0)`: callback становится runnable после минимальной задержки и попадания в соответствующую очередь, но сначала завершается текущий стек и выполняются microtasks. Фоновая вкладка может дополнительно ограничивать timers. В Node.js timers/I/O относятся к фазам его цикла, поэтому детали отличаются.

### Что такое microtask?
<!-- question-id: fullstack-interview-01-js-runtime-013 -->

#### Ответ

Microtask — короткая задача-последовательность, выполняемая в microtask checkpoint до перехода к следующей host task. Ключевые источники в браузере — обработчики Promise (`then`, `catch`, `finally`) и queueMicrotask; разрешение `await` продолжает async-функцию через Promise job. MutationObserver также вызывает callback в рамках microtask-механизма.

Очередь обычно обрабатывается до опустошения, поэтому microtask, которая добавляет следующую microtask, может бесконечно откладывать rendering и tasks. Это даёт удобный способ упорядочить продолжения после текущего синхронного кода, но не способ уступить браузеру кадр. Для уступки нужны host task scheduling API, например таймер/MessageChannel, либо актуальный scheduler API, если он есть в целевых браузерах.

Не смешивать microtask с отдельным потоком и не обещать идентичное поведение host-ов для всех очередей: особенно в Node.js присутствует `process.nextTick`, который имеет собственные правила и приоритет относительно Promise callbacks.

### Какие API создают microtasks?
<!-- question-id: fullstack-interview-01-js-runtime-014 -->

#### Ответ

В ECMAScript/браузере Promise reaction jobs создаются при `.then()`, `.catch()` и `.finally()`; продолжение после `await` также асинхронно ставится как Promise job. `queueMicrotask(callback)` напрямую планирует callback в microtask queue браузерного агента. В DOM есть `MutationObserver`, callbacks которого доставляются через microtask checkpoint.

В Node.js доступны Promise microtasks и `queueMicrotask`, но для `process.nextTick` используется отдельная очередь с особыми правилами, а не просто эквивалент браузерной microtask. MutationObserver доступен лишь в средах с соответствующим DOM API.

`setTimeout(..., 0)`, `setImmediate` и `MessageChannel` не являются microtasks: это способы поставить работу для последующей host task/фазы. Отличие критично для порядка выполнения и fairness. Не полагайтесь на одинаковый порядок между разными источниками задач без документации конкретной среды.

### Какие API создают tasks/macrotasks?
<!-- question-id: fullstack-interview-01-js-runtime-015 -->

#### Ответ

Task создают host API, а конкретная классификация зависит от среды. В браузере типичные примеры — `setTimeout`/`setInterval`, обработчики событий ввода, сетевые callbacks и сообщения `postMessage`; `MessageChannel` доставляет сообщение как task. Сам script обычно исполняется в task. `requestAnimationFrame` относится к rendering update, а не к универсальной «очереди таймеров».

Node.js планирует timers и callbacks I/O в фазах своего цикла, имеет `setImmediate`, а callbacks некоторых API приходят из внутреннего thread pool. Browser APIs нельзя автоматически приписывать Node.js и наоборот.

Важно, что готовность callback-а не означает немедленный запуск: текущий стек и microtasks должны закончиться, а host выбирает следующую доступную task. Порядок таймера относительно событий другого task source обычно нельзя вывести только из чисел задержки.

### Когда выполняется microtask queue?
<!-- question-id: fullstack-interview-01-js-runtime-016 -->

#### Ответ

В браузере после завершения текущей task выполняется microtask checkpoint: очередь обрабатывается до опустошения, включая microtasks, добавленные другими microtasks. Только потом host получает возможность запустить rendering update и выбрать следующую task. Если JavaScript запланировал несколько Promise callbacks, они выполняются после текущего синхронного фрагмента, но до таймера или следующего пользовательского события, если те уже готовы.

Это описание HTML event loop для обычных браузерных задач; rendering может быть пропущен, если кадр не нужен или вкладка неактивна. В Node.js checkpoint-и выполняются по правилам Node и взаимодействуют с фазами цикла и `process.nextTick`.

Практически это объясняет, почему `Promise.resolve().then(...)` обычно выполняется раньше callback-а `setTimeout(..., 0)`, но не следует выводить из этого всеобщий порядок для `MessageChannel`, `setImmediate` или разных host-ов. Если порядок важен, выразите зависимость цепочкой Promise/await или конкретным API, а не случайным таймингом.

### Может ли microtask queue заблокировать rendering?
<!-- question-id: fullstack-interview-01-js-runtime-017 -->

#### Ответ

Да. Браузеру удобно выполнять rendering после текущего task и microtask checkpoint, но перед тем, как он это сделает, очередь microtasks должна опустеть. Если каждая microtask добавляет следующую, checkpoint никогда не завершится — кадр и обработка событий не получат времени. Даже конечная длинная цепочка может превысить бюджет кадра и вызвать заметный jank.

Это не обязательно только микрозадачи: длинная синхронная task также мешает rendering. Для большого объёма вычислений разбивайте работу на порции и периодически уступайте host event loop через task scheduling; `await Promise.resolve()` уступает только microtask-очереди и не гарантирует кадр. Для CPU-heavy кода предпочтителен Worker, для анимации — короткий расчёт в `requestAnimationFrame`.

При диагностике смотрят Long Tasks/Performance профили, а не только субъективный лаг. Нужно учитывать мобильные устройства, фоновые вкладки и стоимость layout/paint: устранение starvation JS не гарантирует, что rendering станет дешёвым.

### Что такое microtask starvation?
<!-- question-id: fullstack-interview-01-js-runtime-018 -->

#### Ответ

Microtask starvation — ситуация, когда microtasks непрерывно пополняют собственную очередь и не дают Event Loop перейти к следующей task. Например, рекурсивный вызов `queueMicrotask(run)` внутри `run` не завершается. Синхронная часть каждой итерации короткая, но очередь checkpoint не опустеет; таймеры, события и браузерный rendering могут голодать.

Похожая проблема возникает при рекурсивной цепочке `Promise.resolve().then(...)` или бесконечном цикле `await Promise.resolve()`: `await` уступает текущий синхронный стек, но продолжение снова попадает в microtask, а не в task.

Если требуется кооперативно обработать много элементов, используйте ограниченный batch и переносите следующий batch в host task (`setTimeout`, `MessageChannel`, поддерживаемый scheduler API) либо в Worker. Выбирайте размер порции измерением, а отмену и ошибки обработки делайте явными. Просто добавлять `await Promise.resolve()` не решает starvation.
