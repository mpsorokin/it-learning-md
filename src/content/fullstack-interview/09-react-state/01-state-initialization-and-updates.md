# State initialization and updates

## Interview questions

### Как работает useState?
<!-- question-id: 09-react-state-q01 -->
#### Ответ

`useState(initialState)` связывает ячейку состояния с текущей identity компонента в React tree и возвращает snapshot этого state плюс setter. Первое значение используется при mount; последующий render получает сохранённое состояние, а новое значение аргумента `initialState` игнорируется. Setter ставит update в очередь и просит React выполнить render; переменная state в уже запущенном обработчике не меняется.

Hooks нужно вызывать на верхнем уровне компонента в одном порядке на каждом render-е. Setter имеет стабильную identity, принимает прямое следующее значение или pure updater от pending state, а updates могут batching-иться. React обычно пропускает работу для потомков, если новый state равен старому по `Object.is`, но точное количество render calls не является контрактом.

State objects/arrays следует обновлять immutable способом. Функция как аргумент имеет особую семантику initializer/updater; чтобы хранить функцию как само значение, передают обёртку `() => fn`.

### Lazy initialization.
<!-- question-id: 09-react-state-q02 -->
#### Ответ

Если начальное значение требует дорогого вычисления, передайте initializer функцию без вызова: `useState(createInitialState)`. React вызовет её при инициализации state компонента, а не на каждом render-е; результат станет начальным значением. Функция должна быть pure, не принимать аргументы и не производить side effects.

В Strict Mode в development React может вызвать initializer дважды, чтобы обнаружить impurity, и отбросить один результат; это не дублирует production side effects, потому что их там вообще не должно быть. При remount или изменении `key` initializer снова запустится. Если вычисление зависит от изменяемых props, lazy initializer не синхронизирует его автоматически после mount.

Не путать с `useMemo`: lazy initializer задаёт начальный state, а memoization кеширует производное вычисление и остаётся оптимизацией. Для server-rendered приложения начальный render должен быть детерминированным и согласованным на сервере/клиенте.

### Почему:
<!-- question-id: 09-react-state-q03 -->

```text
useState(expensiveFunction())

может быть проблемой?
```

#### Ответ

В выражении `useState(expensiveFunction())` JavaScript сначала синхронно вызывает `expensiveFunction`, а уже затем передаёт его результат в `useState`. React использует получившийся результат лишь при первом mount и игнорирует при следующих render-ах, но внешняя функция всё равно будет вычисляться каждый раз до вызова Hook — это лишняя CPU/память и потенциально опасный side effect.

Исправление — передать функцию как initializer, без круглых скобок: `useState(expensiveFunction)`, либо `useState(() => expensiveFunction())`, если нужно передать аргументы/добавить логику. Сам initializer должен быть чистым: в Strict Mode development может выполниться дважды при инициализации.

Функция `expensiveFunction` должна вернуть initial value, не менять глобальное состояние, не отправлять запрос и не читать nondeterministic данные, если это повредит SSR hydration. Запросы/подписки запускают через подходящий data-loading mechanism/effect, а не в initializer.

### Почему:
<!-- question-id: 09-react-state-q04 -->

```text
useState(() => expensiveFunction())

лучше?
```

#### Ответ

В форме `useState(() => expensiveFunction())` стрелка и есть initializer, который React вызывает при начальной инициализации state. Вычисление перестаёт происходить при каждом render-е; React хранит результат до очередного state update/remount. Сама стрелка создаётся как аргумент при вызове компонента, но её тело не выполняется на повторных render-ах.

Этот способ корректен для pure вычисления начального значения и не обновляет state при изменении `props`. В dev Strict Mode initializer может быть вызван дважды. Если функция должна храниться в state как значение, функция-обёртка должна вернуть её: `useState(() => callback)`; аналогично setter функции как value вызывают `setCallback(() => nextCallback)`, иначе React трактует её как updater.

Инициализировать state из props допустимо, когда это именно стартовая величина (например, draft с reset на новую сущность через `key`). Если источник должен оставаться синхронизированным, контролируйте его props/state явно, а не ожидайте повторного запуска initializer.

### Functional updater.
<!-- question-id: 09-react-state-q05 -->
#### Ответ

Функциональный updater — функция `prev => next`, переданная setter-у. React ставит её в очередь и во время обработки update применяет к предыдущему pending state; следующий updater получает результат предыдущего. Поэтому несколько зависимых изменений складываются корректно независимо от snapshot, из которого был вызван handler.

    setCount(current => current + 1);
    setCount(current => current + 1);

Такой код даёт прибавку на два в итоговом состоянии. Updater должен быть pure и не мутировать `current`, не менять внешние переменные и не запускать I/O; Strict Mode development может вызвать updater повторно и проигнорировать один результат. Если следующее значение не зависит от предыдущего, можно передать значение напрямую.

Не используйте updater ради побочных эффектов или чтобы получить синхронный callback: setter не возвращает рассчитанное значение. Для нескольких связанных полей рассмотрите один объектный state/reducer, чтобы обновление сохраняло инварианты.

### Почему:
<!-- question-id: 09-react-state-q06 -->

```text
setCount(count + 1)
setCount(count + 1)

не обязательно даст +2?
```

#### Ответ

В одном обработчике обе правые части вычисляются немедленно из state snapshot того render-а, который создал handler. Если `count` равен 0, обе строки вызывают `setCount(1)`; очередь содержит два одинаковых replacement updates, а не два «прибавить единицу». В итоге отображаемое значение станет 1, не 2.

Нужно описать преобразование через updater, чтобы каждый шаг брал pending результат предыдущего: `setCount(c => c + 1)` дважды. Тогда очередь применит `0 → 1 → 2`. Batching группирует render, но сам не превращает прямые значения в инкременты.

Если новые данные вычисляются из другого authoritative source, избегайте отдельного derived state и стройте transition вокруг актуального значения. Проверить сценарий стоит одним кликом с React Profiler/тестом итогового состояния, а не числом вызовов setter-а.

### State snapshot.
<!-- question-id: 09-react-state-q07 -->
#### Ответ

State snapshot — значение state, которое React передал конкретному вызову компонента. Обработчик события и созданные в этом render-е closures видят именно этот snapshot всю жизнь функции; `setState` запрашивает будущий render, но не мутирует локальную переменную. Поэтому `console.log(state)` сразу после setter-а выведет старое значение, и Promise/timer callback, захваченный тем же render-ом, тоже увидит его.

В следующем render React передаст новый snapshot и создаст новые обработчики. Для зависимого от актуального previous state обновления используйте functional updater; если нужен mutable, не визуальный lifecycle value — ref; если новое значение должно быть рассчитано для UI, не обходите модель через прямую DOM mutation.

Snapshot предотвращает состояние, которое меняется «под ногами» уже запущенного обработчика, и особенно важен при batching/concurrent rendering. Он не гарантирует, что внешний callback сам по себе будет отменён при unmount; для ресурсов нужен cleanup/abort.

### State batching.
<!-- question-id: 09-react-state-q08 -->
#### Ответ

Batching означает, что React собирает state updates и обычно обрабатывает их после выполнения текущего event handler, чтобы не показывать промежуточный UI и избежать лишних render/commit циклов. Несколько setters для разных переменных попадут в один обработанный результат; функциональные updates каждой переменной применяются по очереди.

Начиная с React 18 `createRoot` batching автоматически охватывает также Promise/timer и native event callbacks; legacy root имел более ограниченное поведение. Отдельные пользовательские события не объединяются между собой, а `flushSync` может форсировать синхронный commit для редкой интеграции. Strict Mode/concurrent retries влияют на число вызовов render-функции, поэтому не строить логику на ожидаемом количестве вызовов.

Batching не заменяет атомарную модель связанных state-полей: если они должны меняться как одно целое, задайте переход в reducer или один state object с functional update.
