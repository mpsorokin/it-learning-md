# Indexes and Query Planning

## Interview questions

### B-tree.
<!-- question-id: 31-databases-sql-postgresql-q01 -->

#### Ответ

Ориентир ниже — официальная документация PostgreSQL 18, текущей поддерживаемой major-версии на момент подготовки; план конкретного запроса проверяется на вашей версии, данных и настройках. B-tree — сбалансированный упорядоченный индекс, быстро сужающий область поиска по значениям, которые можно сортировать. Он подходит для равенства, диапазонов, сортировок и многих проверок NULL; при подходящей collation/operator class может обслуживать префиксный LIKE, но не обычный шаблон с wildcard в начале.

B-tree — индекс по умолчанию и наиболее универсальный тип: он также поддерживает уникальность и многоколоночные ключи. Цена — дополнительное место и работа на INSERT/UPDATE/DELETE; изменения индексированных столбцов увеличивают write amplification и могут раздувать индекс. Индекс стоит обосновывать частыми запросами и измерениями, а не добавлять автоматически на каждое поле. [Документация PostgreSQL: типы индексов](https://www.postgresql.org/docs/18/indexes-types.html)

### Hash index.
<!-- question-id: 31-databases-sql-postgresql-q02 -->

#### Ответ

Hash index хранит хеш-код ключа и рассчитан на сравнение равенства; он не поддерживает полезные range predicates и сортировку. В PostgreSQL hash-индексы WAL-логируются начиная с версии 10, поэтому утверждение, будто они не восстанавливаются после crash, устарело. При этом B-tree обычно предпочтительнее: тот же equality плюс диапазоны/порядок, уникальность и более широкая применимость.

Ограниченная длина hash code означает возможность коллизии: найденные кандидаты требуется проверить по исходному значению. Hash index не становится автоматически меньше или быстрее B-tree; результат зависит от распределения данных, cache, конкуренции и workload. Рассматривать его разумно лишь для измеренного equality-heavy workload и после проверки EXPLAIN ANALYZE с BUFFERS на production-like данных.

### Composite index.
<!-- question-id: 31-databases-sql-postgresql-q03 -->

#### Ответ

Composite (multicolumn) индекс хранит упорядоченный ключ из нескольких столбцов, например tenant_id, status и created_at DESC. Он полезен, когда частые запросы используют такой набор фильтров/сортировки; порядок ключей определяет, как индекс сужает диапазон и какую сортировку может отдать. Частый шаблон — равенства по ведущим столбцам, затем диапазон или order key, но порядок надо выводить из реальных query patterns.

Дополнительные ключи увеличивают размер и стоимость записи, не заменяют индекс для иного ведущего столбца и не должны добавляться «на всякий случай». PostgreSQL 18 может выбрать B-tree skip scan и для запроса без ограничения ведущего столбца, если по оценке у него достаточно мало distinct значений; это оптимизация плана, а не гарантия, что индекс (a,b) эффективно обслужит любой запрос только по b. [Многоколоночные индексы PostgreSQL 18](https://www.postgresql.org/docs/18/indexes-multicolumn.html)

### Leftmost prefix.
<!-- question-id: 31-databases-sql-postgresql-q04 -->

#### Ответ

Практическое правило для B-tree: индекс (a,b,c) наиболее эффективно сужает диапазон, когда predicate ограничивает ведущий ключ a, затем b. Равенства по ведущим столбцам и первое range-условие обычно задают границы прохода; условия по правым полям могут отсеять строки внутри индекса, но не обязательно сокращают пройденную часть. Поэтому workload WHERE tenant_id = ? AND created_at >= ? обычно подсказывает порядок (tenant_id, created_at), а обратный порядок отвечает другому набору запросов.

Это не абсолютный запрет: PostgreSQL 18 может применить B-tree skip scan для (a,b) и запроса по b, если distinct значений a мало и повторные поиски дешевле чтения всего индекса. Planner может также предпочесть bitmap/index combination или sequential scan. Смотрите actual plan и распределение данных; не стройте схему вокруг лозунга «без первого столбца индекс бесполезен». [Правило ведущих столбцов и skip scan](https://www.postgresql.org/docs/18/indexes-multicolumn.html)

### Covering index.
<!-- question-id: 31-databases-sql-postgresql-q05 -->

#### Ответ

Covering index содержит все значения, необходимые частому запросу для фильтрации и результата, поэтому PostgreSQL потенциально может выполнить index-only scan без чтения heap. Типичный B-tree: ключ по фильтру/сортировке, а поля результата добавляются как INCLUDE payload. INCLUDE-столбцы не входят в порядок/сравнение ключа и не меняют уникальность, зато позволяют не хранить их как дополнительные ключи.

Наличие всех колонок в индексе — необходимое, но недостаточное условие выигрыша. Для MVCC сервер должен проверить видимость tuple; если heap-страница недавно менялась и visibility map не помечает её all-visible, он обратится к heap. Поэтому покрывающий индекс лучше работает на редко изменяемых страницах. Широкие payload-колонки раздувают индекс, ухудшают cache locality и увеличивают стоимость записи; добавлять их нужно только под измеренный горячий запрос. [Index-only scans и covering indexes](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

### Selectivity.
<!-- question-id: 31-databases-sql-postgresql-q06 -->

#### Ответ

Селективность predicate — доля строк, которую он оставляет. Если status = archived совпадает с 2% таблицы, это высокоселективный фильтр в смысле отбора малого набора; если is_active = true совпадает с 99%, фильтр низкоселективен. Высокая селективность часто делает index scan выгодным, но не гарантирует его: случайные heap fetch по большей части страниц могут стоить дороже sequential scan.

Planner оценивает селективность по статистике ANALYZE: most-common values, histogram и другим сведениям; extended statistics помогают для зависимых колонок. При изменении распределения оценки могут устареть. Сравните estimated и actual rows, buffers и heap fetches, проверьте свежесть статистики и корреляцию, затем измените запрос/индекс и измерьте снова. В терминологии важно пояснять, что «высокая селективность» здесь означает малую долю совпадающих строк.

### Cardinality.
<!-- question-id: 31-databases-sql-postgresql-q07 -->

#### Ответ

Cardinality неоднозначна по контексту. Для столбца часто имеют в виду количество distinct значений: UUID обычно близок к числу строк, boolean имеет максимум два. Для relation или результата запроса cardinality означает число строк; в плане PostgreSQL поле rows — оценка строк, которую выдаст узел, а не количество уникальных ключей.

Distinct-count влияет на ожидаемое число совпадений, но не показывает skew: один tenant может содержать половину записей при большом числе tenant-ов в целом. Planner использует также most-common values и histogram; для корреляции нескольких полей может понадобиться extended statistics. При разборе плана отдельно сравнивают оценки строк на входе и выходе узлов: ошибка cardinality в раннем узле может привести к неверному выбору последующего join.

### Query planner.
<!-- question-id: 31-databases-sql-postgresql-q08 -->

#### Ответ

Planner PostgreSQL строит альтернативные пути доступа/соединения и оценивает их стоимость: sequential/index/bitmap scans, порядок join, nested loop/hash/merge, сортировки и параллелизм. Стоимость — условная модель CPU/I/O, а не миллисекунды. Planner выбирает минимальную оценку из рассмотренных вариантов по статистике данных и параметрам cost model; при LIMIT учитывается и startup cost — получение первой строки.

Это оценка, а не обещание самого быстрого фактического выполнения. Статистика бывает устаревшей; распределение данных, корреляции и bind values — плохо оцененными; на выбранный план влияют версия сервера и настройки. Сначала проверьте actual-vs-estimated rows и актуальность ANALYZE. Не меняйте глобальные planner knobs и не принуждайте индекс, пока не исключили устаревшую статистику, лишнюю работу приложения и несоответствие индекса форме запроса.

### EXPLAIN.
<!-- question-id: 31-databases-sql-postgresql-q09 -->

#### Ответ

EXPLAIN выводит выбранный PostgreSQL план без исполнения statement по умолчанию. План — дерево: листовые узлы читают таблицы/индексы, родительские объединяют, фильтруют, сортируют или агрегируют результат. Смотрите тип узла, cost=start..total, estimated rows и width. Cost измеряется в произвольных planner units, не в миллисекундах. Читать удобно от нижних узлов к верхним: проверить входные объемы, лишние фильтры, sort и промежуточные строки.

EXPLAIN в JSON-формате полезен для инструментального сравнения. План может зависеть от предикатов, типов параметров, LIMIT, статистики и настроек; тестируйте запрос с репрезентативными значениями и production-like данными. Обычный EXPLAIN не измеряет latency и не доказывает, что альтернативный план быстрее. Для фактической проверки нужен actual execution и метрики приложения. [Руководство PostgreSQL по EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html)

### EXPLAIN ANALYZE.
<!-- question-id: 31-databases-sql-postgresql-q10 -->

#### Ответ

EXPLAIN ANALYZE реально исполняет statement и добавляет фактические строки, время узлов, число циклов (loops) и, с BUFFERS, I/O/cache сведения. Сравните actual rows с оценкой rows: заметный разрыв указывает на stale statistics, skew или корреляцию. Для узла, исполненного несколько раз, учитывайте loops; время родителя включает работу потомков, поэтому нельзя сложить все времена дерева как независимые затраты.

Измерение имеет profiling overhead и показывает один запуск в текущих условиях, а не гарантирует такую же latency при production-конкуренции. Критичный edge case: DML и вызываемые функции действительно выполняются, а их эффекты могут сохраниться. Для transactional DML можно обернуть тест в BEGIN/ROLLBACK, но это не отменяет внешние побочные эффекты (например, вызов сети из функции). Не запускайте дорогой запрос без оценки объема, блокировок и влияния на сервис. [EXPLAIN ANALYZE: исполнение и side effects](https://www.postgresql.org/docs/18/sql-explain.html)
