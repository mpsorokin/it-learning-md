# Declarative UI and reconciliation

## Interview questions

### Зачем вообще нужен React?
<!-- question-id: 08-react-rendering-model-q01 -->
#### Ответ

React даёт модель описания интерфейса как функции от данных, локального состояния и контекста. Вместо вручную менять DOM для каждого перехода, компонент возвращает описание желаемого UI, а React согласует его с предыдущим деревом и выполняет необходимые host-операции. Это упрощает композицию сложных экранов, привязку поведения к состоянию и повторное использование компонентов.

React не устраняет DOM, не гарантирует высокую производительность автоматически и не превращает JavaScript в параллельный код. Команда по-прежнему отвечает за корректную модель состояния, семантический HTML, доступность и управление побочными эффектами. Ключевое преимущество — декларативная граница: описываем результат, а не серию хрупких imperative DOM-команд.

### Что решает declarative UI?
<!-- question-id: 08-react-rendering-model-q02 -->
#### Ответ

Declarative UI позволяет задать, что должно быть показано при текущих входах, а reconciliation/renderer берёт на себя перевод этого описания в изменения DOM или другого host-а. Условие вида «если loading — spinner, если данные есть — список» становится явным следствием состояния; не нужно синхронизировать вручную десятки DOM узлов и помнить, что удалить при каждом сценарии.

Это облегчает reasoning и тестирование чистого отображения, но не означает «React автоматически знает намерение продукта». Нужно корректно хранить источник истины, обрабатывать race/error/loading и задавать устойчивую идентичность children ключами. Побочные эффекты — сеть, подписки, imperative widget — должны жить в соответствующих lifecycle/API, а не быть частью вычисления UI.

### Что такое Virtual DOM?
<!-- question-id: 08-react-rendering-model-q03 -->
#### Ответ

Virtual DOM — неформальное название для в памяти описанного UI-дерева, с которым сравнивается предыдущее описание, чтобы получить host-изменения. В React точнее говорить о React elements и internal Fiber tree: element — легковесный immutable description, а Fiber содержит данные для работы reconciler-а и renderer-а. React не выполняет полный универсальный deep diff DOM-деревьев при каждом событии.

Сравнение помогает определить, что сохранить, пересоздать и обновить. Стоимость также зависит от самого render-кода, числа компонентов, ключей, DOM layout/paint, эффектов и данных — «Virtual DOM быстрее реального DOM» слишком упрощённое утверждение. React полезен благодаря декларативной модели и эффективному обновлению для типичного UI, а не потому, что любое сравнение бесплатно.

### Что такое React element?
<!-- question-id: 08-react-rendering-model-q04 -->
#### Ответ

React element — immutable описание типа будущего узла, его props и служебных данных. Его создаёт JSX/`createElement`; само создание не запускает component и не создаёт DOM. `key` остаётся специальной метаинформацией React и не приходит в props. `ref` тоже служит React для связи с узлом, но начиная с React 19 его можно принимать как prop в function component ([документация React 19](https://react.dev/blog/2024/12/05/react-19)); в class component ref по-прежнему адресует instance, а не передаётся как prop. До React 19 function components обычно получали ref через `forwardRef`.

Element можно создавать снова при каждом render; одинаковый внешний вид элемента не означает одинаковую identity как JS-объекта, и reconciler сравнивает смысловую структуру — type, key, position и props — а не требует ссылочного совпадения. React element описывает лишь желаемую структуру; component функция должна быть вызвана React-ом, чтобы получить её результат, после чего host renderer создаёт/обновляет DOM.

### Element vs component vs instance.
<!-- question-id: 08-react-rendering-model-q05 -->
#### Ответ

Element — значение-описание узла (type + props + key). Component — функция или класс, который React вызывает/обрабатывает для получения элементов. Instance — конкретное сохраняемое React состояние/положение компонента между render-ами; для function component это не JS-объект, который приложение обычно получает напрямую. В legacy class component есть экземпляр класса, но и он не тождественен React element или DOM node.

Например, JSX `<Card title="x" />` создаёт React element с type `Card` и props. React вызывает `Card` и получает element host node (скажем, `<article>`); затем renderer создаёт или обновляет DOM. Несколько одинаковых элементов одного типа могут соответствовать разным состояниям из-за разных позиций/keys.

Эти термины важны для понимания `key`, remount и state preservation: нельзя хранить state «в JSX element», а компонентная identity определяется reconciliation-контекстом.

### Что происходит после setState?
<!-- question-id: 08-react-rendering-model-q06 -->
#### Ответ

`setState`/setter сообщает React, что у компонента есть новое состояние или queued updater и требуется выполнить работу для обновления UI. Значение не меняется внутри уже исполняющегося обработчика: его переменные и closures относятся к snapshot текущего render-а. React планирует render, рассчитывает следующее состояние, снова вызывает затронутую часть дерева, reconciles результаты и при необходимости commit-ит host-изменения.

Обновления могут объединяться и иметь разные приоритеты; render в современном React может быть повторён или отброшен, поэтому render logic обязана быть pure. Setter с тем же значением по `Object.is` обычно позволяет React пропустить работу для потомков, хотя сам компонент в некоторых случаях может быть вызван. Обновление state не означает, что DOM непременно изменится или что render состоится немедленно.

### Что такое reconciliation?
<!-- question-id: 08-react-rendering-model-q07 -->
#### Ответ

Reconciliation — процесс сопоставления нового React element tree с предыдущим, чтобы решить, какие поддеревья и состояния можно сохранить, а какие host-изменения нужны. React использует тип элемента, его положение и `key`; при совпадающей identity обычно сохраняет компонент и его state, при изменении типа или key создаёт новый компонент и размонтирует старый.

На уровне host renderer-а reconciliation выявляет вставку, удаление, перемещение и изменение свойств DOM nodes. Он не является поиском любой математически оптимальной последовательности DOM-операций и не анализирует бизнес-смысл объектов. Стабильные keys дают информацию об идентичности children при перестановках.

Render/reconciliation могут выполняться без видимого DOM mutation; commit — отдельный этап применения подготовленного результата. Понимать это разделение полезно при профилировании: дорогой component calculation и дорогой layout/paint — разные bottlenecks.

### Что сравнивает React?
<!-- question-id: 08-react-rendering-model-q08 -->
#### Ответ

React сопоставляет тип узла (host tag или тип компонента), его позицию среди siblings и `key`. У одного типа компонента с тем же key React может сохранить состояние и передать новые props; другой тип или key означает другую identity. Для детей массива keys позволяют сопоставлять элементы независимо от простого текущего индекса и понимать вставки/удаления/перестановки.

Затем компонент вызывается для вычисления новых children (если не сработал допустимый bailout). React не делает автоматически deep comparison всех props любого компонента. `memo` и пользовательский comparator — отдельная оптимизация для пропуска вызова, а DOM renderer сравнивает host props/children и делает только нужные mutations.

Нельзя трактовать reconciliation как универсальный diff любых JS-объектов. Пропущенный/нестабильный key ломает identity; новый объект в prop может быть равным по содержанию, но иметь новую ссылку для `memo` shallow comparison.

### Почему reconciliation O(n), а не O(n³)?
<!-- question-id: 08-react-rendering-model-q09 -->
#### Ответ

Наивный tree-edit distance для произвольных деревьев потребовал бы сравнивать очень много возможных соответствий; классическое описание даёт кубическую сложность в числе узлов. React использует эвристики под UI-моделью: разные типы считаются разными поддеревьями, а siblings сопоставляются локально по ключам и типам. Поэтому типичный проход близок к O(n) по числу элементов, а не к поиску оптимального глобального соответствия.

Эта эффективность основана на допущениях, а не на доказательстве, что всякая операция в любом JSX всегда O(n). Большой список всё равно требует работы пропорционально числу обрабатываемых элементов; неудачные keys, дорогой render и DOM layout могут сделать экран медленным. Virtualization сокращает число одновременно смонтированных узлов, а профилировщик помогает найти реальный bottleneck.

Динамическому списку нужны устойчивые keys из данных: тогда React может линейно сопоставить элементы после reorder без глубокого поиска по содержимому.
