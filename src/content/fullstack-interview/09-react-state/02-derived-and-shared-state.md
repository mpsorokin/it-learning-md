# Derived and shared state

## Interview questions

### Derived state.
<!-- question-id: 09-react-state-q09 -->
#### Ответ

Derived state — значение, которое можно вычислить из уже имеющихся props, state или стабильных данных, например `visibleItems = items.filter(...)`, `total = cart.reduce(...)` или `isValid = errors.length === 0`. Если для следующего render-а оно всегда однозначно выводится из источника, это производное представление, а не ещё один источник истины.

Его обычно считают непосредственно при render-е; expensive pure calculation можно мемоизировать через `useMemo` только после профилирования. Данные с сервера, пользовательский draft и вычисленный форматированный label — разные сущности, даже если содержимое временно совпадает.

Derived state оправдан, когда намеренно фиксируется snapshot на событие/переход (например, черновик формы), либо когда система кэширует результат с чёткой инвалидацией. Тогда явно задайте момент пересчёта и владельца данных, чтобы не получить stale copy.

### Почему derived state часто не нужно хранить?
<!-- question-id: 09-react-state-q10 -->
#### Ответ

Хранение одновременно источника и его производного значения создаёт две версии правды. При обновлении одной легко забыть синхронизировать другую; Effect, копирующий props в state, может отобразить кадр со старым значением, породить лишний render и породить циклические updates. Для простого derived output надёжнее вычислить значение из текущих входов в каждом render-е.

Если вычисление дешёвое, прямой расчёт короче и всегда актуален. Если дорогое, сначала измерьте, затем `useMemo` с корректным dependency list — это оптимизация, React может сбросить кеш; логика не должна зависеть от того, что memo сохранится. Для нескольких полей с инвариантами используйте reducer, чтобы хранить минимальное состояние и обновлять его согласованно.

Отдельный state нужен, когда пользователь редактирует копию данных с отдельным lifecycle, например форму до Save. Это не «дублирование ради render-а», а намеренный draft со своей точкой commit/reset.

### Lifting state up.
<!-- question-id: 09-react-state-q11 -->
#### Ответ

Lifting state up — перенос общего состояния к ближайшему общему предку компонентов, которые должны его читать/менять. Родитель становится single source of truth и передаёт значения вниз через props, а callbacks/actions — вверх. Так siblings не ведут несинхронные локальные копии.

Например, два поля аккордеона, которые должны быть открыты не одновременно, управляются общим `activeId` у Accordion, а не отдельными booleans у каждого Panel. API-компоненты могут оставаться controlled: parent решает значение, child сообщает о пользовательском намерении.

Недостатки — prop drilling и потенциально широкий rerender родительского поддерева. Разбивайте компоненты, локализуйте state до нужной группы, используйте Context для редких широких зависимостей или внешний store с селекторами для частых крупных графов. Поднимать каждый state глобально не нужно.

### State colocation.
<!-- question-id: 09-react-state-q12 -->
#### Ответ

State colocation — хранение state как можно ближе к компонентам, которые реально его используют. Локальное состояние поля ввода не нужно поднимать на уровень приложения, если от него не зависят другие ветки. Это уменьшает пропагацию props/context, область rerender-ов, связанность, а также упрощает reset по lifetime компонента.

Разделение стейта по владельцам делает потоки данных понятнее: модалка контролирует draft, страница управляет выбранной сущностью, общий фильтр поднимается к двум зависимым спискам. Если несколько братьев должны синхронно реагировать на одно состояние, его поднимают ровно до общего владельца; если многие несвязанные части подписываются на высокочастотные обновления, оцените store/selectors.

Слишком низкая колокация тоже вредна, если состояние должно пережить unmount, маршрут или смену key. Сначала определите lifecycle и authoritative owner, затем располагайте state по этому контракту.

### Controlled vs uncontrolled.
<!-- question-id: 09-react-state-q13 -->
#### Ответ

В controlled-компоненте источник истины находится снаружи: parent передаёт `value`/`checked` и обработчик изменения, а child отображает переданное значение. Изменение DOM само по себе не поменяет UI, пока владелец не передаст новый prop. Это удобно для валидации, синхронизации полей и общего контроля, но каждое изменение должно обрабатываться без задержек, иначе поле будет возвращаться к старому значению.

В uncontrolled-компоненте DOM хранит текущее значение; React может задать стартовое `defaultValue`/`defaultChecked`, а ref/FormData читаются при submit. Он проще для небольших/legacy форм, но хуже подходит для live validation и cross-field logic. После mount изменение `defaultValue` обычно не контролирует текущее содержимое.

Не переключайте один input между controlled и uncontrolled в течение его жизни. `<input type="file">` по соображениям браузерной безопасности остаётся uncontrolled; его files читают через ref. Выбор режима делают для всей формы по требованиям, не по моде.
