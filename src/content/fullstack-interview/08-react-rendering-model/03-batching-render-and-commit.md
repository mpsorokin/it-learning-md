# Batching, render and commit

## Interview questions

### Batching.
<!-- question-id: 08-react-rendering-model-q19 -->
#### Ответ

Batching — обработка нескольких state updates в рамках одной React работы так, чтобы вычислить итоговое состояние и выполнить render/commit совместно, вместо синхронного обновления экрана после каждого setter-а. Это уменьшает лишнюю работу и не позволяет пользователю увидеть промежуточно несогласованную комбинацию полей.

Batching не объединяет сами updater semantics: функциональные updater-ы всё равно применяются по очереди, а прямые значения вычисляются из snapshot текущего render-а. Он также не означает, что все будущие updates приложения попадут в один render. Границы зависят от события, root/API и React version; при необходимости сначала проверьте фактическую платформу и Profiler, а не полагайтесь на «один клик = один вызов компонента».

### Automatic batching.
<!-- question-id: 08-react-rendering-model-q20 -->
#### Ответ

Automatic batching в React 18+ с `createRoot` расширил группировку updates за пределы React event handlers — например, для callbacks Promise, `setTimeout`, native events и других async callbacks ([заметки React 18](https://react.dev/blog/2022/03/29/react-v18)). До этого обычно группировались React event handlers, а внешние callbacks могли вызвать несколько render-ов. Это поведение относится к React DOM root/configuration, а не является ECMAScript-свойством.

Batching прекращается там, где нужно завершить отдельное user interaction безопасной границей; независимые клики не объединяются в один update batch. `flushSync` позволяет в редком imperative integration случае немедленно форсировать commit, но ломает часть оптимизаций и может запустить дополнительную работу, поэтому это escape hatch. Не строить correctness на точном количестве render pass-ов.

### Что такое render phase?
<!-- question-id: 08-react-rendering-model-q21 -->
#### Ответ

Render phase — этап, на котором React вызывает function components или соответствующие render-методы, вычисляет element tree и готовит план reconciliation. На первичном render-е строится всё поддерево; при update React может пройти лишь нужные части и сравнить их с текущим деревом.

Этот этап должен быть pure: одинаковые props/state/context дают эквивалентный UI, без мутации внешних объектов, DOM и сети. Современный renderer может приостановить, повторить или отбросить подготовленный render, например при смене приоритета. Поэтому вызов компонента не равен видимому обновлению. Effects не являются способом синхронно выполнять логику в render phase.

Планирование и конкурентность — возможности React, а не гарантия, что всякий render будет прерываться или идти параллельно. Тяжёлый синхронный код внутри одной функции компонента сам по себе не может быть прерван посередине.

### Что такое commit phase?
<!-- question-id: 08-react-rendering-model-q22 -->
#### Ответ

Commit phase — этап, когда React применяет подготовленный результат к host tree: создаёт, обновляет или удаляет DOM nodes, присваивает refs и запускает соответствующие lifecycle/effect операции. Для одного commit-а DOM mutation выполняются согласованно; браузер не увидит React-компонент наполовину обработанным из-за yield посередине render calculation.

`useLayoutEffect`/class layout lifecycles выполняются после DOM mutations, но до браузерного paint; обычные `useEffect` обычно запускаются после commit и могут быть отложены в зависимости от причины update. Cleanup старых эффектов привязан к заменённым эффектам/unmount. Не делайте commit effects источником синхронных derived values — их обычно следует вычислять во время render-а.

Commit не гарантирует, что браузер физически покрасил кадр в тот же момент; DOM update и paint — разные этапы. Код, который измеряет layout/читает DOM, должен выбрать правильный layout effect и учитывать его блокирующую цену.

### Когда React изменяет DOM?
<!-- question-id: 08-react-rendering-model-q23 -->
#### Ответ

React меняет DOM во время commit phase после того, как получил готовое reconciliation-решение для актуального дерева. Во время render phase он рассчитывает элементное дерево и эффекты, но не должен делать пользовательские DOM mutations. Если новый host output эквивалентен предыдущему, commit может пройти без видимого DOM mutation или быть пропущен.

Перед paint выполняются те commit-related шаги, которым важен синхронный layout, включая `useLayoutEffect`; `useEffect` — отдельный пассивный этап после commit, обычно после paint, но timing имеет нюансы для interaction-triggered updates. `flushSync` может форсировать DOM commit перед выходом из блока, только когда это требуется интеграцией.

Не выполняйте ручное изменение React-owned DOM: следующий commit может его затереть или нарушить reconciliation. Для third-party widget изолируйте DOM subtree и синхронизируйте его на границе effect/ref.

### Что такое Fiber?
<!-- question-id: 08-react-rendering-model-q24 -->
#### Ответ

Fiber — внутренняя архитектура React reconciler-а: единицы работы/узлы внутреннего дерева, содержащие связь с дочерними/соседними Fiber, state, props, эффекты и служебные флаги. React поддерживает текущее дерево и work-in-progress версию, чтобы готовить изменения и затем commit-ить их. Это деталь реализации, а не публичный API и не объект, на который приложения должны опираться.

Fiber позволяет представить render как набор управляемых единиц работы и связывает reconciliation с планированием приоритетов. Для component author главное следствие — render может быть переигран/отброшен, поэтому он должен быть pure. Конкретные поля и алгоритмы меняются между версиями.

Fiber не означает автоматически параллельный JS: в одном браузерном агенте пользовательский JavaScript исполняется последовательно. Он даёт React возможность yield-ить между unit-ами работы и переключать приоритет до commit-а.

### Почему Fiber появился?
<!-- question-id: 08-react-rendering-model-q25 -->
#### Ответ

Старый stack reconciler обходил дерево рекурсивным вызовом и не мог уступить main thread посреди глубокой синхронной работы. Это увеличивало риск длинных блокирующих render-ов и затрудняло реализацию приоритетных обновлений, transitions и согласования Suspense.

Fiber перестроил reconciliation как управляемую работу по частям: React может запланировать, приостановить, продолжить или отбросить работу до её commit-а, обрабатывая более срочные updates. Это позволяет повышать отзывчивость при больших/сложных поддеревьях, если код компонентов чист и работа разбивается на yieldable units.

Торговая сторона — сложнее internal model и тот факт, что render не является одноразовым imperative вызовом. Fiber сам по себе не ускоряет медленный алгоритм в компоненте и не делает CPU-heavy loop прерываемым. Измерять нужно end-to-end interaction latency, а не наличие Fiber как такое.

### Что такое interruptible rendering?
<!-- question-id: 08-react-rendering-model-q26 -->
#### Ответ

Interruptible rendering — возможность React при конкурентных возможностях приостановить незавершённый render между единицами React work, уступить main thread срочной работе и позже продолжить либо отбросить старую версию, если появилась более актуальная. Пользователь не должен видеть частично готовое дерево: React commit-ит согласованный результат.

Это не означает, что JavaScript-функция компонента прерывается в середине произвольной инструкции. Один длинный синхронный обработчик или дорогое вычисление внутри одного компонента по-прежнему блокирует поток до возврата; такую работу нужно оптимизировать, chunk-ить или переносить в Worker. Concurrent features позволяют React управлять приоритетом; обычный sync update не всегда прерываем.

В компонент нельзя помещать side effect вроде мутации глобального кеша во время render: попытка может быть повторена или discarded. Commit и эффекты — граница для видимых/внешних действий.
