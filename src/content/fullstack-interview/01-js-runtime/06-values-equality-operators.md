# Значения, equality и operators

## Interview questions

### Почему [] === [] → false?
<!-- question-id: fullstack-interview-01-js-runtime-032 -->

#### Ответ

Массивы — объекты, а `===` для двух объектов сравнивает identity: ссылаются ли оба операнда на один и тот же объект. Литералы `[]` создают два разных массива, поэтому выражение ложно, хотя оба массива пусты. Если `const a = []; const b = a`, то `a === b` истинно.

Для структурного сравнения нужен явно выбранный алгоритм: shallow comparison, deep equality библиотекой или сравнение доменного ключа. JSON stringify как универсальное решение некорректен: теряет типы/undefined, чувствителен к порядку некоторых свойств и падает на циклах. В React identity важна для сравнения зависимостей и memoization, поэтому иммутабельные обновления создают новые ссылки только для изменённых частей структуры.

### Primitive vs reference values.
<!-- question-id: fullstack-interview-01-js-runtime-033 -->

#### Ответ

В JavaScript примитивные значения — `undefined`, `null`, boolean, number (включая `NaN` и ±Infinity), bigint и string; `Symbol` — тоже primitive. Остальные значения — объекты: обычные объекты, массивы, функции, даты, Map и т. п. Примитив передаётся как значение; объектная переменная хранит ссылку на объект, и копирование такой переменной создаёт ещё одну ссылку на тот же объект.

Фраза «reference type» — учебное упрощение: семантика ECMAScript говорит об object values и операциях над ними; язык не обещает конкретный pointer layout. При передаче аргумента в JavaScript всегда копируется значение: для объекта — значение ссылки. Поэтому функция может мутировать общий объект, но присваивание параметру новой ссылки не заменит переменную вызывающего кода.

Примитивы immutable, объект может быть mutable. `const` запрещает переназначить binding, но не замораживает объект за ним. Для предотвращения побочных эффектов нужны соглашения/immutable API, а не только `const`.

### Почему строки immutable?
<!-- question-id: fullstack-interview-01-js-runtime-034 -->

#### Ответ

String — primitive value и по спецификации неизменяема. Операции вроде `toUpperCase()`, `replace()` или конкатенации создают новую строку, не изменяя исходное значение. Индексирование возвращает строковый фрагмент UTF-16, но это не даёт мутировать символ присваиванием по индексу.

Неизменяемость упрощает передачу и кеширование строк: потребитель не может незаметно поменять разделяемое значение. Реализация движка может интернировать строки, применять ropes или оптимизировать конкатенацию, но это не часть контракта. Нужно отдельно помнить, что визуальный символ может состоять из нескольких code units/code points (суррогатные пары и combining marks); операции по `length` и индексам не всегда работают с grapheme cluster.

Для пользовательского текста, обрезки и курсора используйте `Intl.Segmenter` при необходимости языково корректной сегментации; при сравнении/нормализации учитывайте Unicode normalization и локаль. Не превращайте строки в mutable массивы без осознанной модели кодовых точек.

### Как работает equality?
<!-- question-id: fullstack-interview-01-js-runtime-035 -->

#### Ответ

`===` применяет Strict Equality: примитивы сравниваются по правилам типа (для Number `NaN !== NaN`, `+0 === -0`), объекты — по identity. Межтиповые значения всегда не равны. `Object.is` отличается поведением для `NaN` и signed zero. Это хороший default для предсказуемой логики.

`==` применяет Abstract Equality Conversion: допускает ограниченный набор coercion, например `null == undefined`, строка/число преобразуются по правилам языка, boolean сначала становится числом, а сравнение объекта с примитивом может вызвать `ToPrimitive`/пользовательский код. Это может иметь побочные эффекты. Исключение — некоторые специальные правила для `document.all` в браузере.

Реляционные операторы `<`, `>`, `<=`, `>=` сначала приводят операнды к primitive и затем выбирают строковое лексикографическое или числовое сравнение; `NaN` делает упорядоченное сравнение ложным. Для production предпочтительны строгие сравнения и явная нормализация входа, особенно на границе JSON/API.

### Object.is vs ===.
<!-- question-id: fullstack-interview-01-js-runtime-036 -->

#### Ответ

`Object.is(a, b)` сравнивает значения с SameValue semantics: `NaN` считается равным самому себе, а `+0` и `-0` различаются. Оператор `===` делает обратное в этих двух крайних случаях: `NaN === NaN` ложно, `+0 === -0` истинно. Для всех обычных значений результаты совпадают; объекты и там, и там сравниваются по identity.

Это полезно в узких алгоритмах с числовыми краевыми значениями и при сравнении значений state: React state update bailouts используют алгоритм, эквивалентный `Object.is` для таких сравнений. В приложении нельзя объявлять один вариант универсально правильным: для большинства бизнес-условий используйте `===`, для обнаружения `NaN` — `Number.isNaN`, а `Object.is` — когда важна именно его семантика.

Не путать с SameValueZero, используемым, например, `Map`/`Set`: там `NaN` равен `NaN`, но `+0` и `-0` считаются одним значением.

### null == undefined, но null !== undefined — почему?
<!-- question-id: fullstack-interview-01-js-runtime-037 -->

#### Ответ

Abstract Equality Algorithm содержит отдельное правило: `null == undefined` истинно, и ни `null`, ни `undefined` не равны никакому другому значению по loose equality. Это намеренное удобство для проверки «отсутствующего значения». Поэтому `x == null` проверяет одновременно `null` и `undefined` (за известным web legacy исключением `document.all`).

Strict Equality не выполняет такое объединение типов: `null !== undefined`, потому что значения имеют разные типы. Они также по-разному означают отсутствие: `null` обычно задаётся явно как «пустое значение», `undefined` часто означает отсутствие присвоенного значения/аргумента, хотя соглашения зависят от API.

На границе данных полезно не использовать loose equality без явного намерения: для проверок различайте отсутствующее поле, `null` и валидное ложное значение (`0`, `false`, `''`). `x == null` допустим, если по требованиям эти два состояния эквивалентны и команда знает об исключении.

### Как работает optional chaining?
<!-- question-id: fullstack-interview-01-js-runtime-038 -->

#### Ответ

Optional chaining (`?.`) выполняет доступ/вызов только если значение слева равно `null` или `undefined`; в этом случае результат цепочки — `undefined`. Поддерживаются формы `obj?.prop`, `obj?.[expr]` и `fn?.(args)`. Если значение не nullish, доступ продолжается обычно: отсутствующее свойство даёт `undefined`, а попытка вызвать не-функцию всё равно бросает `TypeError`.

Короткое замыкание действует на непрерывную optional chain. После группировки `(obj?.a).b` второе обращение уже обычное и может упасть. Правая часть `obj?.[sideEffect()]` не вычисляется, если `obj` nullish. Optional chaining не превращает все исключения в `undefined` и не защищает от невалидного типа, прокси или getter, который бросил ошибку.

Для обязательного значения лучше валидировать/выбрасывать понятную ошибку, а не молча протаскивать `undefined`. Частое чрезмерное применение `?.` скрывает нарушенный контракт; используйте его, когда вложенная структура действительно необязательна.

### Как работает nullish coalescing?
<!-- question-id: fullstack-interview-01-js-runtime-039 -->

#### Ответ

Nullish coalescing (`a ?? b`) возвращает `b`, только если `a` равен `null` или `undefined`; в остальных случаях возвращает `a`. В отличие от `||`, он сохраняет `0`, `false`, пустую строку и `NaN`, что удобно для дефолтов конфигурации и пользовательского ввода.

Оператор вычисляет левую часть один раз, затем при необходимости правую, поэтому правый default может быть ленивым/побочным. Его нельзя без скобок смешивать с `&&` или `||` — грамматика намеренно выдаёт SyntaxError, чтобы исключить неоднозначное чтение. Можно комбинировать с optional chaining: `user.settings?.theme ?? 'system'`.

Дефолт следует задавать по смыслу: если `null` — намеренный сигнал «очистить», `??` может вернуть fallback вопреки контракту; если принимаются только конкретные значения, нужна валидация. `??` не проверяет пустой массив, пустую строку или некорректный объект.

### || vs ??.
<!-- question-id: fullstack-interview-01-js-runtime-040 -->

#### Ответ

`||` возвращает правый операнд, когда левый falsy: `false`, `0`, `-0`, `0n`, `NaN`, `''`, `null`, `undefined` или `document.all` в браузере. `??` возвращает правый только для `null`/`undefined`. Оба оператора short-circuit-ят, возвращают сами операнды, а не boolean.

Поэтому `port = input || defaultPort` заменит допустимый `0`, тогда как `input ?? defaultPort` сохранит его. Для boolean feature flag часто используют `||` только если намеренно считают `false` поводом применить default; чаще значение `false` является осознанным выбором. Для строковых настроек решите, является ли пустая строка значимой.

Оба оператора вычисляют правую сторону только по необходимости; выражения с логическими операторами не смешиваются без скобок с `??`. Выбор оператора документирует бизнес-семантику отсутствия, а не просто привычку к синтаксису.

### Что делают logical assignment operators &&=, ||=, ??=?
<!-- question-id: fullstack-interview-01-js-runtime-041 -->

#### Ответ

`&&=`, `||=` и `??=` — short-circuit assignment: условно присваивают в тот же target, сохраняя исходное значение, если присваивание не нужно. `x &&= y` обновляет, когда текущее `x` truthy; `x ||= y` — когда оно falsy; `x ??= y` — только при `null`/`undefined`. Это не простые текстовые макросы: reference на target вычисляется один раз, что важно при getter/setter и вычисляемом индексе.

Например, `config.value ??= createDefault()` не вызывает фабрику, если значение уже задано, включая `0` и `false`. `cache[key] ||= value` опасно, если легальный кешированный результат falsy. Присваивание property в strict mode может выбросить ошибку, если свойство не writable; getter/setter могут вызвать пользовательский код.

Выбирайте оператор по смыслу default-а и помните ограничения грамматики на смешивание `??` с `&&`/`||`; ставьте скобки. Для деклараций `const x ??= ...` присваивание недопустимо — оператор применяется только к assignable target.
