# Копирование и structuredClone

## Interview questions

### Shallow copy vs deep copy.
<!-- question-id: fullstack-interview-01-js-runtime-042 -->

#### Ответ

Shallow copy создаёт новый верхнеуровневый контейнер, но вложенные объекты оставляет теми же ссылками. Например, spread массива/объекта или `Object.assign` копирует перечисляемые собственные свойства на один уровень. Изменение вложенного объекта через копию видно исходнику; замена верхнеуровневого свойства — нет.

Deep copy рекурсивно копирует вложенный граф. Простая самописная рекурсия часто ломается на циклах, повторных ссылках, специальных объектах и пользовательских классах. Даже полноценная deep copy не всегда желательна: она может быть дорогой по CPU/памяти и терять идентичность объектов, на которой основаны кеши или UI diffing. В иммутабельных структурах обычно копируют только путь к изменяемому узлу (structural sharing), а не всё дерево.

Нужно определить контракт: какие типы поддерживаются, сохраняются ли циклы и aliasing, как обрабатываются прототипы, дескрипторы и функции. Для переносимого клона поддерживаемого набора встроенных типов чаще подходит `structuredClone`; для доменной модели — специализированное отображение/копирование.

### Что умеет и не умеет structuredClone()?
<!-- question-id: fullstack-interview-01-js-runtime-043 -->

#### Ответ

`structuredClone(value)` клонирует значения по Structured Clone algorithm, сохраняя циклы и повторяющиеся ссылки внутри клона. Поддерживаются распространённые структуры данных, включая массивы, plain objects, Date, Map, Set, ArrayBuffer/typed arrays и циклические графы. С опцией `transfer` transferable-объект (например ArrayBuffer) перемещается, а исходный становится detached, что позволяет избежать копирования буфера.

Алгоритм не является универсальным клонированием любого JS объекта: functions, DOM nodes, WeakMap/WeakSet и некоторые host/exotic значения не клонируются и приводят к `DataCloneError`. Пользовательский prototype, descriptors, getters/setters и приватное состояние класса не переносятся как полноценная инстанция класса; результат следует валидировать под ожидаемую структуру. Поддержка метода зависит от целевого runtime; проверьте browser/Node version или запланируйте fallback.

Clone может быть дорогим для больших деревьев, не выполняет schema validation и не санитизирует недоверенные данные. Transfer полезен только когда владелец исходного буфера действительно может отказаться от него.

### Когда structuredClone лучше JSON serialization?
<!-- question-id: fullstack-interview-01-js-runtime-044 -->

#### Ответ

`structuredClone` предпочтителен JSON round-trip, когда данные содержат циклические ссылки, `undefined`, `BigInt`, `Date`, `Map`, `Set`, typed arrays или значения, которые JSON теряет/не сериализует. JSON сериализация обычно превращает Date в строку, пропускает `undefined`-свойства, ломается на BigInt и циклах, теряет Map/Set и может вызвать пользовательские `toJSON`; преобразование не сохраняет aliasing.

JSON может быть уместен как сериализация обменного формата для уже валидированного JSON-compatible DTO, но это не deep clone-контракт. `structuredClone` сохраняет поддерживаемые встроенные типы и graph relationships, однако не копирует произвольные функции/классы и не является безопасной сериализацией для хранения/пересылки на сервер. Для persisted данных нужен versioned schema, например JSON плюс явная validation и преобразование типов.

Выбор определяется нужной семантикой и поддержкой runtime. На больших объектах замерьте latency и память; зачастую правильнее избегать клонирования всего состояния и использовать immutable updates.
