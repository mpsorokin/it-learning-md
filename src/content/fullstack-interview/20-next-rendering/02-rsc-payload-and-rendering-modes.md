# RSC payload and rendering modes

## Interview questions

### Что такое RSC payload?
<!-- question-id: 20-next-rendering-q08 -->
#### Ответ
RSC Payload — транспортное представление React Server Component tree, а не просто HTML. В нём находятся отрендеренные результаты серверных компонентов, placeholders и ссылки на JS Client Components, а также props, переданные через границу. React использует payload, чтобы согласовать серверное и клиентское деревья при первом отображении и при навигации. Payload не раскрывает исходный код Server Component, но раскрывает выведенные им значения. На начальной загрузке его обычно сочетают с HTML; при клиентском переходе сервер может вернуть RSC-обновление без полной HTML-страницы. Детали и назначение — в [документации Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components).

### Что уходит клиенту?
<!-- question-id: 20-next-rendering-q09 -->
#### Ответ
Браузер получает HTML для немедленного отображения, RSC Payload с серверным UI-результатом и клиентскими ссылками/props, а также нужные JS/CSS/статические ресурсы. Код Server Components и серверные переменные окружения в bundle не отправляются, но всё, что компонент вывел в HTML/RSC либо передал в Client Component, считается публичными данными. Не помещайте секреты в props с надеждой, что компонент их скроет; проверяйте Network и View Source в production. Server Action ID — не секрет и не замена проверке доступа. При переходе может загружаться RSC-ответ и только недостающий клиентский код.

### Что такое SSR в современном Next?
<!-- question-id: 20-next-rendering-q10 -->
#### Ответ
SSR — генерация HTML на сервере для запроса или при предварительном рендеринге. В современном App Router серверный React строит RSC-представление, а Next/React использует его вместе с Client Components для HTML начальной загрузки; результат может быть статически сохранён либо создан динамически в зависимости от данных и конфигурации. HTML позволяет показать содержимое до загрузки интерактивного JS, после чего Client Components гидратируются. SSR не означает автоматически «каждый запрос заново» и не определяет политику кэша. Потоковый SSR может отдать готовые части раньше остальных.

### RSC vs SSR.
<!-- question-id: 20-next-rendering-q11 -->
#### Ответ
Это разные оси. RSC описывает тип компонентов, место их исполнения и сериализуемый протокол между серверным и клиентским деревьями. SSR описывает получение HTML на сервере. На первом запросе Next может использовать оба механизма: Server Components формируют RSC Payload, а React выводит HTML-предпросмотр как для серверных, так и для Client Components. При последующей навигации клиент обычно получает RSC Payload и обновляет сегменты без полной HTML-перезагрузки. Поэтому Client Component может быть SSR на первой загрузке, а Server Component не равен «обычному SSR-компоненту». См. [официальное описание потока](https://nextjs.org/docs/app/getting-started/server-and-client-components).

### CSR vs SSR vs SSG vs ISR.
<!-- question-id: 20-next-rendering-q12 -->
#### Ответ
CSR строит основное содержимое браузером после загрузки JS; SSR генерирует HTML на сервере для запроса; SSG заранее создаёт HTML/RSC результат во время build; ISR позволяет повторно валидировать ранее созданный статический результат по времени или событию. Это не взаимоисключающие ярлыки: одна страница может содержать серверный статический shell, динамический потоковый участок и гидратируемые Client Components. В Next.js 16 предположим App Router; Cache Components — отдельный opt-in режим через cacheComponents, который позволяет сочетать prerendered shell и динамические Suspense-границы. Старую модель fetch/route caching нельзя автоматически переносить на этот режим: [Cache Components](https://nextjs.org/docs/app/guides/partial-prerendering).
