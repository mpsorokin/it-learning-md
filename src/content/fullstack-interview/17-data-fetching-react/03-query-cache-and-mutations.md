# Query cache and mutations

## Interview questions

### staleTime.
<!-- question-id: 17-data-fetching-react-q11 -->
#### Ответ

В TanStack Query v5 staleTime — интервал, в течение которого данные считаются fresh для данного observer. Значение по умолчанию 0: загруженная запись может быть сразу показана из cache, но stale-trigger refetch разрешён при новом mount, focus или reconnect. Пока данные fresh, эти автоматические триггеры обычно не запускают запрос; явный refetch и ручная invalidation остаются отдельными решениями. staleTime не удаляет данные, не продлевает серверную актуальность и не ограничивает наличие записи в памяти — за неактивную запись отвечает gcTime. Выбирайте его по SLA на допустимую устарелость, частоте изменений и цене запроса; права доступа или конфликт записи нельзя защитить только длительным staleTime. В v5 Infinity позволяет оставить запись fresh, пока её явно не инвалидируют, а static предназначен для данных, которые в течение runtime никогда не должны стать stale даже через invalidation; последний вариант стоит применять редко. [См. раздел defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

### gcTime.
<!-- question-id: 17-data-fetching-react-q12 -->
#### Ответ

gcTime в v5 — срок хранения неактивной query в cache до garbage collection; в предыдущих версиях тот же параметр назывался cacheTime. Пока у query есть активный observer, таймер GC не удаляет её, даже если staleTime уже прошёл. Поэтому staleTime отвечает на «когда можно обновлять», а gcTime — «как долго держать неиспользуемую копию». Короткий срок экономит память, но при возврате пользователя чаще показывает пустое initial state и выполняет сеть; длинный поддерживает возврат к ранее открытому экрану, но увеличивает память. Значение по умолчанию для браузера — пять минут; SSR обычно использует бесконечное время GC, поэтому request-scoped QueryClient важно освобождать после ответа, а не хранить его как общий серверный singleton. При logout удаляйте пользовательские записи или меняйте tenant/user сегмент cache, чтобы прежние данные не всплыли в новой сессии.

### invalidation.
<!-- question-id: 17-data-fetching-react-q13 -->
#### Ответ

Invalidation помечает подходящие query как stale и, по умолчанию, запускает refetch активных observers; она не удаляет запись и не вычисляет правильное новое значение. TanStack Query поддерживает prefix matching: ключ-фабрика позволяет после создания/обновления todo инвалидировать затронутые списки, счётчики и детали, не трогая весь cache. Для точного resource используйте более узкий queryKey/exact filter. Если mutation вернула полную нормализованную сущность, её detail cache можно сразу заменить через setQueryData, а производные списки инвалидировать, чтобы сервер пересчитал сортировку, фильтр и права. Возвращайте Promise invalidateQueries из mutation callback, если статус mutation должен оставаться pending до окончания reconciliation. Не инвалидируйте всё после каждого поля: это скрывает неясную модель зависимостей и создаёт сетевую нагрузку. При необходимости работать офлайн или сохранять оптимистическую версию invalidation может запускаться позже при reconnect.

### optimistic updates.
<!-- question-id: 17-data-fetching-react-q14 -->
#### Ответ

Optimistic update показывает ожидаемый эффект до подтверждения backend и уменьшает perceived latency, но создаёт временную конкурирующую клиентскую версию. Для одного места на экране часто проще показать mutation variables как optimistic overlay, не трогая общий cache. Если ту же сущность сразу должны видеть разные consumers, обновляют cache в onMutate: отменяют refetch, сохраняют snapshot, записывают ожидающее значение, при ошибке откатывают snapshot, а после результата подтверждают ответом сервера и/или инвалидируют связанные query. Важно отменить in-flight refetch, иначе он может затереть оптимистичную запись. Snapshot rollback небезопасен при двух конкурентных mutation одного ресурса: откат первой способен стереть подтверждённое изменение второй. Для таких случаев сериализуйте команды per entity, храните операции с ID и переигрывайте оставшиеся поверх подтверждённой версии либо применяйте server revision/ETag с обработкой 409/412. Optimistic UI не должен изображать успех необратимого платежа/удаления без ясного статуса и восстановления.
