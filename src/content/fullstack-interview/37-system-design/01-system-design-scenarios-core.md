# System Design Scenarios: Core Products

## Interview questions

### URL shortener
<!-- question-id: 37-system-design-task01 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Сервис принимает публичные URL, быстро перенаправляет по короткому коду, поддерживает срок жизни и владельца ссылки; чтений существенно больше, чем создания. До capacity planning уточняю пиковые read/write QPS, географию, срок хранения, custom aliases и требования к аналитике. Для примера фиксирую целевой SLO redirect p95 ≤ 100 ms в регионе приложения; это исходное допущение, которое проверяется нагрузочным тестом.

- **API и данные.** `POST /links` возвращает код и полный URL; `GET /{code}` перенаправляет; отдельный endpoint читает/удаляет ссылки владельца. В транзакционной БД храню `code`, целевой URL, owner, `createdAt`, expiry, статус и версию. Уникальный индекс на code обязателен; код генерирую криптографически случайным base62 и повторяю генерацию при конфликте. Предсказуемые последовательные ID не раскрываю.
- **Синхронный путь redirect.** По коду читаю Redis cache, при miss — БД, проверяю expiry/status и возвращаю `302` (или `301` только для неизменяемого контракта). Здесь нет записи в PostgreSQL на каждый GET: это добавило бы БД в latency и отказной путь самого частого запроса. Cache failure деградирует на БД с ограничением stampede; hot keys можно кэшировать ближе к edge. `302` проще для истекающих/изменяемых ссылок и аналитики; `301` браузеры могут кэшировать дольше ожидаемого.
- **Асинхронная аналитика.** Если допустима best-effort статистика, redirect отправляет событие неблокирующим batch/edge-log publisher-ом; при перегрузке буфер bounded и события могут быть отброшены. Это низкая задержка, но без гарантии доставки, поэтому считаю dropped/lag и агрегирую поток отдельно. Если каждый click обязан быть учтён, публикую событие в durable stream и жду подтверждения его приёма перед redirect: это повышает latency и связывает доступность redirect с брокером; доставка обычно at-least-once, consumer дедуплицирует по event ID. PostgreSQL outbox полезен, когда событие атомарно связано с изменением бизнес-состояния; обычный GET такого изменения не делает, поэтому sync outbox transaction на каждый переход не нужен.
- **Сбои и безопасность.** Неизвестный код/истечение дают 404/410 по контракту. Валидирую схемы URL, запрещаю внутренние адреса при любом preview/fetch (SSRF), проверяю ownership, ограничиваю создание и сканирую фишинг; redirect не превращаю в скрытый доверенный переход.
- **Наблюдаемость и trade-offs.** Измеряю p95/p99 redirect, ошибки, cache hit, конфликты кода, истечение ссылок, потери/lag аналитики; trace ID связывает запрос с event ID. Начинаю с одной БД; global replication снижает latency, но усложняет уникальность кодов и консистентное удаление.

### Chat
<!-- question-id: 37-system-design-task02 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Рассматриваю личные и групповые разговоры с историей, доставкой online/offline и reconnect; отдельно уточняю максимальный размер группы, SLA доставки, хранение, вложения и нужно ли сквозное шифрование. Требуется сохранить сообщение до подтверждения приёма, а не гарантировать мгновенную доставку каждому устройству.

- **API и модель.** HTTP: создание разговора, отправка сообщения с `clientMessageId`, чтение истории по cursor; WebSocket — подписка, ack и доставка. Реляционные таблицы `Conversation`, `Membership`, `Message` с монотонной позицией внутри разговора и уникальным ключом `(conversationId, clientMessageId)` дают дедупликацию. Presence и connection registry — эфемерные данные в Redis.
- **Путь и масштаб.** Gateway аутентифицирует пользователя и проверяет membership, сохраняет сообщение и outbox в транзакции, затем брокер доставляет его подключённым gateway-узлам и push-сервису. Partition key по conversation обеспечивает локальный порядок; глобального порядка между всеми чатами не требуется. Историю отдаю курсорной пагинацией, медиа храню отдельно в object storage.
- **Надёжность/согласованность.** Сохраняю до ack; повторная отправка после обрыва идемпотентна. Доставка обычно at-least-once, клиенты дедуплицируют ID; reconnect передаёт последний cursor и запрашивает пропущенную историю. Backpressure ограничивает медленного получателя, недоставленные push-события повторяются с DLQ и возможностью восстановления.
- **Безопасность.** Проверка участника на чтение/запись, rate limits, блокировка/жалоба, шифрование транспорта и хранения, ограничение размера и проверка вложений. Если требуется E2EE, сервер не может индексировать содержимое и иначе реализует abuse handling и multi-device key management — это отдельное архитектурное требование.
- **Наблюдаемость и компромиссы.** Измеряю время от persist до доставки/прочтения, active sockets, reconnect, очередь по partition, дубликаты и ошибки. Не обещаю «exactly once end-to-end»: даю надёжное сохранение, at-least-once доставку и идемпотентную обработку. Sharding по разговору помогает порядку, но очень большие группы требуют отдельной fan-out стратегии.

### Notification system
<!-- question-id: 37-system-design-task03 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Система принимает бизнес-события и доставляет пользователям email, push, SMS или in-app уведомления. Разделяю критичные уведомления и best-effort; выясняю требования к latency, consent, тихим часам, повторной отправке и доказательству доставки.

- **API и модель.** Событие содержит event ID, recipient, тип, tenant и безопасные данные для шаблона. Храню notification/job со статусом, каналом, попытками, provider ID, временем следующего retry и дедупликационным ключом `(eventId, recipient, channel)`. API чтения in-app статуса использует cursor; настройки пользователя хранят каналы, consent и quiet hours.
- **Путь.** Producer пишет событие надёжно (outbox), broker разбивает очереди по каналу/приоритету/tenant, worker проверяет настройки, рендерит версионированный шаблон и вызывает provider. Успех/ошибка и внешний ID сохраняются; отправка в несколько каналов — независимые jobs, чтобы отказ SMS не задерживал email.
- **Надёжность и согласованность.** Доставка внешним провайдером обычно не exactly-once: timeout может скрыть уже принятую отправку. Использую provider idempotency key, где он поддерживается, дедупликацию, bounded retry с backoff/jitter и circuit breaker на квоты/сбои. Постоянно падающие сообщения идут в DLQ с alert и безопасным replay; уведомление может быть `queued`, `sent`, `delivered`, `failed`, статусы не смешиваю.
- **Безопасность.** Учитываю consent/отписку и право на канал, минимизирую PII в очереди и логах, защищаю provider credentials и проверяю подлинность входящих delivery callbacks. Секреты и шаблоны имеют tenant scope; ссылки одноразовые/с ограниченным сроком.
- **Наблюдаемость и trade-offs.** Контролирую lag, age oldest job, delivery latency/rate, provider quota, bounce, retries и DLQ. In-app требует хранения состояния прочтения; email/push чаще best-effort и зависят от внешнего provider. При перегрузке применяю приоритеты и load shedding аналитических/неважных сообщений.

### File upload/storage
<!-- question-id: 37-system-design-task04 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Пользователи загружают крупные файлы, затем скачивают их через приложение/CDN. Уточняю лимиты размера/типы, приватность, retention, региональность, требования к антивирусной проверке и доступности исходного файла.

- **API/данные.** `POST /uploads` авторизует пользователя, проверяет quota и создаёт `uploadId` в статусе `initiated`, возвращая короткоживущий presigned URL или multipart parts. Метаданные (`tenant`, owner, object key, размер, checksum, content type, статус, версия, время) лежат в БД; содержимое — в private object storage с непрозрачным key.
- **Путь и масштаб.** Клиент передаёт файл напрямую в object storage, чтобы API не проксировал гигабайты. `POST /uploads/{id}/complete` проверяет полномочия, размер и checksum, делает операцию идемпотентной и переводит состояние в `quarantined`. Событие запускает malware scan, sniff фактического типа, извлечение метаданных/транскодирование; только успешный файл становится доступен. Чтение — CDN с подписанным URL и политикой cache.
- **Надёжность.** Multipart parts можно повторить; незавершённые upload-ы очищаются lifecycle job-ом. Финализация сверяет storage object и БД, повтор события безопасен. Для долгой проверки API отдаёт статус, а не держит HTTP-соединение. При отказе сканера файл остаётся закрытым, повтор/ручная переобработка наблюдаемы.
- **Безопасность.** Проверяю доступ на initiate, complete и download; ограничиваю время/объём signed URL, блокирую публичный ACL и path traversal, проверяю квоты и содержимое, шифрую transit/at rest, сканирую malware и не доверяю MIME, присланному клиентом. Разделяю ключи tenant и веду аудит скачиваний.
- **Наблюдаемость и компромиссы.** SLI: успешность/время upload и download, ошибки частей, размер/стоимость хранения, время quarantine-to-ready, очередь scan и orphan objects. Прямой upload снижает нагрузку приложения, но требует безопасной выдачи временных прав и reconciliation между объектным хранилищем и БД.

### News feed
<!-- question-id: 37-system-design-task05 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Лента персонализирована по подпискам, чтение частое, посты могут появляться с небольшой задержкой. Уточняю размер графа, допустимую свежесть, алгоритм ранжирования, приватные аккаунты, блокировки и pagination semantics.

- **API/данные.** `POST /posts`, `POST/DELETE /follows`, `GET /feed?cursor=...`. Храню `Post`, `Follow`, visibility/block и при необходимости `FeedEntry(userId, postId, score/time, rankVersion)`. Cursor устойчивый — время/score плюс уникальный ID, чтобы вставки между страницами не дублировали строки.
- **Компоненты и flow.** Post service пишет пост и outbox; fan-out workers получают событие и строят кандидатов. Для обычного автора fan-out-on-write заранее добавляет посты в materialized feeds; для пользователя с огромным числом подписчиков fan-out-on-read избегает дорогостоящего массового push. Гибрид выбирается по распределению followers. Ranker сортирует ограниченный набор кандидатов; API применяет актуальные privacy/block фильтры.
- **Масштаб/cache/согласованность.** Кэшируются горячие страницы и публичные посты с версией/TTL; приватные данные нельзя переиспользовать между пользователями. Очередь сглаживает пики fan-out, consumer идемпотентно дедуплицирует `postId`; feed eventually consistent, авторский пост и follow action могут временно потребовать read-your-writes. Старые записи пересчитываются/удаляются при privacy change.
- **Сбои и безопасность.** Падение ranker-а даёт fallback сортировку по времени; backlog виден по freshness lag. Проверяются ownership, аудит, tenant/privacy, блокировки и rate limit публикаций; пользователь не должен обходить ACL через кэш или cursor. Удаление контента распространяется как tombstone с проверкой на чтении.
- **Наблюдаемость и trade-offs.** Метрики: p95 feed latency, freshness, empty-feed, fanout lag/стоимость, дубликаты, cache hit и ошибки ACL; tracing связывает post event с появлением в ленте. Precompute снижает latency чтения ценой записи/хранения; read-on-demand экономит записи, но дороже для читателей и авторов с большим графом.

### Search autocomplete
<!-- question-id: 37-system-design-task06 -->

Для каждого:

Requirements
→ API
→ data model
→ components
→ request flows
→ scaling
→ cache
→ queues
→ consistency
→ failures
→ security
→ observability
→ trade-offs

#### Ответ

**Предположения и требования.** Это подсказки по каталогу/поисковым запросам при каждом вводе символов; главные цели — низкая latency и полезный top-K, индекс может отставать от источника. Уточняю язык, приватность запросов, доступные поля, минимальную длину и персонализацию.

- **API/данные.** `GET /suggest?q=...&locale=...&limit=...` возвращает ограниченный список с типом и безопасным display value. Источник данных — каталог/словарь; индекс хранит нормализованный префикс, терм, популярность/ранг, locale и visibility. Выбор между search engine prefix query, trie/FST или ограниченной KV-структурой зависит от размера словаря, fuzzy требований и измерений.
- **Путь и масштаб.** Клиент дебаунсит ввод, отменяет устаревший запрос и не посылает каждый промежуточный символ без ограничения. Stateless endpoint нормализует строку, проверяет min length/limit, читает cache по `(normalizedPrefix, locale, segment, version)` и обращается к индексу. Обновления приходят через CDC/event queue с версией документа; backfill перестраивает индекс и затем атомарно переключает alias.
- **Согласованность и отказоустойчивость.** Допустима eventual consistency с видимым лагом; индекс — производная копия и восстанавливается. При отказе выдаю популярные cache results или контролируемую пустую подсказку, не запускаю дорогой полный scan. Кешируем коротко и очищаем/version bump при изменении каталога.
- **Безопасность.** Авторизованные/tenant-specific термы никогда не смешиваются в публичном cache; нормализация не должна снимать ACL. Ограничиваю длину и частоту запросов, не логирую raw персональный текст без необходимости, фильтрую скрытый/удалённый контент.
- **Наблюдаемость и trade-offs.** Отслеживаю p95/p99, cache hit, index lag, zero-result rate, клики по подсказкам, стоимость и ошибки парсинга. Prefix-only даёт предсказуемую latency, fuzzy matching повышает recall ценой вычислений; ранжирование популярностью проще и объяснимее, персонализация требует отдельной оценки качества и privacy controls.
