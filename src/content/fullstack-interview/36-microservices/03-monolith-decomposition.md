# Monolith Decomposition

## Interview questions

### Разбить большой Nest monolith на services — и аргументировать, почему именно эти boundaries.
<!-- question-id: 36-microservices-task01 -->

#### Ответ

Не начинаю с произвольного деления по controller-ам или таблицам. Сначала инвентаризирую use cases, модули, зависимости и общие данные; вместе с командами выявляю бизнес-возможности, точки частых конфликтов релизов, требования к нагрузке, безопасности и отказоустойчивости. Уточняю, кто владеет каждой моделью, какие инварианты требуют атомарности и какие границы уже видны в терминах домена. Сначала усиливаю модульные границы внутри Nest монолита и запрещаю обход модульных API.

Первым кандидатом выбираю bounded context с самостоятельными данными и контрактом, который можно отделить без синхронного вызова десятков модулей. Миграцию делаю постепенно по Strangler: новый endpoint/путь направляется в сервис, старый остаётся fallback на время переключения. Сервис получает владение схемой/записью; другие компоненты работают через API или события, а не общую таблицу. Если миграция требует временной совместимости или backfill, задаю порядок и проверку расхождений; избегаю неопределённого dual-write. Для межсервисных изменений использую outbox и версионированные контракты.

До трафика готовлю CI/CD, health/readiness, секреты, IAM/network policies, лимиты и rollback; добавляю метрики latency/error/traffic, trace context, логи без секретов и alert по пользовательскому SLO. Планирую timeout, retries только для идемпотентных действий, circuit breaker и операционное восстановление. Для workflow с несколькими владельцами явно моделирую pending-состояния и saga/компенсацию. Сравниваю стоимость эксплуатации с выгодой автономного релиза/масштабирования; остальную систему оставляю modular monolith, пока независимая граница не доказана данными.
