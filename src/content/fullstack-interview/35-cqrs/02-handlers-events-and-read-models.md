# Handlers, Events, and Read Models

## Interview questions

### Query handler.
<!-- question-id: 35-cqrs-q06 -->

#### Ответ

Query handler возвращает данные по конкретному запросу и не меняет бизнес-состояние. Он может обращаться к оптимизированной проекции или SQL-запросу и формировать DTO под сценарий чтения, минуя загрузку целого агрегатного графа. Для одного экрана допустим денормализованный read model, если его обновление и восстановление управляемы. Handler проверяет доступ к данным и ограничивает размер/стоимость запроса; read-only по контракту не освобождает от авторизации. Если запрос идёт в асинхронную проекцию, API задаёт ожидания по свежести и при необходимости предлагает read-your-writes механизм.

### Event.
<!-- question-id: 35-cqrs-q07 -->

#### Ответ

Event — факт изменения, который уже произошёл и может быть интересен другим обработчикам; он описывает результат, а не просит выполнить команду. Внутреннее событие может обновить read model или запустить следующий локальный шаг. Межсервисный event — публичный контракт: ему нужны стабильная схема, версия, идентификатор и политика совместимости. EventBus внутри процесса не является надёжным брокером и не гарантирует долговременную доставку. Для публикации после транзакции используют outbox/CDC; потребитель допускает повторы, фиксирует обработанные IDs и наблюдает за задержкой/ошибками.

### Eventual consistency.
<!-- question-id: 35-cqrs-q08 -->

#### Ответ

Eventual consistency означает, что независимые копии или проекции могут временно расходиться, но при успешной обработке событий сходятся к согласованному состоянию. Это не означает «данные когда-нибудь сами исправятся»: нужны надёжная доставка, повторы, идемпотентное применение, обработка схем и метрика лага. UX должен учитывать промежуточное состояние: команда может вернуть результат и версию, а клиент — оптимистично показать изменение, опрашивать статус либо читать из primary до догоняния проекции. Для критичной проверки инварианта (например, доступный остаток) нельзя полагаться на устаревшее read model.

### CQRS vs Event Sourcing.
<!-- question-id: 35-cqrs-q09 -->

#### Ответ

CQRS разделяет модели команд и чтения; Event Sourcing хранит изменения как последовательность неизменяемых событий, из которой восстанавливается состояние. Эти идеи можно применять независимо: CQRS возможен поверх обычных таблиц с CRUD-записью, а event-sourced система может иметь одну модель или построенные проекции. Event Sourcing даёт историю и возможность строить новые представления, но требует версионирования событий, миграции/апкаста, снапшотов, replay, обработки персональных данных и операционного контроля. Его выбирают, когда ценность аудита/истории оправдывает эти обязательства, а не потому, что в системе есть EventBus.

### Projection/read model.
<!-- question-id: 35-cqrs-q10 -->

#### Ответ

Projection — обработчик изменений, который строит удобное для чтения представление, например список заказов с суммой и статусом. Read model — сохранённый результат этой проекции; он может быть денормализованным и даже храниться в другом типе БД. Проекция должна быть детерминированной, идемпотентной и восстанавливаемой из авторитетных изменений. Обработчик отслеживает offset/версию, учитывает дубликаты и порядок на требуемом ключе, делает безопасные upsert и поддерживает перестроение в новую версию схемы. Метрики лага, ошибок и полноты нужны, чтобы обнаружить отставание до обращения пользователя.
