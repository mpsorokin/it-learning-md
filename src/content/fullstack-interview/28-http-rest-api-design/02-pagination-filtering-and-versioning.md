# Pagination, Filtering, and Versioning

## Interview questions

### Pagination.
<!-- question-id: 28-http-rest-api-design-q08 -->

#### Ответ
Коллекционный endpoint не должен по умолчанию возвращать неограниченное число элементов: большой ответ увеличивает задержку, память, стоимость сериализации и нагрузку на БД. Контракт задаёт максимальный размер страницы, разумный default, правила параметров и детерминированный порядок. Клиент получает элементы плюс навигацию или токен продолжения; например, relation `next` может указывать следующую страницу через HTTP `Link` согласно [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288.html). Сам HTTP не стандартизирует query-параметры `limit`, `offset` или `cursor`, поэтому их формат и гарантия стабильности — часть API.

Нужно решить, возвращается ли `totalCount`: точный count на большой или постоянно меняющейся выборке может быть дорогим и быстро устаревать. Если клиенту он не нужен для конкретной задачи, не вычисляйте его на каждой странице. Также определите поведение при превышении лимита и некорректном токене, включение фильтров и сортировки в continuation token, и согласованность между страницами: допускаются ли пропуски/дубликаты при конкурентных изменениях или используется снимок.

Для интерфейсов с бесконечной прокруткой обычно важен быстрый `next` и стабильная выдача, а для админки может быть полезен переход к номеру страницы. Выбирайте модель по пользовательскому сценарию и измерениям, а не только по удобству UI; индекс БД должен соответствовать фильтрам и ключам сортировки.

### Offset vs cursor pagination.
<!-- question-id: 28-http-rest-api-design-q09 -->

#### Ответ
Offset pagination (`limit` + `offset` или `page`) проста для реализации, даёт прямой переход к странице и подходит для небольших, относительно стабильных коллекций. Но БД часто всё равно должна пройти или пропустить предыдущие строки, поэтому глубокие страницы дорожают. Между запросами новые строки могут сдвинуть позиции: пользователь увидит дубликат или пропустит элемент. Точный `totalCount` тоже может быть дорогим.

Cursor pagination продолжает выдачу от значения упорядочивающих полей, например пары `(created_at, id)`. Уникальный tie-breaker обязателен: одна дата сама по себе не задаёт полный порядок. Для следующей страницы запрос использует условие сравнения по этой паре, что обычно эффективнее при подходящем индексе и уменьшает смещение из-за новых записей перед курсором. Это не автоматически snapshot-consistent: удаление, изменение сортируемого поля и транзакционная изоляция влияют на результат; API должен описать ожидаемую согласованность.

Курсор обычно непрозрачен клиенту и кодирует границу, фильтры, сортировку, направление и при необходимости срок/снимок. Сервер валидирует, что он применим к тому же пользователю и запросу; подпись защищает от подмены, но не скрывает данные — для этого нужно шифрование или случайный серверный токен. Cursor удобен для больших лент и последовательного просмотра, offset — для ограниченной выборки с прямым переходом по страницам. Это выбор контракта, а не HTTP-стандарт.

### Filtering.
<!-- question-id: 28-http-rest-api-design-q10 -->

#### Ответ
Фильтр должен быть выражен как ограниченный публичный язык запроса, а не как произвольный фрагмент SQL/ORM. Например, API может разрешать `status`, `category`, диапазон `createdAfter/createdBefore` и `minPrice/maxPrice`; допустимые поля, операторы, формат дат, правила комбинации и поведение при пустом значении фиксируются в документации. Неизвестное поле и неверный тип лучше отклонить явно, чем молча проигнорировать и вернуть результат, который клиент считает отфильтрованным.

Сервер разбирает и нормализует ввод, затем строит параметризованный запрос и проверяет права/область tenant отдельно. Пользовательские значения никогда не конкатенируются в SQL. Allowlist полей также не даёт фильтровать по внутренним или чувствительным атрибутам. Ограничивайте диапазоны, число условий и сложность поиска, иначе даже валидный запрос может превратиться в DoS через дорогую комбинацию фильтров. В ответе сохраняйте понятную семантику: пустой результат — пустая коллекция, а не ошибка; некорректный синтаксис/параметр query — обычно 400. 422 из RFC 9110 относится к понятному, но непроцессируемому содержимому запроса; применяйте его к фильтру только если контракт явно использует это понятие для такого ввода.

Для клиентского удобства нормализованная форма фильтра может сохраняться в ссылке страницы и продолжаться через cursor, но токен должен быть связан с теми же условиями. Индексы выбираются по реальным запросам и селективности; нельзя добавлять все возможные фильтры без оценки их стоимости.

### Sorting.
<!-- question-id: 28-http-rest-api-design-q11 -->

#### Ответ
Сортировка — часть контракта, а не произвольный текст из параметра `sort`. Определите allowlist полей и направления, например `sort=-createdAt,price`, default-порядок и формат записи. Запрос по запрещённому или неиндексируемому полю нужно отклонять либо явно ограничивать; не подставлять имя столбца напрямую в SQL. Сортировка не должна обходить ограничения доступа и не должна давать возможность извлечь скрытые данные через косвенные признаки.

Порядок должен быть полным и детерминированным. Если сортируемые значения совпадают, добавьте стабильный уникальный tie-breaker, обычно ID; иначе соседние страницы могут перемешиваться. Документируйте обработку `null`, регистр/locale, часовой пояс и тип сравнения, если это заметно клиенту. Cursor должен кодировать те же поле, направление и tie-breaker; смена сортировки при использовании старого токена должна завершаться понятной ошибкой.

Для большой коллекции произвольная сортировка может быть слишком дорогой. Поддерживайте набор сценариев, который можно обеспечить индексами и измерить; отдельный search endpoint может быть уместен для полнотекстового ранжирования. Обязательно тестируйте границы равных значений, `null`, пустой набор и переход между страницами.

### Versioning.
<!-- question-id: 28-http-rest-api-design-q12 -->

#### Ответ
Версия API нужна, когда нельзя сохранить совместимость контракта: например, меняется смысл поля, формат/тип данных, обязательность входа или поведение, на которое клиент опирается. Добавление нового необязательного поля обычно совместимо только для клиентов, которые игнорируют неизвестные поля; строгие декодеры и enum без fallback могут сломаться даже от «аддитивного» изменения. Поэтому совместимость проверяют с реальными схемами клиентов, а не называют любое добавление безопасным.

Версию можно выразить в URI (`/v2/...`), media type через content negotiation или отдельным заголовком. Это API-дизайн, а не требование HTTP. Версия в пути заметна и проста для маршрутизации/логов; вариант через media type держит идентичность ресурса отдельно от представления, но сложнее тестировать и кэшировать, если не настроены `Vary`/ключи кэша. Не создавайте новую major-версию для каждого внутреннего релиза и не поддерживайте версии без срока и владельца.

План миграции включает период параллельной поддержки, метрики использования клиентов, документацию, тесты контрактов, уведомление и дату отключения. Для HTTP-сигнала устаревания есть `Deprecation` ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html)) и `Sunset` ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html)); сами по себе заголовки не заменяют коммуникацию и конкретную политику совместимости. Версия должна описывать наблюдаемый контракт, а не внутреннюю архитектуру сервера.
