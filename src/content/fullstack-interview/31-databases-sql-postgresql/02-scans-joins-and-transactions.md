# Scans, Joins, and Transactions

## Interview questions

### Sequential scan.
<!-- question-id: 31-databases-sql-postgresql-q11 -->

#### Ответ

Sequential scan читает страницы таблицы последовательно и проверяет predicate для строк. Это не признак плохого плана: для маленькой таблицы, запроса большого процента таблицы, широкого результата или физически неупорядоченных heap fetch последовательное чтение зачастую дешевле обхода индекса и множества случайных чтений. Оно может быть параллельным и хорошо использует I/O.

Если план неожиданный, сравните estimated/actual rows, размер таблицы, долю совпадений и buffers. Иногда причина — stale statistics или выражение/приведение, не соответствующее индексу; иногда seq scan объективно оптимален. Нельзя оценивать запрос по правилу «есть индекс — должен быть Index Scan»: индекс сам по себе не уменьшает работу, если нужно прочитать большую часть данных.

### Index scan.
<!-- question-id: 31-databases-sql-postgresql-q12 -->

#### Ответ

При Index Scan PostgreSQL находит подходящие записи в индексе, затем по TID обращается к heap, чтобы получить остальные колонки и проверить MVCC-видимость. Такой путь хорош, когда условие отбирает небольшую часть строк и доступ к heap остается разумным. Если совпадения разбросаны по многим страницам, random I/O может сделать sequential scan дешевле.

Смотрите фактические строки, loops, buffers и heap fetches, а не только название узла. Функция/каст на индексированном поле, несовпадающая collation/operator class или неподходящий порядок composite index могут не дать использовать ожидаемый индекс; функциональный/partial индекс иногда решает это, если его predicate совпадает с query и оправдан обслуживанием.

### Bitmap scan.
<!-- question-id: 31-databases-sql-postgresql-q13 -->

#### Ответ

Bitmap plan обычно сначала строит bitmap TID-ов из одного или нескольких индексов, затем сортирует доступ к heap страницам и читает их группами. BitmapAnd/BitmapOr позволяют сочетать индексы без необходимости иметь один composite index под всякую комбинацию фильтров. Этот путь полезен при промежуточной селективности: он уменьшает случайные переходы по heap по сравнению с обычным Index Scan.

Он не сохраняет естественный порядок индекса, поэтому для ORDER BY может понадобиться отдельный sort. Большой bitmap может стать lossy из-за ограниченного рабочего объема памяти: тогда PostgreSQL перечитает страницы и переоценит строки. Проверьте Recheck Cond, exact/lossy heap blocks, work_mem и стоимость фактического плана; bitmap не является автоматически быстрее одиночного индекса или seq scan.

### Join algorithms.
<!-- question-id: 31-databases-sql-postgresql-q14 -->

#### Ответ

Planner выбирает алгоритм join по оценке количества строк, доступным индексам, сортировке входов, ширине строк, памяти и стоимости I/O. Основные варианты — nested loop, hash join и merge join; план может содержать их комбинации, а порядок соединения нескольких таблиц существенно влияет на объем промежуточных результатов. Поэтому ошибка cardinality оценки часто приводит к неверному join strategy.

Чтобы анализировать выбор, смотрите фактические строки и loops каждого child, фильтры join и buffers; затем проверьте, совпадает ли оценка с реальностью и не раздувает ли запрос строки из-за отношения one-to-many. Не задавайте принудительный join type прежде, чем проверить статистику, индексы и дубликаты в модели. Выигрыш оценивается полной query latency и ресурсами, а не эстетичностью узла.

### Nested loop.
<!-- question-id: 31-databases-sql-postgresql-q15 -->

#### Ответ

Nested Loop берет очередную строку внешнего (outer) набора и ищет подходящие строки во внутреннем (inner) наборе. Он особенно хорош, когда outer небольшой, а inner можно быстро отфильтровать индексом; также естественен для очень маленького join или запроса с LIMIT, где важна ранняя первая строка. Грубая оценка — число outer-строк, умноженное на цену одного inner lookup.

Риск — ошибочно большой outer либо отсутствие подходящего индекса: тогда внутренний scan повторяется много раз. В EXPLAIN ANALYZE смотрите loops на inner node и умножайте на фактическую работу за цикл; например, простой index lookup может стать дорогим при тысячах повторов. Перед заменой индекса проверьте, не неверно ли planner оценил кардинальность внешней стороны.

### Hash join.
<!-- question-id: 31-databases-sql-postgresql-q16 -->

#### Ответ

Hash Join обычно строит hash table по меньшей стороне соединения (build side), затем сканирует другую сторону и ищет совпадающие hash keys. Он эффективен для достаточно крупных equijoin без полезного порядка и подходящего индекса на inner relation; hash join не требует предварительной сортировки. Оценка строится на размере набора, количестве distinct ключей и объеме доступной памяти.

Если hash table не помещается в рабочую память, PostgreSQL разбивает обработку на batches и использует временное хранилище, что может сильно увеличить latency. В плане смотрите Hash node, batches, memory usage, temp read/write, размеры строк и row estimates; изменение work_mem может помочь, но увеличивает потенциальный расход памяти на каждый активный узел/запрос. Это не настройка «чем больше, тем всегда лучше».

### Merge join.
<!-- question-id: 31-databases-sql-postgresql-q17 -->

#### Ответ

Merge Join идет по двум входам, отсортированным по ключу соединения, и продвигает соответствующий курсор; при готовом порядке это линейный проход по входным строкам. Он полезен для больших наборов, когда входы уже упорядочены индексом или их сортировка дешевле hash/spill. На стороне могут повторяться ключи, поэтому узел должен корректно обработать группы совпадений.

Если сортировки нет, цена двух Sort может перевесить преимущество join; для потоков, выходящих из других узлов, требуемый порядок также может потребовать materialization. Merge Join обычно применяется к равенствам по merge-joinable operator class, но точная применимость зависит от оператора и типа. В плане проверяйте Sort Method, memory/disk, порядок входов и actual rows; само слово Merge не означает, что данные физически всегда отсортированы в таблице.

### Transactions.
<!-- question-id: 31-databases-sql-postgresql-q18 -->

#### Ответ

Транзакция группирует несколько операций так, чтобы они наблюдались и фиксировались согласно выбранному уровню изоляции, с COMMIT или ROLLBACK на одном соединении. В PostgreSQL все обычные одиночные statements уже исполняются в транзакционном контексте autocommit; явный BEGIN нужен для общего атомарного блока. Внутри транзакции ошибки могут переводить ее в aborted state: до rollback/savepoint последующие команды не продолжатся.

Границы транзакции должны охватывать инвариант, но быть короткими. Не держите row/table locks во время сетевого вызова, ожидания пользователя или дорогой сериализации: это удерживает connection и может блокировать конкурентов. Внешние системы не входят в транзакцию PostgreSQL; платеж/письмо/очередь обычно координируют через outbox/saga и идемпотентные повторы, а не обещают атомарность через COMMIT.

### ACID.
<!-- question-id: 31-databases-sql-postgresql-q19 -->

#### Ответ

ACID — свойства транзакций. **Atomicity:** все изменения транзакции фиксируются вместе либо откатываются. **Consistency:** приложение и ограничения БД сохраняют объявленные инварианты при переходе из одного допустимого состояния в другое; СУБД не угадывает бизнес-правила, которые не выражены в schema/logic. **Isolation:** конкурентные транзакции дают поведение, соответствующее выбранным guarantees, а не видят частично выполненные изменения. **Durability:** после успешного COMMIT результат переживает ожидаемые отказы в пределах конфигурации хранения и replication.

Это не бинарная гарантия всего приложения. Например, COMMIT не делает атомарным вызов платежного провайдера, а durability зависит от WAL/fsync/настройки synchronous replication и модели отказа. Для каждого инварианта решите, где его enforce-ить (NOT NULL/UNIQUE/FK/CHECK, транзакция, outbox), какой уровень изоляции нужен и как клиент повторит запрос при timeout после возможного успешного commit.

### Isolation levels.
<!-- question-id: 31-databases-sql-postgresql-q20 -->

#### Ответ

В PostgreSQL 18 Read Committed — default: каждый statement получает новый snapshot, поэтому два SELECT в одной транзакции могут увидеть разные committed состояния; dirty reads невозможны. Repeatable Read держит snapshot с первого statement транзакции: non-repeatable и phantom reads предотвращены, хотя по SQL-standard остаются serialization anomalies. PostgreSQL Read Uncommitted фактически ведет себя как Read Committed. Serializable использует SSI и гарантирует эквивалент некоторому serial порядку среди успешно зафиксированных транзакций.

Строгие уровни не бесплатны: Repeatable Read может завершить конкурирующее изменение serialization error, а Serializable может отклонить транзакцию при опасной зависимости. Клиент должен откатить и повторить **весь** бизнес-транзакционный блок с backoff и лимитом попыток; нельзя продолжать использовать результаты aborted попытки. Уровень выбирают под конкретный инвариант: атомарный UPDATE по строке/constraint может хватить при Read Committed, сложное «прочитал набор — решил — записал» может требовать явных lock/Serializable. [Isolation levels PostgreSQL 18](https://www.postgresql.org/docs/18/transaction-iso.html)
