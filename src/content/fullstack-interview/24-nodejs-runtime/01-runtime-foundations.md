# Node.js Runtime Foundations

## Interview questions

### Архитектура Node.js.
<!-- question-id: 24-nodejs-runtime-q01 -->

#### Ответ
Node.js — это не «V8 с HTTP-сервером», а runtime: V8 исполняет JavaScript и управляет heap/GC; Node добавляет C++ bindings и стандартную библиотеку (fs, net, crypto, streams), а libuv предоставляет event loop, переносимую интеграцию с ОС и thread pool. JavaScript callback обычно исполняется на одном main thread конкретного isolate. Асинхронная операция либо регистрирует ожидание в ОС (например, сетевой I/O), либо отправляется в libuv pool/другой native subsystem; по завершении в очередь ставится callback, который снова исполняется JavaScript-потоком.

Это объясняет профиль нагрузки: много коротких I/O-bound запросов масштабируются хорошо, пока синхронная работа каждого callback короткая. Один длинный callback задерживает все запросы этого event loop; worker pool тоже имеет конечную пропускную способность. Смотрите не только на средний latency, но и на event-loop delay/utilization, CPU, очередь thread pool и p95/p99. Для архитектурного решения разделяйте orchestration, I/O и CPU-heavy задачи, а не считайте слово «асинхронный» гарантией параллелизма. Модель и её последствия описаны в [официальном руководстве Node.js](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop).

### V8.
<!-- question-id: 24-nodejs-runtime-q02 -->

#### Ответ
V8 — JavaScript engine, который парсит код, строит внутреннее представление, интерпретирует его и оптимизирует горячие участки JIT-компиляцией. Важные для практики механизмы — hidden classes/shapes, inline caches и специализация по наблюдаемым типам. Если объектам присваивают свойства в разном порядке или один горячий call site получает хаотичный набор форм/типов, inline cache становится менее предсказуемым и оптимизации могут деоптимизироваться. Это не повод механически избегать динамических объектов: сначала измеряют профиль, затем проверяют горячий путь.

V8 управляет памятью JavaScript heap и собирает недостижимые объекты; Buffer/ArrayBuffer и нативные ресурсы имеют отдельные составляющие памяти, поэтому heapUsed не равен полному RSS. Каждый Worker Thread имеет свой isolate и heap; обычные объекты между ними не разделяются автоматически. Не опирайтесь на конкретные внутренние эвристики как на контракт: версия V8 зависит от версии Node. В production сначала снимите CPU/heap profile и проверьте аллокации, retained paths и GC pause, затем меняйте структуру данных или лимиты heap.

### libuv.
<!-- question-id: 24-nodejs-runtime-q03 -->

#### Ответ
libuv — C-библиотека, на которой Node строит event loop, таймеры, асинхронную абстракцию над ОС и общий thread pool. Она помогает одной модели приложения работать поверх разных backend-ов: например, epoll на Linux, kqueue на macOS и IOCP на Windows. Для сетевых сокетов ОС обычно сообщает о готовности, а не выделяет отдельный pool thread на каждое соединение; некоторые файловые/DNS/crypto/zlib операции выполняются в worker pool, поскольку их нельзя одинаково представить неблокирующим I/O или они вычислительно дороги.

Поэтому «всё async делает libuv thread pool» — неверно. Promise не создаёт поток, а async/await меняет способ композиции JavaScript, не место выполнения CPU. Pool общий для нескольких API и может стать узким местом: длинные PBKDF2, файловые задачи и другие pool jobs конкурируют. Различайте event-loop delay и задержку очереди pool, задавайте нагрузочные лимиты, избегайте бездумного увеличения UV_THREADPOOL_SIZE и выносите тяжёлые вычисления в отдельно контролируемый pool/сервис. См. [официальное описание event loop и worker pool](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop).

### Event Loop Node vs browser.
<!-- question-id: 24-nodejs-runtime-q04 -->

#### Ответ
Базовые принципы одинаковы: JavaScript исполняет текущий callback до конца, затем runtime обрабатывает готовые async continuation. Но окружение и расписание различаются. В браузере есть rendering opportunity, DOM, пользовательские события и HTML event loop с задачами разных источников; microtasks обычно опустошаются до следующей задачи и перед возможным render. В Node нет браузерного рендера и есть собственные фазы libuv, setImmediate и process.nextTick. Node также имеет queue Promise/queueMicrotask; nextTick — отдельная Node-специфика.

Нельзя переносить между средами точный порядок timers/IO без уточнения контекста: он зависит от фазы, версии Node и того, где зарегистрированы callbacks. Современный Node предоставляет многие Web API, например fetch, но их наличие не превращает его event loop в browser event loop и не делает DOM доступным. Для совместимого кода проектируйте по гарантиям конкретного API, не по наблюдённому порядку логов; тестируйте таймеры через управляемые часы и фиксируйте целевые версии runtime.

### Event Loop phases.
<!-- question-id: 24-nodejs-runtime-q05 -->

#### Ответ
Упрощённый порядок фаз libuv: timers; pending callbacks; idle/prepare (внутренние фазы); poll для I/O; check для setImmediate; close callbacks. Это модель итерации, а не расписание с обещанными миллисекундами. В poll loop получает готовые I/O события и исполняет callbacks. Если очередь poll пуста, loop может подождать I/O до следующего timer/check либо перейти дальше согласно состоянию очередей.

После завершения JavaScript callback Node выполняет подходящие очереди microtasks/nextTick; они не являются обычными фазами libuv. В Node 20/libuv 1.45 изменилось расположение timer processing относительно poll, поэтому старые упрощённые диаграммы и тесты порядка setTimeout(0)/setImmediate могут вводить в заблуждение. Надёжно утверждать можно локальные гарантии API (например, immediate из I/O callback попадёт в check), но не глобальное чередование произвольных асинхронных источников. Сверяйтесь с документацией целевой версии и избегайте бизнес-логики, зависящей от гонки двух таймеров.

### Timers.
<!-- question-id: 24-nodejs-runtime-q06 -->

#### Ответ
setTimeout(cb, delay) означает «не запускать раньше порога delay при доступном event loop», а не «выполнить ровно через delay». Задержка может оказаться больше из-за длинных callbacks, нагрузки, OS scheduling и timer granularity. Нулевую/отрицательную/слишком малую задержку runtime нормализует согласно API; это не способ немедленно уступить CPU в точный момент. setInterval также не является real-time clock: долгий callback и event-loop lag дают дрейф и пропуски ожидаемого cadence.

Для периодической работы отделяйте расписание от длительности: вычисляйте следующий deadline от монотонного времени, решайте явно, догонять ли пропущенные интервалы или пропускать их, и не допускайте параллельного запуска следующей итерации, если предыдущая ещё выполняется. Для отмены храните handle и очищайте его при shutdown; долгоживущие интервалы могут удерживать ссылки и мешать завершению процесса. Дедлайны, retries и rate limiting лучше моделировать отдельными механизмами, с jitter и верхней границей, а не полагаться на точность таймера.

### Poll.
<!-- question-id: 24-nodejs-runtime-q07 -->

#### Ответ
Poll — фаза, в которой libuv получает готовность I/O от ОС, исполняет соответствующие callbacks и, если работы нет, может ждать событие. Именно поэтому сетевые запросы не требуют отдельного JavaScript-потока на соединение: ОС сигнализирует о готовности, а callback позже обслуживается event loop. Poll callback всё равно синхронный JavaScript: если он парсит большой payload или делает тяжёлый цикл, блокируется весь данный loop.

Не следует использовать poll как обещание «сначала завершится этот I/O» при конкурирующих источниках. Таймеры и check имеют отдельные фазы, а ready queue зависит от ОС и нагрузки. Диагностируйте задержки через event-loop delay/utilization и профили callback, а не только по времени ответа внешнего сервиса. При перегрузке ограничивайте конкурентность и размер входа: бесконтрольный fan-out может накопить work и memory, даже если каждая операция сама по себе асинхронная.

### Check.
<!-- question-id: 24-nodejs-runtime-q08 -->

#### Ответ
Check — фаза после poll, где исполняются callbacks setImmediate. Поэтому если setImmediate ставится внутри I/O callback, он запускается в check следующего подходящего прохода после poll; это полезный способ продолжить работу после текущего I/O turn. Вызов из top-level кода в конкуренции с setTimeout(..., 0) не задаёт универсального порядка: результат зависит от момента старта loop и среды.

setImmediate не создаёт поток и не гарантирует низкую задержку, если loop перегружен. Он может помочь разбить длинную обработку на порции, уступая loop между ними, но для CPU-параллелизма нужны Worker Threads/отдельный сервис. При разбиении на порции важно ограничить очередь и поддержать отмену; иначе вместо блокировки появится неограниченный backlog.
