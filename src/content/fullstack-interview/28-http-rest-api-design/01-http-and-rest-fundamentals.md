# HTTP and REST Fundamentals

## Interview questions

### REST.
<!-- question-id: 28-http-rest-api-design-q01 -->

#### Ответ
REST — это архитектурный стиль взаимодействия между клиентом и сервером, а HTTP — протокол с определённой семантикой методов, заголовков и кодов ответа. Поэтому JSON API поверх HTTP не становится REST API автоматически: если каждый endpoint вызывает произвольную команду, это может быть удобный RPC-контракт, но сам формат URL этого не меняет.

В REST ресурсы идентифицируются URI, а интерфейс унифицируется семантикой HTTP: клиент работает с представлениями ресурса через GET, PUT, POST и другие методы. Важны также stateless-взаимодействие (каждый запрос несёт данные, необходимые для его понимания), возможность кэширования там, где она корректна, и возможность посредников образовывать layered system. Гипермедиа может связывать ресурсы и следующие действия; HTTP-ссылки можно передавать, например, через `Link` по [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288.html), но HTTP не требует, чтобы каждый JSON API обязательно выдавал все переходы таким способом.

При проектировании следует отдельно фиксировать HTTP-контракт и доменную модель. HTTP задаёт общие правила: например, повторяемость PUT и смысл 201. API задаёт, что такое «заказ», какие переходы его состояния разрешены и кто имеет право их выполнять. В production важнее последовательная семантика ресурсов и методов, ясные состояния и обратная совместимость, чем косметическое переименование RPC-вызовов в существительные.

### Resource modeling.
<!-- question-id: 28-http-rest-api-design-q02 -->

#### Ответ
Ресурс — это абстракция, которой сервер назначает идентификатор и предоставляет представление; он не обязан совпадать с одной строкой БД. Для marketplace разумно различать товар каталога и предложение продавца: одно описание товара может иметь несколько предложений с отдельными ценой, остатком и статусом. Тогда `GET /products/{id}` читает товар, а `GET /offers/{id}` — конкретное предложение; такой разрез отражает самостоятельные жизненные циклы и права доступа.

Для каждого ресурса определяют стабильный URI, владельца, допустимые представления, операции, инварианты и связи. Коллекция служит точкой поиска или создания, а URI элемента адресует конкретный ресурс. Вложенный путь вроде `/orders/{orderId}/items/{itemId}` уместен, когда идентичность строки имеет смысл только в заказе; чрезмерная вложенность затрудняет повторное использование и авторизацию. Идентификатор родителя нельзя считать доказательством права доступа: сервер всё равно проверяет tenant/владельца.

Изменение существующего ресурса с известным URI естественно выражать PUT или PATCH; создание с серверным ID — обычно POST к коллекции с ответом `201 Created` и `Location`. Доменную команду вроде «подтвердить оплату» можно моделировать отдельным ресурсом операции/запроса либо явным command endpoint, если это точнее контракта. HTTP не диктует единственную схему URL; выбор фиксируется и документируется как контракт API ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)).

### HTTP methods.
<!-- question-id: 28-http-rest-api-design-q03 -->

#### Ответ
Метод несёт общую для всех ресурсов семантику, поэтому его нельзя выбирать только по удобству реализации. GET получает выбранное представление, HEAD имеет семантику GET без тела ответа, OPTIONS сообщает о возможностях взаимодействия. POST просит целевой ресурс обработать представление согласно его собственной семантике и часто используется для создания элемента с назначаемым сервером URI. PUT заменяет состояние целевого ресурса представлением запроса; DELETE просит удалить связь/состояние ресурса согласно контракту; PATCH применяет документ изменений.

У методов есть важные свойства. GET, HEAD, OPTIONS и TRACE определены как safe; safe-методы также idempotent. PUT и DELETE idempotent, но не safe. POST по умолчанию не idempotent. PATCH не получает свойство idempotent автоматически, хотя конкретный формат patch-документа может сделать операцию повторяемой. Эти термины описывают ожидаемый эффект для клиента, а не отсутствие логов или иных внутренних следов. Различия важны для автоматических повторов, кэширования, prefetch и посредников; подробности определяет [RFC 9110, раздел 9](https://www.rfc-editor.org/rfc/rfc9110.html#section-9), а PATCH — [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

Практическое правило: используйте POST для обработки/создания по правилам коллекции, PUT для полной записи известного ресурса и PATCH для явно описанного частичного изменения. Не маскируйте изменение данных под GET или произвольные query-параметры действия.

### Idempotency.
<!-- question-id: 28-http-rest-api-design-q04 -->

#### Ответ
HTTP idempotency означает, что несколько одинаковых запросов имеют тот же предполагаемый эффект на сервере, что и один запрос. Это свойство метода: по [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) PUT, DELETE и все safe-методы idempotent; POST не является таковым по умолчанию. Оно не обещает идентичный ответ на каждом повторе: после первого DELETE повтор может вернуть 404, но целевое состояние всё равно остаётся удалённым. Логи, аудит и счётчик запросов могут фиксировать каждый вызов — они не меняют определение эффекта операции.

Свойство нужно при неопределённом результате сети: клиент отправил запрос, сервер мог выполнить его, но ответ потерялся. Для idempotent-запроса повтор безопаснее; повтор POST без дополнительного контракта способен создать второй заказ или списать оплату второй раз. Поэтому retry-политика должна учитывать метод, результат/момент обрыва, дедлайн, лимит попыток и backoff, а не повторять все 5xx бесконечно.

Для не-idempotent команды можно определить дедупликацию на уровне приложения, например по ключу запроса. Тогда нужно описать область уникальности, связь с principal и payload, срок хранения, конкурентную обработку и повтор результата. Это прикладной контракт: сам HTTP не превращает POST в idempotent только из-за наличия произвольного заголовка.

### Safe methods.
<!-- question-id: 28-http-rest-api-design-q05 -->

#### Ответ
Safe — это свойство семантики метода: клиент не просит и не ожидает изменения состояния целевого ресурса. GET, HEAD, OPTIONS и TRACE определены в HTTP как safe; клиент может автоматически обходить ссылки, предварительно загружать GET или выполнять проверки, не ожидая побочного доменного действия. Safe не означает «сервер вообще ничего не записал»: access log, метрики, аудит чтения и обновление внутренней статистики допустимы, пока это не меняет требуемое состояние ресурса.

Из этого следует важное правило для API: URI вроде `/orders/123?cancel=true`, вызванный через GET, не должен отменять заказ. Семантика действия определяется методом, даже если URI или query выглядят как команда; несоответствие нарушает ожидания клиента и может привести к отмене через crawler, prefetch или кэш. Для изменения нужен unsafe-метод и явная проверка авторизации/CSRF там, где применимо.

Не следует смешивать safe и idempotent. Safe-методы idempotent, но PUT и DELETE idempotent, хотя они не safe: повторный вызов приводит к тому же желаемому состоянию, однако клиент явно запросил изменение. Это различие определено в [RFC 9110, §9.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2).

### Status codes.
<!-- question-id: 28-http-rest-api-design-q06 -->

#### Ответ
Код ответа должен описывать результат HTTP-операции достаточно точно, а тело — при необходимости дать представление или детали ошибки. Успех чтения/изменения с представлением обычно `200 OK`; созданный ресурс — `201 Created` с `Location`; принятое, но ещё не завершённое асинхронное действие — `202 Accepted` с документированным способом проверить статус; успешный ответ без тела — `204 No Content`. Для условного GET кэш может получить `304 Not Modified`.

Ошибки также различают по смыслу: `400 Bad Request` для некорректного запроса/синтаксиса; `401 Unauthorized` — не хватает аутентификации (обычно с `WWW-Authenticate`); `403 Forbidden` — доступ запрещён; `404 Not Found` — ресурса нет или API намеренно скрывает его существование; `409 Conflict` — операция конфликтует с текущим состоянием; `412 Precondition Failed` — не выполнено условие вроде `If-Match`; `415 Unsupported Media Type` — тип тела не поддерживается; `422 Unprocessable Content` — синтаксически понятное содержимое нельзя обработать по смыслу. `429 Too Many Requests` обозначает лимит частоты, а `503 Service Unavailable` — временную недоступность сервиса; в подходящих случаях сообщают время повтора через `Retry-After`.

Не возвращайте 200 на все случаи с `success:false`: это заставляет клиентов угадывать результат и ломает общие HTTP-инструменты. Выбор должен быть согласован с фактическим исходом и последовательно документирован ([RFC 9110, §15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15), [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html)).

### PUT vs PATCH.
<!-- question-id: 28-http-rest-api-design-q07 -->

#### Ответ
PUT и PATCH решают разные задачи. PUT направляет на известный URI полное новое представление целевого ресурса; поля, отсутствующие в полном контрактном представлении, не должны молча трактоваться как «оставить старое значение». Успешный PUT обычно возвращает 200 с представлением или 204 без него; если ресурс создан по URI клиента, возможен 201. Намеренный эффект повторного PUT с тем же представлением одинаков, поэтому метод idempotent. Чувствительный к доступу PUT должен явно оговаривать writable-поля, чтобы клиент не мог менять служебные или чужие атрибуты.

PATCH передаёт patch document — инструкции изменения, а не полное представление. Формат нужно указывать через `Content-Type` и проверять для ресурса; универсального обязательного формата PATCH нет. Например, JSON Patch ([RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html)) задаёт операции над JSON-документом, а JSON Merge Patch — отдельный формат ([RFC 7396](https://www.rfc-editor.org/rfc/rfc7396.html)). PATCH сам по себе не гарантирует idempotency: «увеличить на 1» при повторе изменит состояние снова, тогда как «установить в 5» может быть повторяемым. Сервер обязан применить patch атомарно: либо весь набор изменений, либо ни одного; [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html) также описывает `Accept-Patch` для объявления поддерживаемых форматов.

Чтобы избежать lost update, клиент отправляет полученный `ETag` в `If-Match`. Сервер применяет изменение только при совпадении версии, иначе отвечает `412`; после этого клиент перечитывает ресурс и разрешает конфликт, а не безусловно перезаписывает чужие изменения. Для независимых инвариантов всё равно нужны транзакции/ограничения на стороне хранилища.
