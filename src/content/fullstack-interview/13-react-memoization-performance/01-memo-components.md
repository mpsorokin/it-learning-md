# Memo components

## Interview questions

### React.memo.
<!-- question-id: 13-react-memoization-performance-q01 -->
#### Ответ

`memo(Component)` возвращает компонент-обёртку, который обычно позволяет React пропустить повторный render дочернего компонента, если родитель рендерится, а props остались равными. Это bailout-оптимизация, а не изменение результата и не гарантия: render должен оставаться чистой функцией от props, state и context; React вправе перерендерить компонент и без изменения props. Не используйте `memo`, чтобы скрыть ошибку мутации или добиться корректного поведения.

`memo` окупается, когда компонент реально часто получает те же props, а его render дорогой или его subtree большой. Он почти бесполезен, если каждый render передаёт новый object/function/array, если изменение props необходимо показать сразу либо если render дешёвый. Компонент всё равно обновляется из-за собственного state, используемого Context и других источников обновлений. Подбирайте узкие props и ставьте границу вокруг дорогого листа, а не оборачивайте всё приложение «на всякий случай».

Сначала измерьте в React DevTools Profiler или `<Profiler>` и браузерном Performance trace; сравнивайте пользовательскую задержку и стоимость render, а не только число вызовов компонента. В production измерения отличаются от dev/Strict Mode; для `<Profiler>` нужен специальный production profiling build. [Контракт и ограничения `memo`](https://react.dev/reference/react/memo), [React Profiler](https://react.dev/reference/react/Profiler).

### Как сравниваются props?
<!-- question-id: 13-react-memoization-performance-q02 -->
#### Ответ

По умолчанию React сравнивает каждый prop старого и нового render через `Object.is`; это поверхностная проверка по набору prop-значений, не рекурсивное сравнение объектов. Для строк и чисел равные значения обычно пройдут bailout. Для object, array и function сравнивается идентичность: два объекта `{ id: 1 }`, созданные независимо, различны, даже если поля одинаковы. Поэтому свежий literal или inline callback в родителе сбрасывает весь bailout ребёнка.

Есть три уровня решения: передавать ребёнку только примитивные/минимальные props; стабилизировать действительно нужное значение через `useMemo`/`useCallback`; или передать собственный `arePropsEqual` вторым аргументом `memo`. Comparator обязан вернуть `true` только когда новый render дал бы то же визуальное и поведенческое поведение, и проверить все props, включая функции. Если принять новую callback за старую, она может замкнуть старый state/props. Deep equality часто дороже самого render и становится опасной при изменении глубины данных, поэтому её не вводят без измерения и ограниченной структуры.

Изменяйте данные иммутабельно: при реальном изменении выдавайте новое значение, а неизменённые части сохраняйте, например structural sharing. Мутация объекта при сохранении той же ссылки может привести к пропуску нужного обновления. [Сравнение props и custom comparator](https://react.dev/reference/react/memo).

### Почему memo component всё равно может rerender?
<!-- question-id: 13-react-memoization-performance-q03 -->
#### Ответ

`memo` сравнивает только props, пришедшие от родителя. Он не замораживает компонент и не выключает остальные источники обновлений. Повторный render ожидаем, когда меняется собственный state, меняется используемое значение Context, компонент получает другой `key`/перемонтируется, либо React решает выполнить render по внутренним причинам. В development Strict Mode также повторно вызывает чистый render для поиска side effects; это не означает двойной commit в production.

Проверьте в таком порядке: что изменилось в props по `Object.is`; не создаются ли объект/массив/функция заново; не читает ли компонент Context, который изменился; не происходит ли state update в нём/потомке; стабилен ли key и позиция в дереве. React DevTools Profiler показывает причину render в его версии инструментов; обычный `console.log` может вводить в заблуждение из-за Strict Mode и незакоммиченных/отброшенных render попыток при concurrent rendering.

Не добавляйте comparator, который намеренно игнорирует изменившийся prop: так можно получить stale UI или stale closure. Исправляйте владельца state/данных и используйте bailout только если входы действительно семантически неизменны. [Поведение `memo` с state и Context](https://react.dev/reference/react/memo), [React Strict Mode](https://react.dev/reference/react/StrictMode).

### Context + memo.
<!-- question-id: 13-react-memoization-performance-q04 -->
#### Ответ

Компонент, читающий Context через `useContext`, подписан на текущее значение ближайшего Provider. Когда Provider передаёт значение, не равное предыдущему по `Object.is`, React обновляет consumers этого Context, даже если consumer обёрнут в `memo`. Это намеренно: props-бейлаут не должен скрывать изменение зависимости, которую компонент явно прочитал.

Если компоненту нужно только выбрать часть большого Context, вынесите чтение в небольшой адаптер: адаптер вызывает `useContext`, вычисляет нужный примитив или узкий prop и передаёт его memoized child. Тогда consumer адаптера обновится на весь Context, а дорогой child сможет пропустить работу, если выбранное значение не изменилось. Другие варианты — разделить Context по семантике/частоте обновлений или использовать store с selector-подписками, если нужна гранулярность на большой часто обновляемой модели.

`useMemo` для value Provider помогает лишь когда проблема — новая идентичность value из-за render самого Provider; он не превращает Context в селектор и не спасает consumer при реальном изменении переданного value. [Официальное поведение Context и `memo`](https://react.dev/reference/react/memo), [подписка на Context](https://react.dev/reference/react/useContext).

### Local state + memo.
<!-- question-id: 13-react-memoization-performance-q05 -->
#### Ответ

State принадлежит конкретному экземпляру компонента. Изменение его собственного state требует нового render этого компонента независимо от `memo`: `memo` отвечает за возможность пропустить render из-за неизменившихся props от родителя, а не за блокировку локальной интерактивности. Обновление родителя может быть отдельно пропущено memoized child, если его props не изменились.

Хорошая форма — держать state как можно ближе к UI, который его меняет. Например, раскрытие одного menu не должно заставлять всю страницу пересчитываться; выделите `Menu` с собственным `useState`. Если дорогой соседний компонент рендерится вместе с локальным владельцем state, разрежьте компонент по ответственности или передавайте стабильные минимальные props. Иногда можно передать неизменяемые JSX children в компонент-обёртку, чтобы изменение её собственного state не требовало создавать subtree заново.

Не поднимайте transient UI state вверх ради централизованности без потребности в синхронизации: это расширяет область повторных render и создаёт давление на memoization. Если state действительно общий, размещайте его в ближайшем общем владельце и оптимизируйте лишь измеренные дорогие ветви. [Рекомендации React по локализации state и `memo`](https://react.dev/reference/react/memo).
