# App structure and domain logic

## Interview questions

### Как структурировать большой React app?
<!-- question-id: 19-react-application-architecture-q01 -->
#### Ответ

Начинайте не с модного шаблона папок, а с карты изменений: ключевые user journeys, предметные области, владельцы команд, runtime/deploy границы, критичные интеграции и места, где правка часто ломает соседний код. Обычно верхний уровень — composition приложения и маршруты; ниже — самостоятельные feature/domain-модули с UI, model/use cases, API-адаптерами и тестами; shared содержит только действительно общие стабильные primitives и инфраструктуру. Задайте однонаправленные зависимости и публичные точки входа: feature может использовать shared и объявленные контракты, но не читать внутренние файлы соседа. Чистые правила предметной области не должны импортировать React или fetch. Структура должна отражать ownership и deployment constraints, а не создавать каталог на каждый компонент. Зафиксируйте ограничения импортов линтером/проверкой графа и ревью-правилами, чтобы архитектура исполнялась автоматически. Мигрируйте по новым/часто меняемым vertical slices; rollout измеряйте по lead time, defect rate, bundle size и ошибкам ключевых маршрутов. Микрофронтенды, дополнительные слои и DI-контейнер вводят только при реальном требовании независимой поставки или тестирования.

### Feature-based architecture.
<!-- question-id: 19-react-application-architecture-q02 -->
#### Ответ

Feature-based структура группирует код по пользовательской возможности или предметной области: например, projects может содержать собственные query/hooks, правила, UI, tests и внутренние adapters. Это облегчает поиск, ownership и изменение функции целиком; feature можно развивать и, при необходимости, переносить без открытия десятка глобальных слоёв. На верхнем уровне route собирает feature exports, а общий shared модуль содержит нейтральные UI primitives, форматирование и транспортные соглашения. Между features используйте публичный API или отдельный domain contract; импорт внутренних путей создаёт скрытые связи и усложняет миграцию. Общий код не должен автоматически попадать в shared после второго использования: сначала проверьте одинаковы ли semantics, release cadence и owner. Риск — дублирование или чрезмерное дробление функций; его снижают явные границы и каталог публичных exports. Для команды особенно полезно зафиксировать allowed imports и ответственность за query keys/API, иначе отдельные feature начнут независимо моделировать одно и то же понятие.

### Layered architecture.
<!-- question-id: 19-react-application-architecture-q03 -->
#### Ответ

Layered architecture разделяет код по ответственности, например UI/presentation, application/use cases, domain rules и infrastructure/adapters. Здоровое направление зависимостей идёт внутрь: UI вызывает application API; application зависит от доменных контрактов; database/network implement adapters, но чистые правила не зависят от конкретной библиотеки. В React приложении это помогает тестировать правила без DOM и заменять API client без переписывания компонентов. Слои не обязаны означать четыре папки и интерфейс для каждого вызова: если модуль тривиален, слои добавят переходы и копирование DTO без изоляции. Комбинировать слои с feature-based архитектурой можно: feature владеет своим UI/use case/model, а внутри имеет нужные ports/adapters. Явно различайте transport DTO и domain view model только там, где их контракты действительно отличаются. Проверяйте границы графа импортов автоматически и избегайте циклов между application и infrastructure.

### Где хранить domain logic?
<!-- question-id: 19-react-application-architecture-q04 -->
#### Ответ

Правило, которое определяет допустимость бизнес-операции, должно жить в domain/use-case слое, а не быть разбросано по JSX, случайным event handlers или повторяющимся API вызовам. Чистое преобразование вроде расчёта eligibility или перехода статуса принимает явные данные и возвращает решение; его проще тестировать таблицей граничных случаев. Оркестрация use case может вызывать repository/API и применять правила, но React hook здесь только связывает UI с async command, loading и отменой. Отрисовка форматирует результат и доступность, но не становится источником бизнес-правды. Важно: браузерная проверка нужна для хорошего UX, однако backend обязан повторно проверять permission и инварианты, потому что клиент контролируется пользователем. Не создавайте универсальную папку utils для несвязанных правил: модуль должен иметь понятный owner и публичный contract. Для сложных сценариев явно моделируйте состояние процесса и ошибки, а не спрятанную последовательность setState.
