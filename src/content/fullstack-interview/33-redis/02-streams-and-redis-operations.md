# Streams and Redis Operations

## Interview questions

### Streams.
<!-- question-id: 33-redis-q10 -->

#### Ответ
Redis Stream — упорядоченный append-oriented log внутри Redis key: `XADD` добавляет entry с уникальным ID вида `milliseconds-sequence`, `XRANGE` читает диапазон, `XREAD` позволяет ждать новые записи. Retention ограничивают trim по длине/ID; stream иначе будет расти и занимать память. Один stream может читаться напрямую несколькими независимыми клиентами или через несколько consumer groups.

Consumer group распределяет новые сообщения между consumers одной группы и хранит состояние last-delivered ID и pending entries. После `XREADGROUP` сообщение остаётся в Pending Entries List до `XACK`; при падении consumer приложение должно обнаружить застоявшиеся записи через `XPENDING` и передать их живому worker через `XCLAIM`/`XAUTOCLAIM` (команда `XAUTOCLAIM` доступна с Redis 6.2). Это даёт практически at-least-once обработку: падение после бизнес-эффекта, но до `XACK` вызовет повтор, поэтому handler обязан быть идемпотентным. `XACK` не подтверждает транзакцию в БД и не создаёт exactly-once.

В production задают политику повторов, максимальное число delivery, backoff, dead-letter stream, мониторинг длины/Pending и удаление старых consumers. Тримминг требует особой осторожности: запись, ещё ожидающая обработки группой, не должна случайно потерять payload до recovery. Stream и consumer-group state подчиняются настроенным RDB/AOF и асинхронной репликации Redis; для критичных событий отдельно проверяют fsync, failover и допустимую потерю последних подтверждённых изменений. Базовая модель и команды описаны в [официальной документации Streams](https://redis.io/docs/latest/develop/data-types/streams/); новые возможности Streams добавляются по версиям, поэтому здесь предполагается совместимость с Redis 6.2+ для `XAUTOCLAIM`, без зависимости от новых 8.x-команд.

### Redis vs Kafka.
<!-- question-id: 33-redis-q11 -->

#### Ответ
Это разные компромиссы. Redis оптимизирован для малого latency, структур данных и оперативных операций; Streams добавляют log-like модель, группы, pending и replay в пределах сохранённой retention. Но данные Redis в первую очередь конкурируют за RAM, а persistence/replication и ёмкость исторического журнала зависят от его конфигурации. Redis Pub/Sub вообще ephemeral и не является очередью.

Kafka проектировался как распределённый persistent commit log: партиции, независимое удержание записей по сроку/размеру, consumer offsets и множество групп, которые читают одни и те же события независимо. Он часто лучше для длительного replay, большого event backbone и независимых команд-консумеров; цена — отдельная инфраструктура, partition/key design, управление lag и более сложная операционная модель. Redis Streams может быть проще для фоновых задач и realtime потока, если объём, retention и durability укладываются в Redis.

Ни одно из решений автоматически не даёт exactly-once side effect в произвольной БД: consumer всё равно проектируют с идемпотентностью, retry и обработкой poison messages. Сравнивать нужно конкретно по throughput/latency, retention, восстановлению после потери узла, числу consumer groups, ordering, стоимости памяти/диска, multi-region и навыкам эксплуатации, а не по лозунгу «Redis быстрее». Можно использовать Redis для hot operational state, Kafka для долгого event log, связывая их через outbox/CDC и явно выбранный источник истины.

### Rate limiting.
<!-- question-id: 33-redis-q12 -->

#### Ответ
Rate limiter задаёт измеримую политику — например, не более 100 запросов за rolling 60 секунд на пользователя — и центральное состояние, общее для всех экземпляров API. Fixed window прост и реализуется счётчиком `INCR` с TTL, но граница окна допускает burst: клиент может отправить лимит в самом конце одного окна и ещё лимит сразу в начале следующего. Sliding log точен, но хранит события; sliding counter/approximation экономит память; token bucket позволяет задать ёмкость burst и скорость пополнения.

Состояние обновляют атомарно, обычно Lua script/function: прочитать tokens/time, пополнить bucket с ограничением capacity, разрешить/отклонить запрос, сохранить состояние и TTL одним серверным действием. Отдельные команды `GET` → решение в приложении → `SET` гоняются при параллельных запросах. Для fixed window `INCR` атомарен, но связка `INCR` и первоначальный `EXPIRE` тоже должна быть атомарной (script), иначе crash между командами оставит вечный counter. Redis Cluster требует, чтобы ключи одной Lua-операции были в одном hash slot; используют общий hash tag, если алгоритму нужны несколько ключей.

Ключ лимита строят по доверенной идентичности: authenticated user/API key/tenant, а не только по произвольному `X-Forwarded-For`; IP берут только после настройки trusted proxy. Возвращают понятные `429`, `Retry-After` и оставшуюся квоту, разделяют лимиты по endpoint/дорогим операциям и исключают секреты из key name. При Redis outage заранее решают fail-open или fail-closed по риску, добавляют локальный аварийный лимит, timeout и метрики allow/deny/error, но локальный счётчик не является глобально точным. Redis поддерживает несколько алгоритмов; пример официальной документации — token bucket с атомарной Lua-операцией ([rate limiter](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)).

### Sessions.
<!-- question-id: 33-redis-q13 -->

#### Ответ
Сервер генерирует непредсказуемый opaque session ID и отдаёт его браузеру в cookie с `HttpOnly`, `Secure`, подходящим `SameSite`, ограниченным `Path`/`Domain` и сроком действия. Само состояние хранится в Redis по namespaced key, например `session:<id>`, с TTL; браузер не получает права доступа, роли и секреты в открытом виде. На каждом запросе сервер валидирует session, загружает пользователя и применяет актуальную authorization policy.

После login/изменения уровня привилегий session ID нужно ротировать, иначе session fixation сохраняет атакующему ранее известный идентификатор. Logout удаляет session; смена пароля, отзыв устройства или подозрение на compromise должны иметь механизм массовой или адресной ревокации. Cookie не устраняет CSRF: для cookie-auth нужны SameSite/CSRF token и проверка origin согласно модели приложения. Redis key хранит минимально нужное, сериализация версионирована, TTL обновляется контролируемо (idle timeout плюс отдельный absolute expiry), а PII/секреты не попадают в логи.

Redis outage для аутентификации обычно требует отказать в запросе или использовать заранее спроектированный bounded fallback: выдавать доступ без проверки session опасно. Eviction может разлогинить пользователей, поэтому session store отделяют от кэша и настраивают memory capacity/noeviction с обработкой ошибок. Primary-replica replication асинхронная, так что после failover недавно созданная или отозванная session может временно исчезнуть/вернуться; риск учитывают в security-модели, а особо критичное состояние проверяют в authoritative store. Нужны метрики latency/errors, размер и churn сессий, eviction, failover и очистка просроченных записей.

### Counters.
<!-- question-id: 33-redis-q14 -->

#### Ответ
Для целочисленных счётчиков Redis предоставляет атомарные `INCR`/`INCRBY`: конкурентные команды на одном primary сериализуются, поэтому два клиента не потеряют инкремент из-за read-modify-write в приложении. Команда работает с целым представлением значения в string key; используйте целые в диапазоне signed 64-bit и не кодируйте финансовые суммы через плавающую точку. При необходимости `EXPIRE` задают вместе с первым инкрементом атомарным script, чтобы crash не оставил счётчик без срока.

Атомарность `INCR` не означает idempotency запроса: если клиент потерял ответ и повторил команду, счётчик увеличится второй раз. Для дедупликации храните request/event ID и обновляйте его вместе со счётчиком атомарно (script или транзакция), либо используйте таблицу уникальных событий в authoritative DB. При очень высокой нагрузке один горячий counter становится точкой сериализации; можно дробить его на shards и суммировать при чтении, приняв менее точное мгновенное значение и более сложные TTL/очистку.

При failover подтверждённый increment может потеряться, так как replication по умолчанию асинхронна; persistence и `WAIT` уменьшают риск, но не обеспечивают абсолютную strong consistency. Если счётчик — аналитика или временная квота, этот компромисс бывает приемлем. Если от него зависит баланс/лимит, который нельзя превысить, операция должна быть условной и транзакционно защищённой источником истины, например `UPDATE ... WHERE balance >= amount` с constraint в БД.

### Atomic operations.
<!-- question-id: 33-redis-q15 -->

#### Ответ
Одна Redis-команда атомарна относительно других команд на данном сервере: например, `INCR`, `SET ... NX` или `HINCRBY` не показывают другим клиентам промежуточный результат одной команды. Но последовательность обычных вызовов из клиента не атомарна: между `GET` и `SET` другой клиент может обновить тот же key. Pipeline уменьшает сетевые round trips, но не превращает произвольный read-modify-write в транзакцию.

Для нескольких команд есть `MULTI`/`EXEC`, где queued команды выполняются подряд без interleaving других клиентов на этом узле; `WATCH` даёт optimistic CAS: если watched key изменился до `EXEC`, транзакция отменяется и приложение перечитывает/повторяет. Redis transaction не предоставляет rollback как SQL: runtime error одной команды не отменяет уже выполненные соседние команды. Для логики «прочитать → проверить → записать» часто подходит Lua script/function, выполняемый атомарно; он тоже не является откатом ранее сделанных внутри скрипта записей при последующей ошибке, поэтому до первой мутации валидируют аргументы и состояние.

В Redis Cluster multi-key операции и транзакции обычно требуют ключи в одном hash slot; иначе клиент получит CROSSSLOT. Не следует держать сервер занятой длинным script, а количество ключей и вычисление ограничивают. Атомарность Redis заканчивается на его границе: она не объединяет Redis и SQL, не гарантирует сохранность после failover и не делает внешнюю оплату частью транзакции.

### Lua scripts.
<!-- question-id: 33-redis-q16 -->

#### Ответ
Lua script позволяет передать серверу короткую логику, которая выполняет чтения, условия и изменения без чередования команд других клиентов. Это удобно для token bucket, compare-and-delete lock, атомарного check-and-set и дедупликации. Клиент передаёт keys отдельным списком `KEYS` и обычные аргументы через `ARGV`; все key names должны быть известны скрипту явно, а в Redis Cluster ключи одной операции должны попадать в один hash slot.

Скрипт исполняется в основном потоке Redis и блокирует выполнение других команд на время своей работы. Поэтому он должен быть bounded: не сканировать неограниченные структуры, не делать долгие циклы и не вызывать внешний сервис. Проверяйте типы и диапазоны входов до записи; ошибка после нескольких `redis.call` не откатывает уже произведённые side effects. Версии и единицы измерения аргументов нужно документировать, а коды результата сделать однозначными, чтобы клиент мог корректно отличить deny, retry и ошибку.

`EVALSHA`/script cache может потребовать повторно загрузить script после restart/flush; приложение должно корректно обрабатывать `NOSCRIPT`. Redis 7+ также предоставляет Redis Functions — именованные серверные функции, сохраняемые как часть базы и удобные для повторного использования; это отдельная возможность, не то же самое, что volatile cache обычных загруженных scripts. Учитывайте compatibility и deployment функций/скриптов между версиями и всеми шардами. Официальная документация подчёркивает atomic execution и необходимость ограничивать время скрипта ([programmability](https://redis.io/docs/latest/develop/programmability/eval-intro/)).

### Thundering herd.
<!-- question-id: 33-redis-q17 -->

#### Ответ
Thundering herd — всплеск большого числа одновременных обращений к одному или многим ресурсам, например после массового истечения TTL или восстановления сервиса. Если каждый запрос на cache miss независимо обращается к базе, cache перестаёт сглаживать нагрузку ровно в момент пика; база может перегрузиться, latency вырастет, таймауты породят ещё больше retry и получится feedback loop.

Защита: jitter на TTL; request coalescing/single-flight (один loader на key в процессе); bounded distributed lock для нескольких инстансов; stale-while-revalidate; предварительное заполнение и поэтапный rollout; concurrency limit и backpressure на источник. После lock обязательно повторно проверить cache: другой worker мог уже записать значение. Ожидание lock должно иметь короткий deadline; при его истечении выбирают stale value, деградированный ответ или direct DB fallback с общим лимитом. Без ограничений fallback сам становится herd.

При холодном старте меняйте namespace/прогревайте ключи постепенно, а не очищайте всю базу cache одновременно. Автоматический retry должен иметь exponential backoff и jitter и не повторяться бесконечно. Метрики: concurrent misses по hot keys, запросы к источнику, cache hit/eviction, очередь ожидания, timeout, lock contention и saturation DB. На практике термины thundering herd и cache stampede часто используют как синонимы; иногда первым называют более широкий всплеск к любому восстановившемуся ресурсу.

### Cache stampede.
<!-- question-id: 33-redis-q18 -->

#### Ответ
Cache stampede обычно описывает узкий случай herd: один популярный cache key истёк или стал недоступен, и множество запросов одновременно вычисляют одно и то же дорогое значение. Оно особенно опасно, если запрос к origin fan-out-ится по нескольким зависимостям или запросы ретраятся после timeout.

Обычное решение — single-flight: в процессе хранить один in-flight Promise на key и возвращать его результат всем ожидающим. Между несколькими процессами можно сделать lease-lock `SET key token NX PX ...`, повторно прочитать cache после получения lease и безопасно удалить lock compare-token скриптом. Это снижает дублирование, но lease может истечь при длинном вычислении; задавайте deadline, ограничивайте продление, освобождайте lock в `finally`, не делайте бизнес-эффект под cache lock и держите путь без lock как bounded fallback.

Для контента, где небольшая stale-выдача допустима, эффективнее stale-while-revalidate: сохранять старое значение чуть дольше и обновлять его в фоне. Также помогают TTL jitter, probabilistic early refresh (часть запросов обновляет до expiry), отрицательное кэширование, pre-warming и ограничения concurrency. Выбор зависит от свежести и latency contract: lock минимизирует дублирование, stale value снижает задержку, но отдаёт устаревшее; для строгих данных ответ берут из authoritative source. Нужны метрики возраста значения, числа refresh, lock acquisition/failure и нагрузки на origin, иначе stampede проявится только как неожиданный рост DB latency.
