# Cache and Expiration

## Interview questions

### Для чего Redis?
<!-- question-id: 33-redis-q01 -->

#### Ответ
Redis — in-memory data store с сетевым протоколом и структурами данных вроде strings, hashes, lists, sets, sorted sets и streams. Он полезен не только как key-value cache: его используют для сессий, счётчиков, rate limiting, очередей, Pub/Sub и временных индексов. Команда выполняется атомарно относительно других команд на том же узле, поэтому несколько операций чтения и записи можно объединить в Lua script или транзакцию.

Быстрый доступ достигается тем, что рабочий набор данных находится в памяти; persistence через RDB/AOF и replication доступны, но сами по себе не делают Redis эквивалентом транзакционной реляционной БД. Нужно отдельно выбрать модель durability, eviction, failover и допустимый уровень потери последних записей. Большинство команд обрабатывается последовательно в основном потоке, что упрощает атомарность, но длинная команда, большой Lua script или операция O(N) задержит команды других клиентов. Масштабирование по CPU обычно требует sharding/Redis Cluster, а не ожидания, что один узел параллельно исполнит любую команду.

Принимаем Redis Open Source 8.x как контекст примеров; базовые описанные свойства команд и структур не зависят от конкретной patch-версии. Ключевой production-вопрос — является ли Redis cache/ускорителем или источником данных: от этого зависят настройки persistence, резервирования, eviction и поведение при недоступности.

### Cache.
<!-- question-id: 33-redis-q02 -->

#### Ответ
Cache хранит производную копию данных ближе к потребителю, чтобы повторные чтения обходились дешевле, чем обращение к authoritative source: базе данных, удалённому API или вычислению. Cache не устраняет стоимость источника навсегда — он меняет профиль нагрузки на hit/miss и добавляет задачу управления устареванием.

Для production определяют ключ и его namespace, формат и версию сериализации, TTL, размер данных, invalidation при записи, допустимую stale-выдачу и fallback при сбое Redis. Cache key должен включать все параметры, влияющие на результат (например, tenant, locale и версию прав), иначе получится утечка между пользователями или неправильный ответ. Значения нужно валидировать при чтении: старый schema payload, частичная запись или несовместимый deploy не должны бесконтрольно ломать запрос.

Cache должен иметь явную политику памяти и наблюдаемость: hit ratio вместе с latency источника, miss, eviction, timeout, размер и горячие ключи. Высокий hit ratio сам по себе не доказывает пользу: можно обслуживать устаревшие данные или уменьшить число чтений ценой слишком дорогих инвалидаций. Для данных, потеря которых недопустима, нельзя полагаться на cache-настройки как на замену проверенной модели хранения и восстановления.

### Cache-aside.
<!-- question-id: 33-redis-q03 -->

#### Ответ
При cache-aside приложение владеет протоколом: сначала читает Redis; hit возвращается, miss приводит к чтению authoritative source, после чего результат записывается в Redis с TTL. Запись в кэш обычно не является частью транзакции источника. Это просто для внедрения и делает промахи безопасными: при потере ключа данные можно загрузить снова, но добавляет stale windows, двойные чтения и конкуренцию за один горячий ключ.

При обновлении порядок обычно такой: commit в БД, затем invalidation (`DEL`) кэш-ключа. Если удалить кэш до commit и транзакция откатится, следующий запрос загрузит старое состояние; если commit прошёл, а invalidation потерялась, устаревшее значение живёт до TTL. Даже порядок «commit → DEL» имеет гонку: loader мог прочитать старое значение до commit и записать его в cache после `DEL`. Для ограниченной eventual consistency помогают короткий TTL с jitter, versioned keys, outbox/CDC invalidation и single-flight; строгую свежесть проще гарантировать чтением из источника или версионированной проверкой, чем пытаться сделать Redis и БД общей атомарной транзакцией.

На miss используют защиту от stampede: локальное объединение одинаковых запросов внутри процесса и, для нескольких инстансов, короткий distributed lock с owner token и повторным чтением после получения lock. Если lock не получен, допустим bounded wait, stale value или чтение из БД — решение зависит от latency budget. Важно ограничить параллельность и не позволить кэш-ошибке превратить один miss в лавину запросов к источнику.

### Write-through.
<!-- question-id: 33-redis-q04 -->

#### Ответ
В write-through write path обновляет source of truth и кэш как часть одного логического запроса, а вызывающий код получает успех только после предусмотренных системой записей. Это может уменьшить stale reads сразу после записи и избежать отдельного «первого промаха», но синхронный путь становится медленнее и зависит от доступности обоих хранилищ.

Redis и реляционная БД не участвуют в общей ACID-транзакции. Если БД commit прошёл, а Redis timeout, нельзя считать операцию атомарно откатившейся; повтор операции тоже может иметь побочные эффекты. Сначала фиксируют БД, затем обновляют или инвалидируют Redis; сбои cache-write разрешают через retry/outbox и ограниченное окно stale, либо возвращают ошибку только если контракт требует read-your-writes. Для строже согласованного ответа можно вернуть подтверждённое значение напрямую из БД и инвалидировать кэш асинхронно.

Write-behind — другая схема: сначала изменяется cache, а запись в БД откладывается. Она может повысить throughput, но потеря Redis, сбой flush, переупорядочивание событий или неправильная дедупликация способны потерять или перезаписать бизнес-данные. Её выбирают только с durable queue/log, retry, idempotency, мониторингом backlog и понятным восстановлением; обычный Redis cache не следует использовать как единственную очередь для критичных записей.

### TTL.
<!-- question-id: 33-redis-q05 -->

#### Ответ
TTL ограничивает время существования ключа; Redis удаляет истёкший ключ и дальше возвращает его как отсутствующий. `EXPIRE` задаёт секунды, `PEXPIRE` — миллисекунды, `SET` умеет принимать `EX`/`PX`; `TTL` возвращает оставшееся целое число секунд, `PTTL` — миллисекунд. Значение `-1` означает, что ключ существует без expiry, `-2` — что ключа нет. Обычный `SET` сбрасывает прежний TTL, если явно не используется `KEEPTTL`.

Expiry не является точным таймером или гарантией удаления ровно в указанную миллисекунду: Redis обнаруживает истечение лениво при доступе и фоновым активным циклом. Поэтому TTL подходит для ограниченной свежести кэша, временных токенов и автоматической очистки, но не для запуска платежа или единственной гарантии бизнес-события в заданное время. Добавляйте небольшой случайный jitter к однотипным срокам, чтобы тысячи ключей не истекли одновременно.

TTL задают осознанно для cache/session key и контролируют наличие срока жизни; ключ без срока может навсегда занять память. При репликации expiry синхронизируется от primary, поэтому для read-after-expiry нельзя бездумно полагаться на произвольную lagging replica. Официальные команды и семантика описаны в [документации Redis по expiry](https://redis.io/docs/latest/develop/using-commands/keyspace/); подробности active/passive expiry могут зависеть от версии и конфигурации.

### Eviction policies.
<!-- question-id: 33-redis-q06 -->

#### Ответ
TTL — истечение по времени, eviction — принудительное вытеснение при достижении `maxmemory`; это разные причины исчезновения ключа. При `noeviction` новые команды, требующие дополнительной памяти, получают ошибку, существующие данные не выбираются на удаление. `allkeys-lru` и `allkeys-lfu` выбирают среди всех ключей; `volatile-lru`/`volatile-lfu` — только среди ключей с TTL; `volatile-ttl` предпочитает ключи с ближайшим expiry. Если volatile-политике нечего вытеснять, она ведёт себя как `noeviction`.

LRU/LFU в Redis — приближённые алгоритмы с выборкой кандидатов, а не идеальный глобальный список, поэтому их качество и CPU нужно оценивать на реальном распределении обращений. Для чистого кэша `allkeys-lru` часто является разумной отправной точкой, но LFU может лучше сохранять долгоживущие hot keys при всплесках; TTL не является eviction policy и сам по себе не ограничит memory до заданного предела.

Для cache и критичных stateful данных обычно безопаснее разделить инстансы: eviction кэша не должен незаметно удалить активную сессию или очередь. Выбирайте `maxmemory` с запасом на allocator fragmentation, replication/AOF buffers и нагрузочные пики, а не ровно по физической RAM. Наблюдайте `evicted_keys`, `expired_keys`, `keyspace_hits/misses`, `used_memory` и ошибки записи; отдельно проверьте поведение приложения при `OOM`/eviction и недоступности Redis. Список политик и ограничения описаны в [официальной документации Redis](https://redis.io/docs/latest/develop/reference/eviction/); отдельные политики появляются в новых версиях.

### Cache invalidation.
<!-- question-id: 33-redis-q07 -->

#### Ответ
Invalidation — согласованный механизм сообщить кэшу, что конкретная копия больше не соответствует authoritative source. Наиболее частые подходы: удалить ключ после успешного commit и перечитать при следующем запросе; обновлять значение write-through; использовать версионированный key namespace; ограничивать stale через TTL; публиковать событие из outbox/CDC. Выбор зависит от допустимой задержки устаревания, частоты записи и стоимости пересборки.

У каждой схемы есть race conditions. `DEL` до commit создаёт риск преждевременной перезагрузки; `DEL` после commit может потеряться; старый loader, начавшийся до invalidation, способен записать устаревший ответ уже после неё. Outbox делает доставку события повторяемой, но потребители должны быть идемпотентны; версия/etag позволяет отвергать старые результаты, но требует корректно получать актуальную версию и включать её во все связанные ключи. Invalidation через Pub/Sub — сигнал, а не durable журнал: отключённая подписка пропустит сообщения.

Для связанных сущностей определите область инвалидации (списки, детали, агрегаты и пагинационные страницы), порядок событий и идемпотентность. При deploy полезны namespace versioning и постепенное заполнение нового поколения; массовая синхронная очистка всего cache может сама вызвать stampede. Контракт должен прямо говорить, является ли согласованность strong/read-your-writes или eventual и какое окно stale допустимо.

### Distributed locks.
<!-- question-id: 33-redis-q08 -->

#### Ответ
Базовая lease-блокировка на одном Redis primary создаётся атомарно: `SET lock:resource <случайный-token> NX PX <lease-ms>`. `NX` не даёт перезаписать чужой lock, TTL освобождает его после падения владельца. Владелец хранит криптографически случайный token и удаляет ключ только если token всё ещё его: сравнение и удаление выполняются одним Lua script. Обычный `DEL` опасен: lease могла истечь, lock перехватил другой процесс, а старый владелец своим `DEL` снимет уже чужую блокировку.

Это lease с конечным сроком, а не вечная взаимная блокировка. Процесс может остановиться на паузе GC или потерять сеть дольше TTL, затем продолжить работу уже без lock и конфликтовать с новым владельцем. Продление также делается compare-and-extend по token и должно завершаться до дедлайна. Для защиты целевого ресурса от просроченного владельца нужен fencing token — монотонный номер, который ресурс проверяет при каждой записи; если такого контроля нет, Redis lock не доказывает отсутствие конкурентной записи.

Failover добавляет риск: репликация Redis по умолчанию асинхронная, поэтому primary может подтвердить lock и упасть до репликации; новый primary выдаст тот же lock другому владельцу. Для некритичной дедупликации/экономии работы это иногда приемлемо. Для финансовой корректности используйте транзакцию, unique constraint или conditional update в самой БД; при строгих safety требованиях выбирайте coordinator/lock service с подходящими гарантиями и явно моделируйте отказ. Сравнение токена, TTL и требования к majority описаны в [официальном паттерне Redis locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

### Pub/Sub.
<!-- question-id: 33-redis-q09 -->

#### Ответ
Redis Pub/Sub даёт broadcast по channel или pattern: подписанные клиенты получают сообщения сразу после `PUBLISH`; это удобно для best-effort уведомлений, live fan-out и сигналов об invalidation. Подписчик не получает историю перед подключением и не подтверждает обработку сообщения.

Семантика at-most-once: если подписчик отключён, перегружен или не успевает обработать сообщение, Redis не хранит его для последующего replay. Следовательно, Pub/Sub не подходит как единственный транспорт для платежей, обязательных фоновых задач, аудита или надёжной синхронизации кэша. Для replay, pending и acknowledgement нужны Redis Streams/другая durable очередь; даже там нужно выбрать persistence, replication и idempotency, потому что доставка сообщения не равна ровно одному выполнению бизнес-эффекта.

Отдельно учитывайте operational cost fan-out: подписка на широкий pattern может размножить трафик, а медленный consumer создаёт нагрузку на соединение. Для сигналов, потеря которых допустима, добавьте восстановление состояния (например, периодическую сверку и TTL); для непропускаемых изменений публикуйте transactional outbox и используйте durable consumer.
