# Browser navigation and document parsing

## Interview questions

### Что происходит после ввода URL?
<!-- question-id: 06-browser-internals-q01 -->
#### Ответ
При типичной навигации браузер разбирает URL и политики, проверяет Service Worker и HTTP-кэш, затем при необходимости разрешает hostname, открывает или переиспользует соединение и отправляет запрос. После ответа (включая redirects) HTML parser строит DOM и обнаруживает ресурсы; браузер рассчитывает стили и геометрию, рисует и композитит кадр.

Шаги перекрываются во времени; кэш, HTTP/2/3, процессы и внутреннее устройство различаются между браузерами. Это полезная модель потока, а не обязательный одинаковый пайплайн.

### DNS lookup.
<!-- question-id: 06-browser-internals-q02 -->
#### Ответ
DNS разрешает hostname в сетевые адреса. Браузер и ОС сначала могут использовать кэш; иначе recursive resolver получает ответ через DNS-иерархию. Результатом могут быть A/AAAA, CNAME и несколько адресов; TTL задаёт кэширование, а CDN часто направляет клиента к подходящему edge.

Запрос может идти через обычный DNS либо DNS over HTTPS/TLS. При известном IP, кэшированном ответе, Service Worker или переиспользуемом соединении нового lookup может не быть. Смотрите DNS timing и фактические запросы в trace.

### TCP/TLS.
<!-- question-id: 06-browser-internals-q03 -->
#### Ответ
Для HTTP/1.1 и HTTP/2 типичный HTTPS использует TCP и TLS: TLS проверяет сертификат сервера, согласует параметры защиты и создаёт шифрованный канал; сессии и соединения могут переиспользоваться. ALPN помогает согласовать протокол приложения.

HTTP/3 работает поверх QUIC/UDP с TLS 1.3 в handshake, поэтому ему не нужен отдельный TCP-этап. Допущение: обычная современная HTTPS-навигация; proxy, VPN, resumed sessions и сетевые политики могут изменить наблюдаемый путь.

### HTTP request.
<!-- question-id: 06-browser-internals-q04 -->
#### Ответ
Запрос содержит method, path, headers, cookies и, при необходимости, тело. Браузер применяет кэш и security policies; сервер возвращает статус, заголовки и тело. Возможны redirect, cache revalidation через ETag/Last-Modified, ответ из кэша или ошибка; HTTP/2/3 меняют передачу, но не модель request/response.

Service Worker может перехватить запрос и ответить локально. CORS обычно относится к доступу скрипта к cross-origin fetch-ответу, а не к показу основного документа навигации.

### HTML parsing.
<!-- question-id: 06-browser-internals-q05 -->
#### Ответ
HTML parser работает потоково: tokenizer создаёт токены, а tree builder формирует и исправляет DOM по правилам HTML. Parser-inserted classic script без async/defer может приостановить построение дерева, пока файл загружается и выполняется: скрипт способен менять DOM или вызывать document.write.

Браузер может параллельно обнаруживать ресурсы дальше по документу, но это оптимизация реализации. Неполная или ошибочная разметка обычно не останавливает parsing: tree builder применяет правила восстановления HTML. [HTML Standard: scripting](https://html.spec.whatwg.org/multipage/scripting.html).

### DOM.
<!-- question-id: 06-browser-internals-q06 -->
#### Ответ
DOM — дерево узлов текущего документа, созданное HTML tree builder-ом и доступное через Web API; скрипты могут его менять. Оно содержит элементы, текстовые узлы и другие node types.

DOM не равен визуальному дереву: display:none-узел остаётся в DOM, а псевдоэлемент не является обычным DOM-элементом. Внутреннее представление layout/render tree может отличаться от DOM.

### CSSOM.
<!-- question-id: 06-browser-internals-q07 -->
#### Ответ
CSSOM — представление загруженных CSS rules, используемое при вычислении стилей. Браузер разбирает stylesheets, применяет media queries, cascade, inheritance и custom properties, получая computed style узлов DOM.

Таблицы стилей могут задержать первый render; stylesheet перед синхронным script может также задержать его выполнение, если скрипт читает стили. Термин CSSOM удобен как учебная модель, а внутренние структуры движков различаются.

### Render Tree.
<!-- question-id: 06-browser-internals-q08 -->
#### Ответ
Render tree — обобщённое представление визуально участвующих узлов DOM и их computed styles, из которого можно рассчитать layout. Узел с display:none обычно исключён из раскладки, тогда как visibility:hidden обычно сохраняет место; псевдоэлементы могут иметь визуальные boxes без обычного DOM-узла.

Это полезное объяснение, а не стандартизованное публичное дерево и не обещание одинаковой архитектуры всех браузеров.
