# Interfaces и отношения типов

## Interview questions

### interface vs type.
<!-- question-id: fullstack-interview-03-typescript-core-019 -->

#### Ответ

interface и type alias оба описывают структурные типы объектов и часто взаимозаменяемы. interface поддерживает declaration merging и расширение через extends, поэтому удобен для публичных расширяемых контрактов, библиотечных деклараций и augmentation. type умеет выражать union, tuple, primitive aliases, conditional/mapped types и композицию через операторные выражения. Есть различие диагностики конфликтов: при extends несовместимое переопределение обычно сразу ошибка, а при пересечении свойства пересекаются и могут стать never. Свежий object literal также проходит excess-property check в обоих случаях — это проверка на вероятную опечатку, а не exact object type. Выбор обычно определяется возможностью расширения, выразительностью и API-конвенцией.

### Declaration merging.
<!-- question-id: fullstack-interview-03-typescript-core-020 -->

#### Ответ

Declaration merging — правило, по которому некоторые повторные объявления с одним именем объединяются в одну сущность типа. Наиболее частый случай — два interface с совместимыми полями; повторное непереназначаемое поле обязано иметь тот же тип, а overload-сигнатуры функций объединяются. Это механизм для расширения типов библиотеки через module/global augmentation (например, добавить поле в Request), а не способ произвольно переопределить уже объявленное свойство. Type alias повторно объявить нельзя. Merging влияет на статические декларации и не добавляет runtime-поле или реализацию; импорт и module scope должны соответствовать реальному пакету.

### extends vs intersection.
<!-- question-id: fullstack-interview-03-typescript-core-021 -->

#### Ответ

interface A extends B явно наследует контракт и может добавлять/уточнять совместимые поля; конфликт несовместимых деклараций приводит к диагностике у объявления. type A = X & Y образует пересечение: объект должен удовлетворять X и Y одновременно. При одинаковом ключе TS пересекает типы свойств, поэтому string & number становится never и проблема иногда проявляется лишь при использовании. extends читабельнее для линейного расширения интерфейсных контрактов и ловит конфликты раньше; & гибче для generic-композиции, union-ов и alias-ов. Ни один вариант не меняет runtime-объект и оба сохраняют структурную типизацию.

### keyof.
<!-- question-id: fullstack-interview-03-typescript-core-022 -->

#### Ответ

keyof T строит union ключей T, пригодный для generic-доступа и mapped types. Для { id: string; active: boolean } это "id" | "active"; сочетание T[K] затем извлекает тип выбранного поля, а ограничение K extends keyof T гарантирует допустимый ключ. При string index signature результат расширяется до string | number (JavaScript приводит числовые ключи объектов к строкам); у массива появляются числовой индекс и методы, у tuple — конечный union индексов и строковых имён. keyof union требует осторожности: безопасные общие ключи для union могут сузиться, тогда как keyof intersection обычно объединяет доступные ключи. Проверяйте нужную семантику на требуемом TS target и не трактуйте keyof как список runtime-свойств.
