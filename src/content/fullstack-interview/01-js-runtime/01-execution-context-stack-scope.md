# Execution context, stack и scope

## Interview questions

### Что происходит при выполнении JavaScript-файла?
<!-- question-id: fullstack-interview-01-js-runtime-001 -->

#### Ответ

Вызов JavaScript-файла проходит через несколько уровней, и детали зависят от host-среды. Сначала браузер или Node.js загружает модуль/скрипт и передаёт исходный текст движку. Движок разбирает синтаксис, строит внутреннее представление (обычно AST), проверяет ошибки, затем интерпретирует код и/или компилирует горячие участки в машинный код. Конкретная стратегия — деталь реализации V8, SpiderMonkey и других движков.

Перед выполнением создаётся global execution context либо module context. Для модулей связываются импорты и экспорты; их код выполняется в strict mode, а top-level bindings не становятся свойствами global object. Затем выполнение синхронно идёт по стеку вызовов. Синтаксис `async`, `await`, `Promise`, `setTimeout` сам по себе не означает, что весь файл исполняется параллельно: асинхронность координирует host и очередь задач. Наконец, приложение не должно полагаться на точное число стадий JIT или внутреннее устройство движка — это не контракт языка.

### Что такое Execution Context?
<!-- question-id: fullstack-interview-01-js-runtime-002 -->

#### Ответ

Execution Context — спецификационное понятие, описывающее состояние, необходимое для выполнения кода. Упрощённо в нём есть текущая область лексических привязок, окружение для `var`/функций и информация о вызываемой функции, `this` и точке продолжения. При вызове функции создаётся новый context; при возврате управление продолжает предыдущий. В реализации это состояние может быть оптимизировано и не обязано буквально соответствовать отдельному объекту в памяти.

Удобно различать global/script или module context и function context. Function declarations и `var` исторически инициализируются иначе, чем `let`/`const`: последние существуют в лексическом окружении, но недоступны до инициализации (temporal dead zone). Замыкание может удерживать нужные bindings после возврата функции; движок вправе оптимизировать хранение, пока поведение остаётся эквивалентным.

Важно не смешивать execution context с lexical environment или call stack: context — более широкое состояние выполнения; environment описывает разрешение имён; stack — упорядоченная модель активных синхронных вызовов. Детали наподобие «сначала фаза создания, потом фаза исполнения» — полезная учебная модель, а не два самостоятельных наблюдаемых прохода, буквально выполняемых всеми движками.

### Что такое Call Stack?
<!-- question-id: fullstack-interview-01-js-runtime-003 -->

#### Ответ

Call Stack — модель LIFO для активных синхронных вызовов. Вход в функцию добавляет её execution context поверх стека, `return` или исключение снимает его и возобновляет вызывающий код. Поэтому вложенные вызовы выполняются до возврата из вызывающего, а обычный JavaScript в одном agent не прерывается другим callback посреди инструкции.

Рекурсия без условия остановки и чрезмерная глубина вызовов исчерпывают доступный стек и приводят к `RangeError: Maximum call stack size exceeded` (текст зависит от движка). Это отличается от долгого цикла: он может не переполнить стек, но всё равно блокирует поток и интерфейс. Асинхронное продолжение обычно начинает новый turn и не сохраняет весь прежний синхронный стек; async stack traces в DevTools — диагностическое представление, а не гарантия сохранения стекового кадра.

На сервере CPU-heavy синхронный обработчик задерживает другие запросы на том же event loop. Практические меры — ограничивать входные размеры/глубину рекурсии, превращать рекурсивный обход в итеративный, а тяжёлые вычисления выносить в Worker/worker thread или дробить на кооперативные порции.

### Что такое Lexical Environment?
<!-- question-id: fullstack-interview-01-js-runtime-004 -->

#### Ответ

Lexical Environment — спецификационная структура, которая связывает имена переменных с их значениями или состоянием и указывает на внешнее лексическое окружение. Именно лексическая структура кода определяет, какую привязку найдёт обращение к имени; она не меняется от того, через какой объект вызвали функцию. При входе в блок могут появиться bindings `let` и `const`, а при вызове функции — параметры и локальные bindings.

Лексическая среда не равна объекту, доступному из JavaScript, и не обязательно физически материализуется в таком виде. Для замыкания движок сохраняет только то состояние, которое необходимо для наблюдаемого поведения. `var` имеет function/global scope, тогда как `let`/`const` имеют block scope и TDZ до выполнения декларации. Module bindings также лексические и не добавляются как свойства `globalThis`.

Свойства объектов и лексические bindings — разные пространства имён: например, присваивание `obj.x` не меняет локальную переменную `x`. Понимание этого помогает объяснять shadowing, closures и отличие `this` от lexical scope.

### Как работает scope chain?
<!-- question-id: fullstack-interview-01-js-runtime-005 -->

#### Ответ

При разрешении идентификатора движок сначала ищет binding в текущем лексическом окружении, затем переходит по ссылкам к внешним lexical environments, пока не найдёт имя или не дойдёт до верхнего окружения. Ближайший binding побеждает: это shadowing. Если имя не найдено, возникает `ReferenceError` (за исключением особых механизмов host/global scope).

Связи формируются лексически — по месту объявления функции, а не по месту её вызова. Поэтому функция, переданная как callback из другого модуля, продолжает видеть окружение, в котором была создана. Это основа closure. `this` разрешается отдельными правилами вызова и не является следующей ступенью scope chain.

`let`/`const` в блоке затеняют внешнее имя и до инициализации находятся в TDZ; доступ к затенённой переменной не «провалится» к внешнему binding, а выбросит ошибку. Статические проверки вроде ESLint/TypeScript помогают обнаруживать случайное затенение, а явные имена и небольшие области видимости уменьшают риск логических ошибок.
