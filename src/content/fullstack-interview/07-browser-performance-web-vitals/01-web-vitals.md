# Web Vitals

## Interview questions

### LCP.
<!-- question-id: 07-browser-performance-web-vitals-q01 -->
#### Ответ

Largest Contentful Paint показывает, когда в видимой области отрисован самый крупный контентный элемент, который пользователь, вероятно, воспринимает как основное содержимое: обычно это изображение, poster видео или крупный текстовый блок. Это не событие «страница полностью загрузилась»: пока пользователь не взаимодействовал со страницей, кандидат может меняться, когда появляется более крупный элемент. Метрика зависит и от документа, и от ресурса, и от момента, когда браузер может его отрисовать.

Для полевой оценки используйте p75 загрузок, отдельно как минимум для mobile и desktop: ориентиры web.dev, обновлённые 7 мая 2025 года, — good ≤ 2,5 с, needs improvement 2,5–4 с, poor > 4 с. Один Lighthouse-прогон или среднее по сайту не заменяет это распределение. Данные CrUX охватывают только подходящие по трафику Chrome-опыты; собственный RUM нужен, чтобы сегментировать по URL/шаблону, устройству, сети, авторизации и определить конкретный LCP-элемент.

Для диагностики разбейте LCP на TTFB, задержку обнаружения ресурса, его загрузку и задержку от готового ресурса до отрисовки. Это помогает выбрать причину, а не оптимизировать наугад: например, большой интервал до запроса hero-изображения указывает на позднее обнаружение из CSS или JavaScript; длинный download — на размер/сеть; render delay — на блокирующий CSS, занятый main thread или позднее появление DOM. Проверьте waterfall и trace, затем подтвердите изменение в поле. Не применяйте `loading="lazy"` к вероятному LCP-изображению; `preload` и `fetchpriority="high"` оправданы только для действительно критического ресурса и после измерения. [Определение и разложение LCP](https://web.dev/articles/optimize-lcp), [пороговые значения CWV](https://web.dev/articles/defining-core-web-vitals-thresholds).

### CLS.
<!-- question-id: 07-browser-performance-web-vitals-q02 -->
#### Ответ

Cumulative Layout Shift измеряет неожиданное смещение уже видимых элементов между кадрами. Оценка отдельного сдвига — произведение impact fraction (какую часть viewport затронуло перемещение) на distance fraction (насколько далеко сдвинулся самый подвижный элемент). Добавление элемента само по себе не считается сдвигом, но если оно толкает существующий текст или кнопку, их перемещение попадёт в метрику. Сдвиг после явного действия пользователя может быть ожидаемым; API помечает дискретное действие, случившееся в пределах 500 мс, флагом `hadRecentInput`, а непрерывный scroll таким действием не считается.

Текущий CLS — не сумма за всю жизнь вкладки, а максимальная сумма в session window: сдвиги объединяются при промежутках менее секунды, окно ограничено пятью секундами. Это особенно важно для SPA, лент и страниц, которые долго остаются открытыми. По официальным ориентирам web.dev p75 должен быть ≤ 0,1; > 0,25 — poor; между значениями нужно улучшение. CLS — безразмерная величина, её нельзя трактовать как время.

В поле группируйте данные по странице и сегменту, а в RUM сохраняйте источник/элементы сдвига и сценарий пользователя. Частые причины — изображения, iframe и реклама без зарезервированного размера, поздний контент, шрифтовый swap. Лабораторный отчёт часто покрывает лишь загрузку и может пропустить сдвиг после async-запроса, scroll или открытия виджета. Есть и граница измерения: Layout Instability API не отдаёт родительской странице сдвиги внутри iframe, хотя пользователь их видит; из-за этого CrUX и собственный RUM могут различаться. [Определение, исключения и измерение CLS](https://web.dev/articles/cls), [пороговые значения](https://web.dev/articles/defining-core-web-vitals-thresholds).

### INP.
<!-- question-id: 07-browser-performance-web-vitals-q03 -->
#### Ответ

Interaction to Next Paint оценивает отзывчивость всей страницы на протяжении посещения: измеряет задержку взаимодействий click, tap и keypress от начала жеста до кадра, в котором браузер может показать визуальный результат. Это не среднее время всех обработчиков и не время до полной готовности приложения. Для одного взаимодействия важны три участка: input delay до запуска обработчиков, processing duration самих обработчиков и presentation delay до следующего кадра. Поэтому одинаковый INP может требовать разных исправлений: разделить длинную задачу до обработчика, уменьшить работу обработчика либо сократить вычисления/layout/paint после него.

Обычно берётся самое медленное взаимодействие страницы; при большом их числе реализация отбрасывает по одному наибольшему на каждые 50 взаимодействий, чтобы единичная случайная задержка меньше искажала результат. Итоговый порог оценивают по p75 полевых page views, отдельно для mobile и desktop: ≤ 200 мс — good, > 500 мс — poor, промежуток требует улучшения. Это ориентиры, не SLA для каждой сессии. INP не учитывает hover, scroll и zoom, хотя эти действия всё равно могут быть важны для UX.

Для полевого расследования сохраните URL/route, тип и имя взаимодействия, его длительность и сегменты устройства/браузера; один агрегированный INP не показывает проблемную кнопку. Затем воспроизведите пользовательский сценарий в Performance panel, разложите задержку на три участка и найдите конкретный длинный обработчик, пересчёт layout или конкурирующий скрипт. RUM и лаборатория дополняют друг друга: лабораторный прогон воспроизводим, но не знает всех реальных устройств и сценариев; CrUX может показать регрессию, но обычно не объяснит её причину. [INP: определение, агрегация и ограничения](https://web.dev/articles/inp), [официальные пороги](https://web.dev/articles/defining-core-web-vitals-thresholds).

### TTFB.
<!-- question-id: 07-browser-performance-web-vitals-q04 -->
#### Ответ

Time to First Byte — время от начала navigation request до получения браузером первого байта ответа. Это сигнал ранней части критического пути, а не чистое время вычисления backend: на него влияют redirect, DNS/TLS/соединение, сеть, edge/cache, очередь и обработка на сервере. Высокий TTFB сдвигает FCP и LCP, но один этот показатель не говорит, какой именно слой медленный.

TTFB не входит в текущие Core Web Vitals. В качестве грубого ориентира web.dev приводит ≤ 0,8 с как good и > 1,8 с как poor, но прямо подчёркивает зависимость от архитектуры. Для client-rendered SPA быстрый HTML важен, чтобы раньше начать загрузку JavaScript и рендер; у SSR-страницы с готовым содержимым умеренно более высокий TTFB иногда сочетается с лучшими FCP/LCP, чем очень быстрый пустой shell.

Сравните field и lab, сегментируйте по route, региону, CDN/cache-hit, типу навигации и сети. В trace/Resource Timing отделите время до запроса, ожидание ответа и загрузку; `Server-Timing` помогает связать клиентский запрос с backend-операциями. Измеряйте итоговый LCP/FCP и пользовательский опыт: снижение TTFB за счёт дорогого SSR или отказа от полезного кеширования может ухудшить TTFB latency/cost trade-off, не улучшив отображение контента. [Рекомендации по TTFB](https://web.dev/articles/optimize-ttfb).

### FCP.
<!-- question-id: 07-browser-performance-web-vitals-q05 -->
#### Ответ

First Contentful Paint — время от навигации до первого отображения любого контента страницы: текста, изображения, SVG или непустого canvas. Он отвечает на вопрос «пользователь уже видит хоть что-то?», а не «появилось ли главное содержимое?» — за последнее лучше отвечает LCP. FCP включает задержки предыдущей навигации, установки соединения, redirect и TTFB, поэтому его нельзя автоматически приписывать frontend-коду.

По ориентирам web.dev p75 ≤ 1,8 с считается good, > 3 с — poor; измерять стоит отдельно mobile/desktop и по реальным page views. FCP полезен как ранний диагностический сигнал и не является одним из трёх текущих Core Web Vitals. Хороший FCP при плохом LCP часто означает, что shell/placeholder уже показан, но основное изображение или контент поздно загружается/рендерится. Обратная ситуация требует проверки определения и состава метрик, а не предположения, что показатель ошибочен.

Сопоставьте FCP с LCP и этапами waterfall: проблема до FCP чаще указывает на navigation/TTFB, блокирующие CSS или начальный render path; разрыв FCP→LCP направляет поиск к главному контенту. Lab-прогон удобен для повторяемой диагностики, но для целей UX ориентируйтесь на полевые распределения и реальные сегменты. [FCP: определение и ограничения](https://web.dev/articles/fcp), [пороговые значения CWV](https://web.dev/articles/defining-core-web-vitals-thresholds).

### Что раньше означал FID?
<!-- question-id: 07-browser-performance-web-vitals-q06 -->
#### Ответ

First Input Delay измерял задержку только первого подходящего дискретного действия (click, tap или keypress): от получения события браузером до момента, когда main thread смог начать его обработку. Типичная причина высокого FID — главный поток занят загрузкой, parsing или исполнением JavaScript. Метрика не включала длительность самого event handler и время до следующего кадра, поэтому могла быть хорошей, даже если интерфейс после клика долго не обновлялся.

12 марта 2024 года INP официально заменил FID в Core Web Vitals; с сентября 2024 года Chrome прекратил поддержку FID в своих performance-инструментах. FID полезен как исторический термин и для чтения старых дашбордов, но для текущей диагностики отзывчивости он неполон. INP смотрит взаимодействия на всём протяжении посещения и учитывает задержку до следующего кадра, поэтому лучше выявляет медленные действия уже после загрузки. [Объявление о замене FID на INP](https://web.dev/blog/inp-cwv-march-12), [что именно измерял FID](https://web.dev/articles/fid), [завершение поддержки в Chrome](https://web.dev/blog/fid).

### Что такое long task?
<!-- question-id: 07-browser-performance-web-vitals-q07 -->
#### Ответ

По Long Tasks API W3C long task — работа UI thread длительностью не менее 50 мс. Определение включает event-loop task вместе с ближайшим microtask checkpoint, шаг обновления rendering или работу браузера на UI thread между такими шагами. Пока main thread занят, он не может своевременно обработать ввод и выполнить следующий кадр, что создаёт input delay, пропуск кадров и часть причин плохого INP.

Порог 50 мс — диагностическая граница API, а не обещание, что задача длительностью 49 мс безвредна или что любой long task обязательно приводит к плохому INP. Серия меньших работ, конкуренция с рендером и конкретное время взаимодействия тоже имеют значение; наоборот, задача может быть долгой, когда пользователь не пытается взаимодействовать. Смотрите на частоту, суммарный blocking time, источник и связь со trace/реальными медленными действиями, а не только на число записей.

Исправления — убрать ненужную работу, делить вычисления на порции с yield, переносить подходящие вычисления в Web Worker, отложить необязательные задачи и оптимизировать конкретный обработчик. Слишком агрессивное дробление тоже имеет overhead, а перенос работы в worker добавляет сериализацию/обмен сообщениями, поэтому подтвердите выигрыш профилем и полевым INP. [Спецификация W3C Long Tasks API](https://www.w3.org/TR/longtasks-1/).
