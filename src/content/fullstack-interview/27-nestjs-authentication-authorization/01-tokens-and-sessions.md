# Tokens and Sessions

## Interview questions

### Authentication vs authorization.
<!-- question-id: 27-nestjs-authentication-authorization-q01 -->

#### Ответ

**Authentication** отвечает на вопрос «кто выполняет запрос»: приложение проверяет пароль, passkey, внешний identity provider или уже предъявленную сессию и связывает запрос с доверенным principal (например, userId, tenantId, sessionId). **Authorization** отвечает на вопрос «что этому principal разрешено сделать с конкретным ресурсом сейчас». Эти задачи независимы: валидная личность не означает разрешение на любой endpoint или объект.

В HTTP обычно различают 401 Unauthorized — credentials отсутствуют или недействительны (для bearer-схемы сервер также должен сообщить challenge через WWW-Authenticate) — и 403 Forbidden — личность распознана, но политика запрещает действие. Для чувствительных ресурсов допустимо отвечать 404, чтобы не раскрывать существование объекта. Проверку прав нужно делать не только по роли на контроллере, но и по конкретной записи и операции; например, при чтении заказа фильтровать выборку по tenant/user, а не загружать чужую запись и полагаться на UI.

### JWT.
<!-- question-id: 27-nestjs-authentication-authorization-q02 -->

#### Ответ

JWT — компактный формат утверждений (claims), сериализованных как header, payload и signature. В типичном JWS подпись подтверждает целостность и издателя, но **не шифрует** payload: любой обладатель токена может его декодировать. Поэтому туда не кладут пароли, секреты и лишние персональные данные; для конфиденциальности нужен отдельный механизм шифрования, но для обычной API-аутентификации чаще лучше минимизировать claims.

Сервер не должен доверять payload до проверки подписи. При валидации фиксируют допустимый алгоритм и ключ, проверяют iss, aud, exp, при использовании — nbf, а также назначение токена: access token одного сервиса нельзя принимать как ID token или как токен другой API. Это следует из JWT Best Current Practices (RFC 8725): не выбирать алгоритм по неподтверждённому заголовку, разделять ключи/контексты и корректно обрабатывать kid. Ключи берут из secret manager/KMS, умеют ротировать с коротким периодом перекрытия ключей проверки, старый удаляют после максимального TTL токенов.

JWT удобен для локальной проверки несколькими сервисами без обращения к центральной сессии, но он не является автоматически безопасной или «полностью stateless» архитектурой: отзыв, смена прав и обнаружение компрометации требуют отдельной стратегии. Подписанные JWT обычно используют как короткоживущие bearer credentials только по TLS; утечка токена равна возможности действовать от имени пользователя до истечения или отзыва.

### Access token.
<!-- question-id: 27-nestjs-authentication-authorization-q03 -->

#### Ответ

Access token предъявляется API в Authorization: Bearer … и дает ограниченный доступ на ограниченное время. В claims обычно достаточно стабильного subject (sub), issuer/audience, времени жизни и, если архитектуре действительно нужно, узких scopes/tenant context. Сервер все равно проверяет актуальные объектные права: роль или scope в старом токене не должны обходить проверку владения конкретным ресурсом.

TTL выбирают как баланс между частотой обновления и окном ущерба при краже. Чем выше риск операции, тем разумнее короткая жизнь токена и дополнительная проверка (step-up/MFA), а не только увеличение набора claims. Bearer token нужно передавать по TLS, не писать в URL, логи, аналитику и ошибки. В браузере хранение в localStorage подвергает токен краже при XSS; хранение в памяти сокращает персистентность, но не спасает от действующего XSS. Для web-приложения часто безопаснее BFF, который держит токен на сервере и выдает браузеру только cookie с защищенной сессией.

Access token не следует использовать как refresh token. Его проверка в Nest guard/Passport strategy должна завершаться формированием минимального request principal, а endpoint возвращает только разрешенные клиенту данные, не весь payload и не внутренние claims.

### Refresh token.
<!-- question-id: 27-nestjs-authentication-authorization-q04 -->

#### Ответ

Refresh token предназначен только для получения нового access token и обычно живет дольше. Для server-side web-сессии практичный вариант — криптографически случайный непрозрачный секрет, а не JWT: сервер хранит его хеш и запись о пользователе, token family, сроках и состоянии. Хеш защищает базу при утечке; сам refresh token должен быть недоступен JavaScript, если он хранится в браузере — HttpOnly, Secure, узкий Path, обоснованный SameSite, плюс CSRF-защита для state-changing запросов.

При refresh сервер атомарно проверяет, что токен активен, не истек и принадлежит ожидаемому клиенту/сессии, затем инвалидирует его и выдает следующий токен той же family. Абсолютный и неактивный TTL ограничивают длительность сессии. Logout, смена пароля, блокировка аккаунта и подозрение на компрометацию должны позволять отозвать family на сервере.

Есть важный edge case: два параллельных запроса могут попытаться обновить один токен. Без координации второй запрос будет выглядеть как replay и может отозвать всю family. Клиенту стоит сериализовать refresh; на сервере переход состояния должен быть атомарным, а допустимое короткое окно повтора (если оно вообще нужно) проектируют осторожно, потому что оно расширяет возможности атакующего.

### Rotation.
<!-- question-id: 27-nestjs-authentication-authorization-q05 -->

#### Ответ

Для refresh-token rotation каждый успешный refresh выдает новый одноразовый токен и делает предыдущий недействительным. На сервере нужно хранить связь токенов в family и атомарно выполнить «проверить active → пометить consumed → создать successor»; иначе конкурентные запросы могут породить две действующие ветки. Если уже использованный токен предъявлен снова, это сигнал возможного копирования: отзывают соответствующую family, фиксируют security event и предлагают повторную аутентификацию. Простая выдача нового токена без инвалидирования старого не является rotation.

Политика повтора — осознанный trade-off: потерянный ответ после успешной ротации может заставить легитимного клиента повторно отправить старый токен. Grace period или idempotent refresh result улучшают восстановление, но смягчают replay detection; их ограничивают конкретной сессией/операцией и проверяют повторную идентичность запроса. На клиенте объединяют параллельные refresh-запросы, а не запускают их из каждого API-вызова независимо.

Отдельно ротируют **ключи подписи JWT**: новые токены подписывают новым kid, verifier временно принимает новый и предыдущие ключи, затем удаляет старый после истечения максимального TTL ранее выданных токенов. Это не заменяет refresh-token rotation и не отзывает автоматически уже выпущенные токены.

### Token revocation.
<!-- question-id: 27-nestjs-authentication-authorization-q06 -->

#### Ответ

У подписанного JWT нет встроенного механизма немедленного отзыва: если подпись и claims валидны, автономный verifier примет его до exp. Компромиссные варианты — короткий TTL access token, список отзыва по jti, версия сессии/учетной записи, introspection или проверка состояния session record. Первые подходы добавляют состояние и сетевую/кеш-зависимость в каждый запрос; короткий TTL уменьшает, но не устраняет окно доступа.

Refresh token отзывается проще: сервер инвалидирует его запись или всю family, поэтому следующая попытка обновления не пройдет. Для особо чувствительных операций проверка статуса сессии/аккаунта должна видеть актуальное состояние (с понятным поведением при недоступности хранилища); для обычного чтения можно применять короткий кэш с принятым окном eventual consistency. Logout на одном устройстве обычно отзывает одну сессию, logout everywhere, password reset и disable account — все сессии/refresh families.

Отзыв должен быть наблюдаемым и безопасным: аудит хранит субъект, время и причину без записи токенов; denylist имеет TTL не длиннее токена, а сравнение токенов выполняется по идентификатору/хешу, не по открытым секретам.

### Session vs JWT.
<!-- question-id: 27-nestjs-authentication-authorization-q07 -->

#### Ответ

В cookie-based session браузер хранит случайный session ID, а состояние пользователя и срока жизни — на сервере (например, Redis или БД). Это упрощает немедленный logout, отзыв, смену ролей и ограничение числа устройств; горизонтальное масштабирование требует общего отказоустойчивого store, настройки TTL, очистки и защиты от session fixation. Cookie автоматически прикладывается браузером, поэтому нужны Secure, HttpOnly, подходящий SameSite и CSRF-защита.

JWT access token проверяется локально по подписи, поэтому API-инстансам не обязательно читать session store на каждом запросе; это снижает связность и может быть полезно для сервисных API. Цена — сложнее мгновенно отзывать токены, claims устаревают до истечения, а ключи, issuer/audience, ротация и clocks становятся частью security boundary. JWT может быть больше session ID и чаще попадает в логи, если не настроить redaction.

Это не выбор «modern vs legacy». Для web/BFF с серверным контролем сессий opaque session ID часто проще и безопаснее; для распределенных API короткоживущий JWT может быть удобен, если принят риск окна отзыва. Возможна комбинация: browser session cookie на BFF, а BFF обменивает ее на краткоживущий audience-restricted token для внутреннего API. Независимо от механизма authorization все равно проверяется на сервере для каждого ресурса и действия.
