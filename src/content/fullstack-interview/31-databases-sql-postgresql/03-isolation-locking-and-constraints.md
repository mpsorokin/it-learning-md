# Isolation, Locking, and Constraints

## Interview questions

### Dirty read.
<!-- question-id: 31-databases-sql-postgresql-q21 -->

#### Ответ

Dirty read — чтение транзакцией значения, записанного другой еще не завершенной транзакцией; если writer откатится, reader увидел бы значение, которого никогда не было в committed состоянии. PostgreSQL MVCC не допускает dirty reads ни на одном уровне: запрошенный READ UNCOMMITTED реализуется как READ COMMITTED.

При Read Committed запрос видит только данные, committed до начала его snapshot; при Repeatable Read/Serializable используется более стабильный snapshot. Это не значит, что все конкурентные аномалии невозможны: например, Read Committed допускает non-repeatable read и write skew; их регулируют явной блокировкой, ограничением данных или уровнем изоляции.

### Non-repeatable read.
<!-- question-id: 31-databases-sql-postgresql-q22 -->

#### Ответ

Non-repeatable read: одна транзакция дважды читает одну и ту же существующую строку, но между чтениями другая транзакция обновляет ее и фиксирует изменения. Например, первая читает баланс 100, другая коммитит 80, первая снова читает и получает 80. Это не dirty read: второй результат committed.

В PostgreSQL это возможно при Read Committed, поскольку каждый statement берет новый snapshot; Repeatable Read и Serializable сохраняют snapshot для транзакции и не показывают такие внешние изменения. Если решение основано на прочитанном значении, не ограничивайтесь двумя SELECT: используйте атомарный conditional UPDATE, row lock/версию, constraint или Serializable с retry — в зависимости от инварианта и желаемой конкуренции.

### Phantom read.
<!-- question-id: 31-databases-sql-postgresql-q23 -->

#### Ответ

Phantom read происходит, когда повторный predicate query в той же транзакции возвращает новый набор строк из-за concurrently committed INSERT/UPDATE, который начал соответствовать условию. Например, транзакция повторно читает все активные резервы пользователя, а параллельная добавляет новую подходящую строку. Это изменение набора, в отличие от non-repeatable read одной ранее прочитанной строки.

В PostgreSQL Repeatable Read сильнее минимального SQL-standard требования: snapshot не показывает phantom rows, созданные после начала транзакции. Но это не делает уровень Serializable: остаются serialization anomalies, например write skew через разные строки. Serializable SSI запрещает несериализуемые committed результаты, но может прервать транзакцию, поэтому приложение повторяет ее целиком. [Поведение уровней PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html)

### MVCC.
<!-- question-id: 31-databases-sql-postgresql-q24 -->

#### Ответ

MVCC (multi-version concurrency control) хранит версии строк вместо того, чтобы читать всегда одну изменяемую копию. Каждое statement/transaction имеет snapshot, по которому определяет, какие tuple versions видимы с учетом commit-ов, transaction IDs и собственных изменений. UPDATE обычно создает новую версию; старую нельзя удалить, пока ее еще могут видеть активные snapshots.

Преимущество — обычные чтения не берут блокировки строк, конфликтующие с row updates, поэтому читатель и writer часто не блокируют друг друга. Это не означает отсутствия блокировок: writers конфликтуют на строках, DDL может ждать table locks, а долгие транзакции задерживают очистку старых версий. Autovacuum/VACUUM освобождают место для повторного использования и поддерживают статистику/visibility map; при долгом idle-in-transaction или replication slot растут dead tuples/bloat и нагрузка. Мониторьте возраст транзакций, vacuum progress, dead tuples и задержку реплик. [MVCC в PostgreSQL 18](https://www.postgresql.org/docs/18/mvcc-intro.html)

### Locks.
<!-- question-id: 31-databases-sql-postgresql-q25 -->

#### Ответ

PostgreSQL автоматически берет table-level locks для совместимости DDL/DML и row-level locks для конфликтующих изменений; приложение может запросить row lock через SELECT FOR UPDATE/SHARE и варианты NO KEY. Row lock удерживается до конца транзакции или отката к savepoint; он блокирует конкурирующие writers/lockers этой строки, но обычный SELECT по MVCC обычно продолжит чтение старой видимой версии.

Явные locks нужны, когда инвариант нельзя выразить атомарным UPDATE или constraint-ом; чаще применяют наиболее узкую блокировку и короткую транзакцию. SELECT FOR UPDATE резервирует уже существующие найденные строки, но не является универсальной блокировкой всех будущих строк по predicate. Advisory locks подходят для application-defined key, но их границы, namespace, единичность и освобождение становятся обязанностью приложения. Для диагностики смотрят pg_locks и блокирующие PID. [Explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html)

### Deadlock.
<!-- question-id: 31-databases-sql-postgresql-q26 -->

#### Ответ

Deadlock — цикл ожидания: транзакция A держит ресурс, нужный B, а B держит ресурс, нужный A. Пример: A обновляет inventory для товара X, затем Y; B — сначала Y, затем X. Ни одна не может продолжить. PostgreSQL детектирует цикл и прерывает одну транзакцию с deadlock detected (обычно SQLSTATE 40P01); выбранная жертва может зависеть от момента обнаружения.

Основная профилактика — во всех code paths захватывать несколько строк в стабильном порядке (например, sort by primary key), держать транзакции короткими, не делать network wait с удерживаемыми locks и индексировать запросы, уменьшая время блокировки. Логируйте deadlock details и строьте метрики по SQLSTATE; при retry повторите всю транзакцию с bounded exponential backoff, если операция идемпотентна/защищена ключом. Retry — резервная обработка, а не замена согласованному порядку.

### Optimistic locking.
<!-- question-id: 31-databases-sql-postgresql-q27 -->

#### Ответ

Optimistic locking предполагает, что конфликт редок: запись выполняется с проверкой версии, полученной при чтении. Типичный вариант — столбец version, который увеличивается при каждом изменении; UPDATE с WHERE id = … AND version = … должен вернуть ровно одну строку. Ноль строк означает удаление или конкурентное изменение, и приложение отвечает конфликтом (например, 409/412), перечитывает данные и решает конфликт, а не молча перетирает чужую запись.

Критично, чтобы чтение версии и compare-and-swap были частью одного атомарного UPDATE или корректной транзакции; сначала прочитать, затем без version predicate обновить — не optimistic locking. Ограничение версии защищает lost update, но не любая межстрочная бизнес-аномалия; для нее могут потребоваться constraint, блокировка или Serializable. В UI обычно показывают свежие данные и просят повторно подтвердить конфликт, а автоматическое merge допустимо только для независимых полей.

### Pessimistic locking.
<!-- question-id: 31-databases-sql-postgresql-q28 -->

#### Ответ

Pessimistic locking заранее берет lock, ожидая, что конфликт вероятен и критическую секцию нужно сериализовать. Для существующего ресурса в PostgreSQL можно в короткой транзакции выполнить SELECT … FOR UPDATE, проверить актуальные значения и обновить их до commit. Конкурирующий locker/writer дождется окончания; при необходимости NOWAIT превращает ожидание в мгновенный конфликт, SKIP LOCKED подходит для независимых задач очереди, но не для чтения полного бизнес-состояния.

Цена — блокировки, очереди ожидания, lock contention и deadlock; нельзя держать lock во время пользовательского/сетевого ожидания. Row lock покрывает найденные существующие строки, но не абстрактное условие и будущие строки. Поэтому выберите constraint/advisory/predicate strategy, когда блокировка только row не обеспечивает инвариант. Учитывайте, что Repeatable Read/Serializable могут вместо обновления изменившейся после snapshot строки вернуть serialization failure.

### Constraints.
<!-- question-id: 31-databases-sql-postgresql-q29 -->

#### Ответ

Constraint — декларативный инвариант, который PostgreSQL проверяет независимо от того, пришло ли изменение из API, фоновой задачи или ручного SQL. NOT NULL и CHECK валидируют значения строки; PRIMARY KEY обеспечивает идентичность и уникальность; UNIQUE запрещает дубликаты в заданном ключе; EXCLUDE поддерживает запрет конфликтующих пар для выбранных операторов/типов. Ограничения защищают и от гонок, которые невозможно надежно закрыть предварительным SELECT на уровне приложения.

Важные edge cases: CHECK считается прошедшим также при результате NULL, поэтому для required field нужен еще NOT NULL; UNIQUE по умолчанию допускает несколько NULL значений (в PG15+ можно явно использовать NULLS NOT DISTINCT, если это контракт). Для связанных бизнес-правил нужно понять, допустим ли DEFERRABLE constraint, проверяемый на commit, а не при каждой команде. Объявляйте корректную семантику на уровне БД и переводите ожидаемые unique/check violations в стабильную доменную ошибку; не раскрывайте клиенту внутренний SQL.

### Foreign keys.
<!-- question-id: 31-databases-sql-postgresql-q30 -->

#### Ответ

Foreign key обеспечивает ссылочную целостность: значение дочерней колонки должно ссылаться на уникальный/primary key родителя либо быть NULL, если колонка nullable. Он предотвращает orphan rows при конкурентных запросах и других писателях; приложенческий SELECT «проверить, что родитель есть» не заменяет FK. On delete/on update действие выбирается под доменную семантику: RESTRICT/NO ACTION для запрета, CASCADE только когда дочерние строки действительно являются частью жизненного цикла родителя, SET NULL — если связь необязательна.

PostgreSQL обычно создает индекс для referenced primary/unique key, но не создает автоматически индекс на referencing child columns. Такой индекс часто нужен для JOIN и чтобы удаление/обновление родителя не сканировало всю child table; выбор зависит от нагрузки и размера. В multitenant-модели можно делать составные FK/unique keys с tenant_id, чтобы даже некорректный код не связал объект с чужим tenant. Учитывайте порядок блокировок FK, большие cascade-операции и возможность DEFERRABLE constraint для циклических/пакетных изменений.
