# Keys and render updates

## Interview questions

### Почему key важен?
<!-- question-id: 08-react-rendering-model-q10 -->
#### Ответ

`key` сообщает React identity элемента среди siblings при reconciliation. Стабильный key позволяет сопоставить тот же logical item после вставки, удаления или сортировки, сохранить его component state и корректно применить host changes. Ключи должны быть уникальны в пределах siblings и стабильны во времени; глобальная уникальность не нужна.

`key` — служебная метаинформация, компонент не получает его в `props`, поэтому domain id нужно передавать отдельно. Если identity элемента меняется, измените key намеренно: это приведёт к unmount старой ветви и mount новой, вместе со сбросом state. `key={Math.random()}` ломает сопоставление на каждом render-е и пересоздаёт поддерево.

### Почему array index плохой key?
<!-- question-id: 08-react-rendering-model-q11 -->
#### Ответ

Index описывает текущую позицию, а не identity записи. При удалении или вставке посередине индексы следующих элементов сдвигаются, и React может переиспользовать state/DOM одного ряда для другого. В controlled списке это особенно опасно: открытый input, локальное состояние и focus могут оказаться у соседней записи; для uncontrolled input можно увидеть «переехавшее» значение.

Используйте стабильный id сущности как key. Index приемлем только если список статичен: порядок навсегда фиксирован, нет insert/delete/reorder, а локальный state либо отсутствует, либо его привязка к позиции намеренна. Генерировать key в render-е тоже нельзя — это эквивалент постоянной смены identity.

### Когда index допустим?
<!-- question-id: 08-react-rendering-model-q12 -->
#### Ответ

Index допустим, когда порядок массива гарантированно неизменен, элементы не добавляются/удаляются/перетасовываются, и компонент не хранит state, чья идентичность должна следовать за сущностью. Типичный пример — фиксированный перечень шагов или статический skeleton, где позиции по смыслу постоянны.

Нужно оценить не только текущий экран, но и будущие действия: фильтрация/сортировка тоже меняет позицию и делает index плохим key. Если гарантии слабые, лучше добавить stable id или использовать естественный уникальный key. Отсутствующий key заставляет React применять index-подобное сопоставление и даёт ту же проблему.

На code review важно документировать инвариант неизменного порядка; если список позже становится динамическим, key нужно пересмотреть вместе с тестом на state при reorder.

### Что происходит при изменении key?
<!-- question-id: 08-react-rendering-model-q13 -->
#### Ответ

React видит новую identity и удаляет старый компонент/subtree, затем создаёт его заново с начальным состоянием. При commit старые DOM nodes уходят, новые монтируются; эффекты прежней ветви очищаются, refs обнуляются и создаются заново. Поэтому смена key — удобный явный способ сбросить локальное состояние формы при смене сущности.

Не используйте key как обычный prop и не меняйте его случайно: input потеряет фокус/selection, сетевые подписки перемонтируются, а дорогое поддерево повторно инициализируется. Key действует в контексте siblings и позиции родителя; тот же key у другого родителя не переносит instance.

### Что вызывает rerender?
<!-- question-id: 08-react-rendering-model-q14 -->
#### Ответ

Типичные причины render-а: первоначальный mount; обновление собственного state; render родителя, который по умолчанию ведёт к вызову детей; изменение context, который читает компонент; обновление внешнего store, на который он подписан (`useSyncExternalStore`). Props сами по себе не «обновляют» компонент независимо от родителя: обычно новые props приходят при render-е владельца.

`memo`, `shouldComponentUpdate`, compiler-generated optimization и другие bailouts могут пропустить вызов при неизменных входах, но не дают абсолютной гарантии. Собственный state или используемый context всё равно способен обновить memoized component. Dev Strict Mode может вызвать pure render code дополнительно, чтобы обнаружить impure logic.

Считать нужно разные события: вызов component function, commit, DOM mutation и браузерный paint — это не одно и то же. React Profiler измеряет render commits, а console log функции может вводить в заблуждение из-за concurrent retries и Strict Mode.

### Rerender parent → что происходит с children?
<!-- question-id: 08-react-rendering-model-q15 -->
#### Ответ

Обычно React вызывает потомков, когда родитель снова render-ится, потому что им нужно проверить новый результат. Даже если потомок получил «те же» значения, функция может быть вызвана; затем reconciliation часто не найдёт host changes и DOM останется прежним.

`memo(Child)` может пропустить вызов при одинаковых props (по умолчанию сравнение каждого prop через `Object.is`), если у Child не менялись его own state/context. Новый объект/inline callback в props ломает это сравнение identity-wise. `memo` — оптимизация, а не semantic guarantee; React Compiler в некоторых конфигурациях может генерировать аналогичные оптимизации автоматически.

Сначала измерьте профилировщиком. Часто достаточно локализовать state или упростить дерево; добавление `memo` с неверным custom comparator может оставить экран со stale behavior, если comparator игнорирует prop, влияющий на обработчик.

### Значит ли rerender, что DOM обязательно изменится?
<!-- question-id: 08-react-rendering-model-q16 -->
#### Ответ

Нет. Render — вычисление React tree; commit выполняет host mutations только там, где новая структура/props требуют изменения. Компонент может быть вызван, но возвращённая разметка совпадёт и DOM mutation не понадобится. Также render может быть начат, приостановлен или отброшен без commit-а.

Даже DOM не меняется — браузерный paint не обязательно происходит. И наоборот, layout/paint могут случиться из-за CSS, размеров viewport или внешних причин без новой функции React. Поэтому «сколько render-ов» нельзя напрямую переводить в «сколько перерисовок экрана».

При измерении различайте React Profiler commit, число вызовов компонента, DOM mutation observer и browser Performance paint/layout events. Исправлять следует наблюдаемый пользовательский bottleneck, а не console count ради самого count-а.

### State update с тем же значением.
<!-- question-id: 08-react-rendering-model-q17 -->
#### Ответ

React сравнивает новое состояние с текущим через семантику `Object.is`. Если значения одинаковы, setter может полностью пропустить обновление; React вправе вызвать компонент в некоторых ситуациях, чтобы проверить результат, но потомки/commit обычно не нужны. Для примитивов это очевидно; для объектов сравнивается ссылка.

Типичная ошибка — мутировать объект и передать ту же ссылку: React может решить, что ничего не изменилось, а прошлые snapshots и memoization уже повреждены. Создавайте новый объект/массив по изменённому пути. Обратный край: новый, но структурно равный объект имеет другую identity и может инициировать render.

`Object.is(NaN, NaN)` true, а `Object.is(+0, -0)` false. В обычном UI эти числа редки, но идентичность state следует понимать точно; не используйте мутацию как способ обновления.

### Object.is в React.
<!-- question-id: 08-react-rendering-model-q18 -->
#### Ответ

Важные различия с `===`: `Object.is(NaN, NaN)` возвращает true, а `Object.is(+0, -0)` — false. Для большинства остальных примитивов и ссылок результат совпадает с strict equality. React использует Object.is-подобную проверку для bailouts setter-а и сравнения отдельных props в `memo`.

Это делает ссылочную идентичность объектов частью performance/correctness модели: мутировав тот же объект, можно скрыть обновление; создав новый объект без нужды, можно вызвать лишнюю работу. Для вложенного состояния применяют immutable update/structural sharing, чтобы менялся только путь к реально изменённому узлу.

Не следует вручную сравнивать весь объект через stringify ради повторения этой политики: это меняет семантику, дорого и не поддерживает все значения. Специальный comparator нужен только после измерений и обязан сравнивать всё, что влияет на отображение и behavior.
