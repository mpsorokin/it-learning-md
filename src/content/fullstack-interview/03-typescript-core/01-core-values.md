# Базовые типы

## Interview questions

### any — зачем существует?
<!-- question-id: fullstack-interview-03-typescript-core-001 -->

#### Ответ

any — escape hatch, который отключает статическую проверку для значения. Он нужен при поэтапной миграции JavaScript, для несовершенных типов сторонней библиотеки или на временной границе с динамическими данными. Из any разрешены произвольные чтения, вызовы и присваивания, а результат таких операций обычно снова any. Важно: any существует только для компилятора и не добавляет runtime-проверок. Для данных из сети предпочтительнее unknown плюс явная валидация; any стоит локализовать, документировать и постепенно устранять.

### Почему any опасен?
<!-- question-id: fullstack-interview-03-typescript-core-002 -->

#### Ответ

any разрывает цепочку доказательств типов: компилятор перестаёт проверять доступ к полям, сигнатуры функций и совместимость результата с дальнейшим кодом. Ошибка обнаруживается уже тестами или в production, а не в месте её возникновения. Особенно опасна протечка any через generic, массив или публичный API: один некорректно типизированный ответ библиотеки распространяет небезопасность на весь граф вызовов. Например, значение из any можно передать функции, ожидающей User, хотя ни одного обязательного поля там может не быть. Предпочтительны unknown, узкая граница приведения и runtime-схема; если any неизбежен, держать его на адаптере и сразу преобразовывать в проверенный тип.

### Что такое unknown?
<!-- question-id: fullstack-interview-03-typescript-core-003 -->

#### Ответ

unknown — безопасный верхний тип для значения, форма которого пока неизвестна. Любое значение можно присвоить в unknown, но само unknown нельзя читать, вызывать или передавать как более конкретный тип без сужения либо проверки. Например, после проверки typeof value === "string" значение можно использовать как строку. Тип не существует в сгенерированном JavaScript, поэтому при парсинге JSON он не проверяет данные сам: проверку нужно выполнить в runtime, вручную или схемой (Zod, Valibot и т. п.). Он хорошо описывает границу доверия: вход API, catch-ошибку, сообщение из очереди.

### unknown vs any.
<!-- question-id: fullstack-interview-03-typescript-core-004 -->

#### Ответ

Оба типа позволяют присвоить им любое значение, но дальнейшее использование различается. any отключает проверки в обоих направлениях: его можно присвоить конкретному типу и пользоваться как этим типом без доказательств. unknown тоже принимает любое значение, но перед чтением требует narrowing; его нельзя безопасно присвоить, например, в string. Поэтому unknown сохраняет обязательство проверить значение в точке использования, а any это обязательство стирает. Идеальная граница: внешний ввод — unknown, затем runtime validation — доменный тип; any допустим лишь как ограниченный компромисс для неконтролируемо типизированного legacy API.

### Что такое never?
<!-- question-id: fullstack-interview-03-typescript-core-005 -->

#### Ответ

never — тип значения, которое невозможно получить в корректно типизированной точке программы. Он является bottom type: совместим с любым целевым типом (поскольку значения нет), но ни одно обычное значение не присваивается never. Функция с возвращаемым типом never не завершается нормально: она бросает исключение, зацикливается или завершает процесс. В union never исчезает, поэтому он полезен как результат фильтрации и как маркер недостижимой ветви. Это не то же самое, что void: void означает, что вызывающему не обещают полезный результат, но функция может нормально завершиться.

### Где реально появляется never?
<!-- question-id: fullstack-interview-03-typescript-core-006 -->

#### Ответ

Практические появления: функция, которая всегда бросает исключение или завершает процесс, например fail(message): never; ветвь exhaustive switch после исчерпания discriminated union; типовой фильтр Exclude/Extract, где неподходящие элементы сводятся к never; и generic без допустимого кандидата. В exhaustive switch часто пишут const unreachable: never = value; если в union добавят новый вариант, присваивание перестанет компилироваться — это контроль полноты, а не runtime-проверка. В некоторых generic-контекстах (например, пустой массив без контекста) компилятор может временно вывести never[]; конкретное поведение зависит от контекста, strictness и версии TS, поэтому лучше давать явный тип, если он важен.

### void vs undefined.
<!-- question-id: fullstack-interview-03-typescript-core-007 -->

#### Ответ

void и undefined — разные по смыслу типы. undefined — конкретное runtime-значение; переменная типа undefined может содержать только его. void прежде всего используется как контракт «результат не предназначен для использования», особенно в return type функции. Функция, возвращающая void, может фактически выполнить return undefined или не иметь return; при присваивании функции с результатом в callback типа () => void вызывающая сторона обязуется игнорировать этот результат — поэтому callback, возвращающий значение, часто допустим. Но переменной void нельзя обращаться как к произвольному значению. Если API обещает именно undefined, укажите undefined; если важен только эффект вызова, используйте void.
