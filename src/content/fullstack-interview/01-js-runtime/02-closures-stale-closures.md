# Closures и stale closures

## Interview questions

### Что такое closure?
<!-- question-id: fullstack-interview-01-js-runtime-006 -->

#### Ответ

Closure — функция вместе с доступом к лексическому окружению, в котором она была создана. Это позволяет функции обращаться к внешним параметрам и локальным переменным, даже когда внешняя функция уже вернула управление. Например, фабрика может вернуть функцию-инкрементатор, которая сохраняет закрытый счётчик.

Замыкание удерживает bindings, а не обязательно снимок значений. Если binding изменяемый, последующие вызовы могут видеть его новое значение; если для каждой итерации создан отдельный binding (как `let` в цикле), каждая closure будет видеть свой. С `var` в цикле все callbacks часто разделяют одну function-scoped переменную — отсюда исторический баг с одинаковым последним индексом.

Closure естественен для callback-ов, модулей и инкапсуляции, но долгоживущий listener/timer может удерживать большой граф объектов и мешать сборке мусора. Следует отменять подписки/таймеры, где они больше не нужны, и удерживать только необходимое состояние.

### Почему closure продолжает видеть переменные после завершения функции?
<!-- question-id: fullstack-interview-01-js-runtime-007 -->

#### Ответ

Возврат из функции снимает её активный execution context со стека, но не обязан уничтожать lexical bindings, к которым всё ещё существует достижимая ссылка. Вернувшаяся функция-замыкание ссылается на окружение внешнего вызова, поэтому движок сохраняет его до тех пор, пока замыкание доступно; когда недостижимыми становятся и функция, и окружение, память может быть собрана GC.

Это модель наблюдаемого поведения, а не требование выделять объект среды на heap в каждом случае. JIT может упростить или вовсе убрать хранение, если это не меняет результат. Closure захватывает доступ к bindings: изменение переменной в том же окружении будет видно, а отдельная переменная может быть намеренно создана для фиксации значения.

В production типичная проблема не в «утечке из-за closure» как таковой, а в неожиданной достижимости: подписка на глобальный emitter, интервальный таймер или кеш удерживает функцию и всё окружение. Нужны явный lifecycle cleanup, отмена async-операций и анализ heap snapshot при доказанных утечках.

### Что такое stale closure?
<!-- question-id: fullstack-interview-01-js-runtime-008 -->

#### Ответ

Stale closure — callback, который использует binding или значение из более раннего рендера/момента, чем предполагает автор. Closure здесь работает корректно; ошибка возникает из-за lifecycle callback-а и выбранного состояния. Типичные источники — `setInterval`, DOM/event subscription, Promise callback, memoized callback или эффект с неполными dependencies.

Например, если callback создан при `count = 0`, а эффект зарегистрировал его один раз, будущие вызовы могут продолжать читать это значение. Для накопления состояния лучше использовать функциональное обновление (`setCount(c => c + 1)`), чтобы не захватывать старый `count`. Если callback должен отражать актуальные props/state, его следует пересоздавать при изменении зависимостей и корректно переподписывать, либо использовать актуальный ref/поддерживаемый React паттерн.

Нельзя автоматически добавлять все переменные в dependencies, если это создаёт цикл побочных эффектов; нужно сначала определить, какое состояние callback обязан видеть. В тестах полезно управлять таймерами и проверять последовательность нескольких обновлений, а не только первый вызов.

### Какие типичные stale-closure bugs возникают в React?
<!-- question-id: fullstack-interview-01-js-runtime-009 -->

#### Ответ

Частые случаи — эффект с интервалом или подпиской, созданный один раз и читающий устаревший state/prop; async-запрос, начатый для старого значения поиска, который завершается позже нового; и callback, зафиксированный в `useMemo`/`useCallback` с неполным dependency array. В итоге UI может обновляться из старого значения, утечёт listener, а медленный ответ перезапишет более свежий результат.

Решение зависит от нужной семантики. Для обновления на основе предыдущего state — функциональный setter. Для синхронизации эффекта с props/state — полный список dependencies и cleanup старой подписки. Для гонки запросов — `AbortController` или request-id/ignore flag в cleanup, чтобы устаревший запрос не записывал результат. `useRef` подходит для изменяемого значения, которое должно быть доступно callback-у без запуска рендера, но он не заменяет state, когда UI должен реагировать на изменение.

React Strict Mode в development может повторно запускать эффекты, помогая выявлять отсутствующий cleanup; это не означает, что production callbacks разрешено оставлять некорректными. В React 19.2+ для логики, запускаемой только из Effect и желающей читать последние committed значения без переподключения, доступен [`useEffectEvent`](https://react.dev/reference/react/useEffectEvent); это не способ скрывать настоящие dependencies.
