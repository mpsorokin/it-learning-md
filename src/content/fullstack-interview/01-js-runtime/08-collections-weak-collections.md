# Коллекции и weak collections

## Interview questions

### Object vs Map.
<!-- question-id: fullstack-interview-01-js-runtime-045 -->

#### Ответ

Обычный объект — запись со строковыми и Symbol-ключами, прототипом, property descriptors и привычной поддержкой JSON/объектного литерала. Он хорош для фиксированной структуры доменной сущности, например DTO, где поля заранее известны. Нужно учитывать inherited keys и специальные имена; для словаря без прототипа можно создать `Object.create(null)`.

`Map` — специализированная коллекция ключ-значение: ключом может быть значение любого типа, включая объект; итерация сохраняет insertion order, есть `size`, `set/get/has/delete`, а ключи не конфликтуют с именами прототипа. Он естественнее для динамических словарей и кешей. Семантика ключа объектная identity, примитивы сравниваются по SameValueZero.

`Map` не сериализуется стандартным JSON напрямую, а сравнение/копирование Map требует явной логики. Производительность зависит от движка и workload: выбирайте по модели данных и API, а не по непроверенным микро-бенчмаркам.

### Array vs Set.
<!-- question-id: fullstack-interview-01-js-runtime-046 -->

#### Ответ

Array хранит упорядоченную последовательность, допускает дубликаты, индексный доступ и операции вроде `map`, `filter`/`splice`; это подходящий выбор, когда порядок/позиция и повторяемость значимы. `Set` хранит уникальные значения по SameValueZero, поддерживает проверку membership и итерацию в порядке вставки; подходит для дедупликации и множества идентификаторов.

`Set` не индексируется по позиции и не предоставляет автоматически операций над множествами во всех целевых runtime — их можно реализовать через iterator, `has` и `add`. Удаление/поиск в массиве требуют сканирования линейно, а Set обычно оптимизирован для membership, но ECMAScript задаёт сложность лишь как в среднем лучше линейной, не конкретное O(1).

Если нужны duplicates, стабильные позиции и преобразования — Array. Если ключевой инвариант «каждое значение только один раз» и частые проверки присутствия — Set. Сложные объекты в Set сравниваются по ссылке, а не по содержимому.

### Map vs WeakMap.
<!-- question-id: fullstack-interview-01-js-runtime-047 -->

#### Ответ

`Map` сильно удерживает ключи и значения, предоставляет `size`, итерацию, `keys`/`values` и возможность перечислить/очистить записи — это удобно, когда коллекция должна быть наблюдаемой и её lifecycle контролирует приложение. Ключом может быть любой тип, а порядок итерации определён как insertion order.

`WeakMap` допускает weakly held object keys; ECMAScript 2024 разрешает также некоторые Symbols, не зарегистрированные через `Symbol.for`, но поддержку нужно проверить для target runtime. Запись WeakMap сама по себе не удерживает key. Пары работают как ephemerons: даже если value ссылается обратно на key, этот цикл, достижимый только через WeakMap, не мешает сборке key и связанного value. Но key или value всё ещё могут удерживаться другими strong references — например, если value отдельно сохранено в глобальном кеше и ссылается на key. WeakMap не итерируем, у него нет `size` и `clear`, потому что наблюдаемое перечисление сделало бы недетерминированную достижимость через GC частью API.

Выбирайте WeakMap для metadata/caches, чей срок жизни должен следовать за объектом и не нужен для перечисления; Map — когда требуется явное удаление, статистика, сериализация/экспорт или управляемый жизненный цикл.

### Set vs WeakSet.
<!-- question-id: fullstack-interview-01-js-runtime-048 -->

#### Ответ

`Set` — коллекция уникальных значений с проверкой membership, размером, удалением и итерацией; её удобно перебирать, логировать и преобразовывать. `WeakSet` содержит weakly held object values; ECMAScript 2024 разрешает также некоторые Symbols, не зарегистрированные через `Symbol.for`, но поддержку нужно проверить для target runtime. WeakSet не перечисляется, не имеет `size` и не очищается целиком. Это важно: нельзя надёжно ответить «какие элементы живы?» через WeakSet, поскольку GC недетерминирован.

WeakSet применим для дополнительной маркировки объектов (например, уже посещённые node-объекты) без продления их жизненного цикла. Он не подходит для списка активных соединений/компонентов, который нужно показывать пользователю или полностью освобождать: используйте Set и явное удаление.

Объекты сравниваются по identity. Добавление структурно одинакового, но заново созданного объекта не удаляет дубликат. При использовании для DOM-узлов учитывайте, что конкретные узлы могут сохраняться ссылками иных API, а weak-семантика касается только самой коллекции.

### Когда Map объективно лучше Object?
<!-- question-id: fullstack-interview-01-js-runtime-049 -->

#### Ответ

`Map` является более подходящим выбором, когда коллекция динамическая: нужны ключи не только string/Symbol, количество записей, частые вставки и удаления, предсказуемая итерация или пользовательские объектные ключи. У Map нет наследуемых ключей от `Object.prototype`, поэтому безопаснее принимать произвольные ключи без специальной обработки `__proto__` и `constructor`.

Для записи со стабильной схемой (`user.id`, `user.name`) объект обычно проще: естественный доступ по полям, JSON-сериализация, удобный TypeScript interface и interoperable API. `Map` требует явного сериализатора, а его ключи-объекты сравниваются по identity. Обычный объектный dictionary можно создать без прототипа, если важна совместимость с объектной формой.

Нельзя утверждать, что Map всегда быстрее: спецификация не закрепляет точную сложность операций, а движки оптимизируют оба случая. Используйте семантику и ergonomics как критерий, затем измеряйте реальные hot paths.

### Почему WeakMap полезен для caches/metadata?
<!-- question-id: fullstack-interview-01-js-runtime-050 -->

#### Ответ

WeakMap хранит metadata отдельно от самого объекта, при этом его ключ-ссылка не является самостоятельной причиной сохранить ключ от garbage collection. Например, библиотека может связать private state с объектом без добавления публичного поля и без глобального реестра, который навсегда удерживал бы все когда-либо обработанные объекты.

Также WeakMap подходит для кеша производных данных, срок жизни которых должен совпадать со сроком жизни ключевого AST/DOM node/объекта. Но результат не перечислим, поэтому нельзя строить на нём глобальный размер кеша, eviction по LRU или диагностический список. Для ограниченного кеша с eviction обычно нужен обычный Map и явная очистка.

Слабая ссылка не отменяет необходимость lifecycle design. Цикл `WeakMap → value → key` сам по себе не удерживает key: сборщик обрабатывает такую пару как ephemeron. Если же key или value достижимы по независимому strong-пути (например, из другого Map, глобального кеша или замыкания), этот путь удержит их независимо от WeakMap. Если объект нужно освободить в предсказуемый момент или перечислять кеш, явное удаление из обычного Map часто понятнее и надёжнее.
