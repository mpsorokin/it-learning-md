# Contracts and API Reliability

## Interview questions

### Validation.
<!-- question-id: 28-http-rest-api-design-q13 -->

#### Ответ
Валидация API начинается на границе доверия и выполняется на сервере, даже если клиент уже проверил форму. Разделите проверку на уровни: корректность HTTP/JSON и типов; ограничения полей (обязательность, длина, диапазон, формат); согласованность полей; доменные инварианты; право пользователя выполнить операцию над конкретным tenant/resource. Ошибки синтаксиса запроса обычно дают `400`, неподдерживаемый `Content-Type` — `415`, а синтаксически понятное содержимое, которое нельзя обработать по смыслу, может дать `422 Unprocessable Content` по [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.21). Конфликт текущего состояния часто точнее передать как `409`, а несоответствие `If-Match` — как `412`.

Валидация не заменяет ограничения хранилища. Две параллельные операции могут одновременно пройти проверку «email свободен» или «остатка достаточно»; уникальность, внешние ключи, лимиты и списание остатка должны быть защищены транзакцией/constraint-ами. Ошибки этих ограничений затем отображаются в стабильный доменный ответ, не раскрывающий SQL.

Политика неизвестных полей, null/отсутствующего поля, нормализации, округления и форматов должна быть явной. Не принимайте массовое присваивание всего JSON в модель БД: используйте DTO/allowlist writable-полей. Тестируйте граничные значения, неверную кодировку/тип, попытку изменить запрещённое поле и конкурентный конфликт; одинаковый ввод должен приводить к предсказуемому контрактному исходу.

### Error response format.
<!-- question-id: 28-http-rest-api-design-q14 -->

#### Ответ
Для API удобно стандартизировать ошибку как Problem Details по [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), обычно с `Content-Type: application/problem+json`. HTTP status остаётся главным для протокола; JSON может содержать `type` (стабильный URI вида ошибки), `title` (краткое обобщённое описание), `status`, `detail` (пояснение для этого случая) и `instance` (идентификатор конкретного инцидента/запроса). API может добавить расширения: например, список нарушений с JSON Pointer к полю, correlation ID или машинный код доменной ошибки. Для массовых ошибок сохраняйте одну общую оболочку, а расширение документируйте.

Клиент должен ветвиться по HTTP status и стабильным машинным полям, не разбирать `detail` как программу: его формулировка и язык могут измениться. `status` в теле должен соответствовать коду HTTP; при несовпадении авторитетен код ответа. Тип проблемы должен иметь стабильную семантику и при необходимости вести к документации. Формат ошибок не должен скрывать нужный `WWW-Authenticate`, `Retry-After` или другие HTTP-заголовки.

В ответ нельзя помещать stack trace, SQL, секреты, внутренние hostname, токены и чужие персональные данные. Для клиента давайте достаточно сведений, чтобы исправить запрос или понять, можно ли повторить его; детали расследования оставляйте в защищённых логах с correlation ID. Если существующая система уже имеет совместимый доменный формат, RFC 9457 не требует заменять его без причины.

### Idempotency keys.
<!-- question-id: 28-http-rest-api-design-q15 -->

#### Ответ
`Idempotency-Key` — полезный прикладной контракт для повторяемого создания/команды с побочным эффектом, например создания заказа или платежного intent. Само название заголовка не задаёт поведения в RFC 9110: API обязано описать синтаксис и предел длины ключа, область уникальности (обычно principal/tenant + endpoint/операция), retention window и ответы при повторе. Клиент генерирует случайный ключ на одну логическую операцию и повторяет именно его при сетевом таймауте; новая пользовательская операция получает новый ключ.

Сервер сохраняет ключ вместе с нормализованным отпечатком существенных параметров/тела и состоянием операции. Первое выполнение атомарно резервирует ключ; конкурентный дубликат не должен запустить вторую операцию. При том же ключе и том же запросе сервер возвращает сохранённый результат либо текущее состояние незавершённой операции. Тот же ключ с другим payload следует отклонить как конфликт, например `409`, а не молча применить новый запрос. Не включайте в fingerprint нестабильные transport-заголовки; включайте всё, что меняет смысл команды.

Нужно решить, что хранить при временном сбое, как обрабатывать in-progress запросы и сколько повторять тело/заголовки ответа. TTL ключа уменьшает объём хранилища, но после истечения нельзя допустить дубликат критичной операции: финансовые и складские инварианты защищаются ещё и постоянными уникальными идентификаторами/ограничениями и сверкой с провайдером. Ключ не является авторизацией или защитой от CSRF и должен быть связан с аутентифицированным контекстом.

### Rate limiting.
<!-- question-id: 28-http-rest-api-design-q16 -->

#### Ответ
Rate limiting ограничивает расход ресурса и защищает от злоупотребления, случайных циклов клиента и всплесков нагрузки. Правило должно соответствовать риску: ключ лимита может учитывать principal/tenant, endpoint, IP для неаутентифицированного трафика и класс операции; IP в одиночку плохо идентифицирует пользователя за NAT и подвержен обходу. Разделите квоты на чтение/запись, дорогой поиск, отправку OTP, конкурентные запросы и общий аварийный бюджет. Порог и алгоритм (fixed/sliding window, token bucket, concurrency cap) — решение сервиса, которое проверяется по нагрузке и бизнес-ущербу.

Для превышения клиентского лимита верните `429 Too Many Requests` по [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html), поясните безопасно причину и при наличии оценки укажите `Retry-After` — время или дату, когда разумно повторить запрос. Для временной перегрузки самого сервиса подходит `503 Service Unavailable`, при необходимости тоже с `Retry-After`; не используйте 429 как универсальную ошибку для любого сбоя. Сервер может ограничивать запросы даже до аутентификации, поэтому не раскрывайте чувствительные сведения.

Клиент уважает `Retry-After`, применяет exponential backoff с jitter и максимальным дедлайном, не размножает параллельные повторы. Rate limit — не механизм корректности: запись, которую безопасно повторять, всё равно требует idempotency/concurrency контроля. Метрики должны показывать отказы по измерению и tenant, но логи не должны превращать заголовки авторизации и payload в утечку.

### API backward compatibility.
<!-- question-id: 28-http-rest-api-design-q17 -->

#### Ответ
Backward compatibility означает, что существующий корректный клиент продолжает получать ожидаемый результат после изменения сервера. Рискованны удаление/переименование поля, изменение типа или единиц измерения, превращение optional в required, смена значения по умолчанию, новый побочный эффект, изменение правил сортировки/пагинации и сужение набора допустимых статусов. Даже добавление поля может сломать клиента со строгой схемой; добавление значения enum — клиента с исчерпывающим `switch`. Поэтому клиентам полезно иметь политику неизвестных полей/значений, а изменения проверяются на реально используемых версиях SDK.

Расширяйте контракт постепенно: новые выходные поля — как optional и с определённой семантикой; новые возможности входа — без изменения старого поведения; изменение результата — отдельная операция/версия, если безопасной совместимости нет. Не переиспользуйте прежний код ошибки или поле под новый смысл. Контрактные тесты должны проверять и то, что сервер по-прежнему принимает старые запросы, и то, что новые ответы не нарушают старых клиентов.

Для breaking change объявите план миграции, наблюдайте трафик клиентов, поддерживайте период перехода, затем отключайте по опубликованной политике. Заголовки `Deprecation` ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html)) и `Sunset` ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html)) помогают сообщить о намерении и сроке, но не гарантируют, что клиент прочитал предупреждение. Важны changelog, контакт владельца API и способ протестировать новую версию.

### Спроектировать API для marketplace/dating/e-commerce-style приложения.
<!-- question-id: 28-http-rest-api-design-task01 -->

#### Ответ
**Допущения.** Проектирую многопользовательский marketplace/e-commerce API: продавцы публикуют предложения с ценой и остатком; покупатели могут анонимно искать публичные предложения, а заказ и управление ими требуют аутентификации; платёж обрабатывает внешний провайдер, доставка может завершиться асинхронно. Клиентская цена не является авторитетной. Все изменяющие операции проверяют tenant/роль и владение, а деньги/цены передаются в целых minor units с валютой.

**Ресурсы и чтение.** Модель включает `products` каталога, `offers` продавца, `carts`, `orders`, `payments`, `shipments` и `inventory-reservations`. Примеры: `GET /v1/offers?category=...&sort=-createdAt&limit=...&cursor=...`, `GET /v1/offers/{offerId}`, `GET /v1/orders/{orderId}`. Коллекции имеют ограниченный размер страницы, фиксированный сортировочный tie-breaker и cursor, связанный с фильтрами. Публичная проекция offer не раскрывает внутренний остаток/поставщика. Для редактирования offer сервер возвращает `ETag`; изменение требует `If-Match`, чтобы конкурентная запись получила `412`, а не затёрла чужую цену.

**Создание заказа.** `POST /v1/orders` принимает ссылки на offer и количество, адресную/доставочную опцию и ключ операции. Сервер повторно проверяет цену, доступность, лимиты и права; клиент не диктует итоговую сумму. Под транзакцией БД резервирует остаток, создаёт заказ в состоянии `pending_payment` и запись outbox. Если заказ как ресурс создан синхронно, ответ `201 Created` с `Location: /v1/orders/{id}` и представлением; если команда лишь принята к длительной обработке и результат ещё не создан/не завершён, используется `202 Accepted` и URI статуса, что явно отражается в контракте. Событие outbox запускает оплату и доставку; вебхук провайдера проверяется по подписи и дедуплицируется. При успешной оплате состояние становится `paid`, при отказе резерв освобождается/истекает. Межсервисный процесс — saga с компенсацией, а не распределённая транзакция, которой система не умеет обеспечить.

**Повторы, ошибки и надёжность.** Для создания заказа сервер атомарно сохраняет `Idempotency-Key`, scope пользователя/операции, hash нормализованного запроса и сохранённый результат; тот же ключ и payload воспроизводят исходный результат, другой payload получает `409`. Бизнес-уникальность заказа/платежа и дедупликация webhook защищены постоянными ограничениями, поэтому критическая гарантия не зависит только от срока хранения ключа. `400/422` покрывают malformed/непроцессируемый ввод, `401/403` — аутентификацию и доступ, `404` — отсутствующий или скрытый ресурс, `409` — нехватку остатка/недопустимый переход, `412` — устаревший ETag, `429` — квоту. Ошибки оформлены через RFC 9457 без внутренних деталей.

**Безопасность и эксплуатация.** Идентификатор покупателя берётся из проверенного principal, а не из body; права и tenant проверяются на каждом чтении/изменении. Ограничиваются размер тела, частота поиска/оформления и число попыток оплаты; секреты и PII не попадают в логи. Метрики покрывают задержку, процент 4xx/5xx, отказы по запасам, дубли ключей, зависшие заказы, ошибки провайдера и возраст outbox. Сверка заказов с платёжным провайдером восстанавливает пропущенные события. Эти endpoint-ы и состояния — доменные допущения; HTTP-статусы, условия ETag, идемпотентность методов, `Retry-After` и Problem Details берутся из соответствующих RFC, а не из бизнес-модели.
