# Scheduling и timers

## Interview questions

### Где находится requestAnimationFrame относительно tasks/microtasks/rendering?
<!-- question-id: fullstack-interview-01-js-runtime-019 -->

#### Ответ

`requestAnimationFrame` (rAF) — callback браузера на стадии обновления rendering, обычно перед вычислением/отрисовкой следующего кадра. Это не timer и не обычная microtask. Для одного окна callbacks rAF запускаются перед очередным repaint; точное расписание зависит от частоты экрана, скрытой вкладки, throttling и загрузки. После task и microtask checkpoint браузер может сделать rendering update, а в его процессе вызывает rAF callbacks согласно HTML rendering model.

Если rAF callback меняет DOM, изменения могут попасть в ближайший кадр; тяжёлая работа внутри него всё равно задерживает кадр. Для анимации используйте timestamp из callback, а не предполагайте фиксированные 16 мс, и отменяйте цикл через `cancelAnimationFrame`. Для подготовки данных/сети rAF обычно не подходит. Порядок rAF и timer не следует считать гарантированным для произвольного совпадения таймингов; это browser API, которого нет в стандартном Node.js.

### Что делает requestIdleCallback?
<!-- question-id: fullstack-interview-01-js-runtime-020 -->

#### Ответ

`requestIdleCallback` просит браузер вызвать callback, когда у main thread есть свободное время, и передаёт `IdleDeadline`, позволяющий оценить остаток idle budget через `timeRemaining()`. Это best-effort API для некритичной фоновой работы вроде порционного индексирования или предварительной подготовки кеша, а не точный таймер и не способ назначить дедлайн завершения.

Под нагрузкой callback может долго не вызываться; опция `timeout` просит вызвать его по истечении времени, но тогда он может прийти не в idle period. Нужно обрабатывать работу маленькими порциями и продолжать её при следующем вызове. API поддерживается не всеми целевыми браузерами, поэтому для production нужен fallback через доступный task scheduler/таймер и проверка `deadline.didTimeout`.

Не размещайте там критичную логику: сохранение пользовательских данных, сетевой ответ или доступность действия не должны зависеть от того, что браузер когда-нибудь предоставит idle time.

### MessageChannel — зачем и когда используется?
<!-- question-id: fullstack-interview-01-js-runtime-021 -->

#### Ответ

`MessageChannel` создаёт пару связных портов. В браузере отправка через `port.postMessage()` вызывает `message` event на другом порту как отдельную host task. Это позволяет организовать очередь кооперативных задач, уступающую текущему стеку и microtask checkpoint-у, без искусственной задержки таймера. Планировщики UI-фреймворков исторически применяли этот подход, чтобы разбивать работу на части.

Это не приоритетная «магическая» очередь: браузер сам выбирает выполнение относительно других task sources, и сообщения могут задерживаться. API есть в web workers и современных браузерах, но наличие нужно проверить для конкретной среды; в Node.js доступность и семантика отличаются от browser DOM API.

Для разового отложенного callback-а проще `setTimeout`; для частой кооперативной очереди MessageChannel может уменьшить timer clamping, но усложняет отмену и очистку. Закройте порты при завершении, ограничивайте размер очереди и не используйте её для настоящего параллелизма.

### Почему setTimeout(fn, 0) не означает немедленный вызов?
<!-- question-id: fullstack-interview-01-js-runtime-022 -->

#### Ответ

Задержка `0` не исполняет callback синхронно и не прерывает текущий стек. Она означает минимальную запрошенную задержку до того, как timer станет готовым; callback ставится в очередь host task, а затем выполняется, когда event loop дойдёт до него. Текущий JS-код завершится, microtasks выполнятся раньше следующей task, а другие готовые задачи могут быть выбраны раньше.

Минимальные задержки ограничиваются браузером, вложенные timers могут быть clamped, а неактивные вкладки — дополнительно throttled. Node.js имеет собственные правила timers. Поэтому `setTimeout(fn, 0)` полезен для переноса работы за текущий turn, но не для точного времени исполнения и не гарантирует уступку ровно через ноль миллисекунд.

Если задача — отобразить кадр, выбирайте rAF; уступить браузеру при порционной работе — task/MessageChannel/scheduler по поддержке; измерить время — монотонные часы (`performance.now()` в браузере). Не делайте correctness зависимым от миллисекундного порядка таймера.
