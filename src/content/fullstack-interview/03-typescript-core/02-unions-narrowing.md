# Unions и narrowing

## Interview questions

### Union types.
<!-- question-id: fullstack-interview-03-typescript-core-008 -->

#### Ответ

Union A | B означает, что во время выполнения значение принадлежит хотя бы одному из перечисленных типов; до сужения безопасно использовать лишь общие для вариантов свойства. Union — не обязательно размеченное «ровно одно» состояние: структурно типизированное значение может удовлетворять сразу нескольким участникам. Это хороший способ представить конечный набор допустимых состояний или входных форм. Для протокола состояний добавляют literal discriminant, например { kind: "loading" } | { kind: "success"; data: T }; это делает сужение предсказуемым и позволяет компилятору обнаружить необработанные варианты.

### Intersection types.
<!-- question-id: fullstack-interview-03-typescript-core-009 -->

#### Ответ

Intersection A & B требует, чтобы значение удовлетворяло одновременно обоим контрактам. Если у участников разные независимые поля, результат комбинирует их; если одно и то же поле несовместимо, например string и number, это поле становится невозможным (never), а некоторые дальнейшие проверки могут свести целый объект к never. Это не «объединение возможностей» — для него служит union. Intersection полезен для композиции mixin-подобных контрактов, но при конфликте типов обычно яснее определить новый тип или исправить границы, чем маскировать конфликт пересечением.

### Literal types.
<!-- question-id: fullstack-interview-03-typescript-core-010 -->

#### Ответ

Literal type описывает конкретное значение, например "GET", 200 или true, вместо всей категории string, number или boolean. Он возникает из const-контекста, аннотации, readonly tuple или union литералов и служит основой для discriminated unions и точных API-контрактов. Обычная изменяемая переменная обычно widening: const method = "GET" сохраняет литерал, а let method = "GET" чаще получает string, поскольку допускает дальнейшее присваивание. Для составных конфигураций можно применить as const или satisfies; первый фиксирует readonly-литералы, второй проверяет совместимость, сохраняя полезную конкретность выражения.

### Type narrowing.
<!-- question-id: fullstack-interview-03-typescript-core-011 -->

#### Ответ

Type narrowing — статическое уточнение типа переменной по контролируемому потоку: после typeof, instanceof, проверки discriminant, null-check или пользовательского predicate компилятор рассматривает только те варианты, которые могут пройти проверку. Сужение привязано к потоку управления и может быть отменено, если значение переназначено; для изменяемых свойств и alias-ов компилятор консервативен, потому что другой код мог изменить данные. Проверки TS доказывают лишь форму на этой ветке по правилам компилятора, но не валидируют входящие JSON/данные пользователя автоматически. На внешней границе сначала нужна настоящая runtime-проверка, а потом narrowing.

### Discriminated unions.
<!-- question-id: fullstack-interview-03-typescript-core-012 -->

#### Ответ

Discriminated union — union объектных типов с общим обязательным полем-дискриминантом, обычно literal-строкой: { kind: "success"; data: T } | { kind: "failure"; error: Error }. Проверка switch (state.kind) сужает state до соответствующего варианта и открывает только его поля. Это явнее и безопаснее, чем множество независимых boolean-флагов, которые допускают невозможные комбинации (loading и success одновременно). Для полноты добавляют default с проверкой never: компилятор заставит обработать вариант, появившийся позже. Важно сохранять дискриминант literal-типом, иначе он размоется до string.

### Type guards.
<!-- question-id: fullstack-interview-03-typescript-core-013 -->

#### Ответ

Type guard — условие или функция, после которой TS сужает тип: встроенные typeof, instanceof, in, сравнение с литералом и truthiness, а также user-defined predicate вида value is User. Type guard — не отдельный runtime-механизм TypeScript: в JavaScript выполняется реальное условие, а компилятор использует его форму как доказательство. Поэтому выражение должно действительно проверять обещанное. Ложный predicate (например, возврат true без проверки) обходит type checker и может привести к runtime-ошибке; сложные структуры нужно валидировать по полям, а иногда проверять схемой, которая одновременно даёт runtime-результат и корректную типизацию.
